# rf2-4lv73 — What may be tracked under `ai/`?

| **Related live bug** | `rf2-2dupb` — the intended `ai/extended-context/` negation is inert |
| **Related lifecycle bead** | `rf2-vxgfnd.99.1` — remove the temporary tracked synthesis tree at S7 |
| **Evidence baseline** | `origin/main` at `9e78d4f989`, fetched and inspected 2026-07-18 |

## Decision in one sentence

Mike must decide whether `ai/` is truly local-only, or local **by default**
with a small set of explicit durable exceptions—and, if exceptions remain,
whether new files in those locations are authorized by location alone or only
when a task explicitly puts them there.

The repository cannot truthfully keep the current answer. It has 85 tracked
files under `ai/`, a documented committed-context directory that is currently
broken, and an absolute instruction saying never to stage any of them.

## What the live repository says

### `CLAUDE.md` gives an absolute prohibition

The root instruction says:

> **The whole tree is local-only** (`/ai/` is in `.gitignore`); never `git add`
> anything under it.

Later, its pull/stash guidance repeats the premise:

> The `ai/` tree is local-only and won't show up in `git status`.

Both statements are false for tracked files. An ignore rule affects discovery
of untracked paths; it does not untrack an existing file. Editing a tracked
file under `ai/` appears in `git status`, stages normally, and belongs in the
commit when that file is in task scope.

### Git tracks exactly two `ai/` trees today

`git ls-tree -r --name-only origin/main ai` returns exactly 85 paths:

| Tracked tree | Files | Current mechanism |
|---|---:|---|
| `ai/findings/new-substrate-synthesis/` | 61 | Force-tracked; edits stage normally, new files remain ignored and require `git add -f` |
| `ai/findings/new-substrate-codex/` | 24 | Force-tracked by the same mechanism |
| Everything else under `ai/` | 0 | Untracked/local today |

This is not an accidental single-file leak. The synthesis tree was
deliberately committed as the worker-visible program plan. Its S7 removal is
tracked by `rf2-vxgfnd.99.1`, and that bead explicitly forbids removing it
before its live contracts and citations have durable homes. The codex source
tree is also deliberately tracked, although the S7 cleanup bead names only the
synthesis tree.

The current `.gitignore` comment knows about both trees, but ends with the
singular claim:

> Only this subtree is tracked; all other `ai/findings/*` stay local.

That sentence is inaccurate. It should say “these two subtrees” and name both,
or state the rule without the misleading singular.

### `ai/extended-context/` is intended durable, but is not currently unignored

The mayor-method documents consistently classify
`ai/extended-context/` as committed durable context:

- the mayor consults it at bootstrap;
- retrospectives contribute context a future mayor would need;
- `bootstrap.md` explicitly contrasts committed extended context with
  gitignored findings.

`.gitignore` attempts to implement that contract:

```gitignore
/ai/
!/ai/extended-context/
!/ai/extended-context/**
```

It does not work. Git does not descend into a directory excluded by `/ai/`, so
the later negations cannot re-include a child. Independent verification against
`origin/main`:

```text
$ git check-ignore -v ai/extended-context/example.md
.gitignore:33:/ai/  ai/extended-context/example.md
```

There are zero tracked extended-context files, so the broken rule remained
invisible until a retrospective tried to add the first one. This is the live
`rf2-2dupb` bug. Its proposed mechanical repair—change `/ai/` to `/ai/*`, then
verify the existing negations—is consistent with Git's directory traversal
rules and preserves the ignored-by-default posture.

Any `CLAUDE.md` wording that says extended-context stages normally is truthful
only after, or atomically with, that fix. Wording this decision as though the
negation already works would replace one bad instruction with another.

### The mayor-method default and the temporary exception are different layers

`docs/the-mayor-method/README.md` says ordinary `ai/findings/` are exploratory,
gitignored, and never committed; actionable results graduate into Beads, specs,
or docs. That remains a good default.

The two tracked new-substrate trees are deliberate exceptions to that default:
the program needed a shared, clean-clone-visible design record while its
contracts graduated. The synthesis exception is explicitly temporary. It does
not justify making every finding durable, and the general method does not make
the exception cease to exist.

The instruction should say “default plus exceptions,” rather than forcing one
layer to pretend the other is absent.

## Instruction precedence and why the contradiction is a real defect

The repository has only root `AGENTS.md` and root `CLAUDE.md`; there are no
nested instruction files changing the `ai/` rule.

- `AGENTS.md` is silent about `ai/`. It neither repeats nor repairs the false
  prohibition.
- `CLAUDE.md` is an imperative agent instruction, not descriptive background.
  “Never git add” is intentionally read as a hard constraint by a careful
  worker.
- `.gitignore` is Git mechanics plus comments. It is not a higher-precedence
  authorization document. A worker should not be expected to infer that a
  comment silently overrules an explicit agent instruction.
- An explicit operator/dispatch instruction can place a tracked `ai/` file in a
  task's write scope. That resolves one task, but requiring every worker to
  recognize and justify a local override is exactly the friction a root
  instruction exists to remove.

The right response is not “workers should know to disobey `CLAUDE.md`.” The
right response is to make the standing instruction true, so obedience and
successful delivery point in the same direction.

There is no need to duplicate the full boundary in `AGENTS.md` merely because
it is currently silent. Duplicating a volatile exception roster across two
instruction files creates another drift surface. The minimal repair is a
truthful `CLAUDE.md` rule plus correct Git mechanics; an explicit task remains
the authority for whether a particular new durable file belongs in scope.

## Concrete worker failure modes

| Failure | How the current wording causes it | Consequence |
|---|---|---|
| **Correct edit, refused commit** | Worker edits an already-tracked synthesis file, then reads “never git add anything under it” literally | Work is stranded or returned as a proposal despite being the assigned implementation |
| **Missing new file** | Worker creates a new file in a force-tracked tree and uses ordinary `git add`; Git ignores it and status stays clean | PR omits the main deliverable while the worker reports success |
| **Broad force-add** | Worker concludes the only way past the contradiction is `git add -f ai/...` without a narrow authorization rule | Local findings, decisions, prompts, or private scratch can be committed accidentally |
| **Repeated archaeology** | Every worker runs `git ls-files`, reads history, and re-derives why two paths are exceptional | Time and context are wasted; different agents reach different policies |
| **False clean-tree assumption** | Pull guidance says `ai/` never appears in status, so a worker overlooks a tracked synthesis edit | Pull/rebase conflict, lost hand-off, or accidental mixed commit |
| **Blocked retrospective** | Worker follows the documented “committed extended context” path, but the inert negation hides the file | Durable context never reaches the next clean clone; `rf2-2dupb` is the observed instance |
| **Exception becomes permission** | Wording merely says “new files there need `git add -f`,” without saying when adding one is authorized | Location alone is mistaken for permission to turn exploratory material into repository history |
| **Stale lifecycle rule** | S7 removes synthesis tracking but the instruction continues to list it | Future workers force-add files into a tree that has intentionally returned to local-only |

The key distinction is between **mechanics** and **authorization**:

- “This existing file is tracked” is a Git fact.
- “A new ignored file belongs in durable history” is a task/policy decision.
- `git add -f` is only the mechanism after that decision; it is not permission.

## What Mike must decide

### 1. The top-level policy

Choose between:

- `ai/` is universally local-only, requiring the 85 tracked files to be
  untracked now; or
- `ai/` is local-only by default, with exact durable exceptions.

The second matches the live program plan and avoids prematurely executing the
S7 cleanup bead.

### 2. The fate of `ai/extended-context/`

Choose between:

- keep the mayor-method contract and fix `rf2-2dupb`, so extended context is an
  ordinary unignored committed directory; or
- retire that contract, remove the ineffective negations, and make
  retrospectives local/Bead-only; or
- require explicit force-add for every extended-context contribution.

The first is the most coherent. The directory has a real named consumer—a fresh
mayor—and the one-character ignore repair makes the existing design work
without widening the rest of `ai/`.

### 3. Authorization for new files in force-tracked trees

Choose whether:

- any new file under the two named trees may be force-added; or
- a new file may be force-added only when the current task explicitly places
  it in that durable tree.

The second trusts the worker while keeping the boundary intentional. The
worker does not need separate permission after the task names the durable
location, but a broad “write a finding” task does not silently authorize
repository history.

### 4. How much instruction duplication to accept

Choose whether the rule is:

- stated once in `CLAUDE.md`, with `.gitignore` implementing the mechanics; or
- copied into both `CLAUDE.md` and `AGENTS.md`.

One correct rule is smaller and less likely to drift. `AGENTS.md` is not
currently wrong; it is silent. If cross-agent discoverability later proves
insufficient, add a one-line pointer rather than a second exception roster.

## Credible policy options

### Option A — local by default, exact durable exceptions

Replace the universal prohibition with:

- named force-tracked trees;
- normal staging for existing tracked files;
- `git add -f` only for task-authorized new files in those trees;
- ordinary committed behavior for `ai/extended-context/` once `rf2-2dupb` is
  fixed;
- a hard local-only rule for every other `ai/` path.

**Consequences:**

- matches all 85 tracked files and the mayor-method's intended committed
  context;
- gives workers an exact, low-friction decision procedure;
- prevents location from becoming blanket authorization;
- requires the S7 cleanup to remove synthesis from the exception list when it
  removes the tracked tree.

This is the recommended option.

### Option B — universally local-only

Keep the current `CLAUDE.md` instruction and untrack every `ai/` file; remove
the extended-context exception.

**Consequences:**

- the instruction becomes simple and literally true;
- clean clones lose the current worker-visible source plan and codex design
  record;
- it executes the substance of `rf2-vxgfnd.99.1` before its promotion/citation
  gates;
- retrospectives cannot use the committed context channel documented by the
  mayor method.

This may be a valid end state after the planned graduations, but it is false to
the current program state.

### Option C — make every named durable directory normally unignored

Change the ignore structure so both new-substrate trees and extended-context
are negated exceptions. New files in all three appear in status and use ordinary
`git add`.

**Consequences:**

- removes `git add -f` friction;
- but turns any scratch file placed in the large findings trees into a visible
  commit candidate;
- weakens the deliberate “new durable file requires an explicit choice” tooth;
- expands a temporary exception when the stage plan is trying to retire it.

This optimizes a rare command at the cost of a safer default.

### Option D — keep the contradiction and override it per dispatch

Leave `CLAUDE.md` unchanged; every task involving a tracked `ai/` file says to
violate the prohibition.

**Consequences:**

- no immediate repository-doc edit;
- every dispatch grows a special boundary clause;
- agents must decide whether the task truly overrides the standing rule;
- missing-file and broad-force-add failures remain likely;
- trust in the rest of the instruction file erodes.

This is the highest-friction option.

### Option E — use Git state alone as the instruction

Say only: “stage tracked files; do not stage ignored files.”

**Consequences:**

- future-proof for existing paths;
- but says nothing about when a new force-added file is authorized;
- does not express why extended-context is intended committed;
- makes `git check-ignore` rather than project intent decide policy.

Git state is an excellent diagnostic, not a complete governance rule.

## Minimal implementation after the ruling

If Mike chooses Option A, the change can stay small:

1. Resolve `rf2-2dupb` first or in the same PR by making the
   `ai/extended-context/` negation effective; verify with `git check-ignore -v`
   against extended-context, an ordinary findings path, and both force-tracked
   trees.
2. Replace the absolute local-only paragraph in `CLAUDE.md` with the
   default-plus-exceptions wording below.
3. Correct the later stash sentence so it distinguishes ignored local files
   from tracked exception files.
4. Correct `.gitignore`'s singular “Only this subtree” description to the
   actual two force-tracked trees. Do not make `.gitignore` comments the
   authority for authorization.
5. Add the `CLAUDE.md` exception-list cleanup to the S7 removal work represented
   by `rf2-vxgfnd.99.1`, so synthesis does not remain blessed after `git rm`.
6. Do not rewrite the mayor method, move artefacts, unignore the large findings
   trees, or add a tracking helper script. None is needed to make the rule
   reliable.

Focused verification is enough:

```text
git ls-tree -r --name-only HEAD ai/
git check-ignore -v ai/findings/ordinary-new-file.md
git check-ignore -v ai/extended-context/new-context.md
git check-ignore -v ai/decisions/new-decision.md
git ls-files --error-unmatch <an existing synthesis path>
git ls-files --error-unmatch <an existing codex path>
```

Expected final state:

- ordinary findings and decisions remain ignored;
- new extended-context files are not ignored;
- the two existing force-tracked trees remain tracked;
- edits to their existing files stage normally;
- their new files remain ignored unless deliberately force-added;
- no unrelated `ai/` path becomes a commit candidate.

This dossier task is itself an example of the task-scoped exception: Mike
explicitly required the current `ai/decisions/<bead-id>.*.md` packets to reach
the mayor's check-in. That authorizes force-adding these named files for this
task; it does not make `ai/decisions/` a standing durable tree or authorize
unrelated decision scratch.

## Codex Recommendation

Rule **Option A** and land it together with the mechanical `rf2-2dupb` fix.
The smallest truthful policy is “local by default, exact durable exceptions,”
with task scope—not directory location or `git add -f`—authorizing a new durable
file.

Use this replacement wording in `CLAUDE.md`:

> **The `ai/` tree is local-only by default, not universally.** Do not stage an
> ignored file under `ai/` unless the current task explicitly places it in a
> durable exception.
>
> - `ai/findings/new-substrate-synthesis/` and
>   `ai/findings/new-substrate-codex/` are force-tracked project trees. Edits
>   to their existing tracked files stage normally. A new file there belongs
>   in Git only when the task explicitly puts it in that durable tree; stage
>   that new file with `git add -f`.
> - `ai/extended-context/` is committed durable context and stages normally.
> - Every other `ai/` path—including ordinary `ai/findings/`,
>   `ai/decisions/`, and `ai/specs/`—remains local and must not be added.
>
> If a path is unclear, use `git ls-files --error-unmatch <path>` to test
> whether an existing file is tracked and `git check-ignore -v <path>` to see
> the rule for a new path. Git mechanics do not authorize expanding the
> durable set.

That wording assumes `rf2-2dupb` lands atomically or first. Until its ignore
repair is present, the `ai/extended-context/` bullet is not true and should not
ship alone.

Also replace the later stash parenthetical with:

> Ignored/local `ai/` files do not appear in ordinary status; tracked exception
> files do and must be handled like any other tracked work before pulling.

Correct `.gitignore` to describe **both** force-tracked findings trees, and make
the extended-context negation effective. Do not declare `.gitignore` comments
the authoritative policy: they have already drifted, and ignore patterns
describe mechanics rather than permission.

No `AGENTS.md` duplication, new policy file, helper command, or broad
unignoring is warranted. This rule is short enough for a programmer or agent
to apply without ceremony, precise enough to prevent accidental force-adds,
and temporary where the program is temporary. When S7 removes the synthesis
tree, the same cleanup must delete that one bullet entry.
