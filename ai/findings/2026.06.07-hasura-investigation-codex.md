# Hasura Migration Investigation for re-frame2

Date: 2026-06-07

Status: Findings and design recommendation

Related documents:

- `docs/EP/resource-queries.md`
- `docs/EP/app-db-runtime-partition.md`
- `spec/Pattern-WebSocket.md`

## Executive Recommendation

Day8 should create a first-party optional library, tentatively
`day8/re-frame2-hasura`, for apps that use Hasura GraphQL and realtime
WebSockets.

That library should not be a second client-side data model. It should be an
adapter over the re-frame2 resource, mutation, route, machine, frame, trace, and
Xray contracts:

- GraphQL reads become `reg-resource` entries.
- GraphQL writes become `reg-mutation` entries.
- Hasura live queries become resource instances whose active owners keep a
WebSocket operation alive.
- JWT refresh, WebSocket connection, reconnect, resubscribe, and stale socket
suppression are modeled by state machines.
- Route metadata and explicit events cause work; subscriptions remain passive
materialized views.
- Tooling sees operation names, variables summaries, owners, scopes, status,
connection state, and errors without receiving auth tokens or raw sensitive
payloads.

The library should be outside core, but re-frame2 should expose a narrow
extension surface for first-party feature modules: resource transports, mutation
transports, route metadata keys, Xray panels, trace redactors, teardown hooks,
and test stubs. That is enough for Hasura without making an unrestricted plugin
system.

## Source Facts

### Hasura

The existing Day8 apps are using the Hasura GraphQL Engine v2-style endpoint
shape, typically `/hasura/v1/graphql`, proxied through nginx with WebSocket
upgrade headers.

Hasura JWT mode expects a client-provided `Authorization: Bearer <JWT>` header.
Hasura verifies the JWT and extracts `x-hasura-*` session variables; the docs
call out the role variable and commonly-used user id as authorization inputs.
The documented JWT claims include `x-hasura-default-role`,
`x-hasura-allowed-roles`, and optional app-specific `x-hasura-*` claims.

Hasura subscriptions are query-like operations sent over WebSockets. The v2 docs
state that a subscription receives updates when upstream fields change, supports
query concepts, and has a single-root-field caveat: multiple active
subscriptions must be separate operations. Hasura distinguishes live queries,
which send the latest query result, from streaming subscriptions, which stream
rows by cursor/batch. Existing Day8 apps mostly use live-query semantics.

Hasura v2 documents support for both the Apollo `subscriptions-transport-ws`
protocol and the GraphQL-over-WebSocket protocol implemented by the `graphql-ws`
library, selected by the `Sec-WebSocket-Protocol` header. The current Day8
`re-graph` usage and the rf8 `re-graph2` experiment are built around the legacy
`"graphql-ws"` subprotocol string, so migration must support that path first and
add newer protocol support by configuration and test matrix rather than by
assumption.

Hasura Event Triggers automate asynchronous logic on connected database changes
for `INSERT`, `UPDATE`, and `DELETE`. This matches Day8's effects-table /
transactional-outbox style in Exceler8: the SPA writes durable intent to the
database, Hasura/Django/Celery perform longer-running work, and the UI observes
resulting state.

Hasura Allow Lists can restrict execution to known GraphQL operations in
metadata. That matters for a re-frame2 library because registered resources and
mutations can expose operation names/hashes and make allow-list drift visible.

The older apps share a repeated pattern:

- fetch a Day8 JWT from Django;
- open a `re-graph` WebSocket to Hasura;
- refresh JWT before expiry and re-send `connection_init`;
- dispatch initial queries/subscriptions after auth;
- store Hasura results under app-db paths such as `[:subs :hasura ...]` or
  `:hasura/query`;
- use `:dirty?` flags, async-flow gates, and callback events to coordinate
  loading;
- use operation string builders in several places, often with TODOs to move to
  variables or plain GraphQL documents;
- use manual `re-graph/subscribe`, `re-graph/unsubscribe`, and `re-graph/mutate`
  calls in application handlers;
- handle partial GraphQL errors by custom notification events;
- duplicate connection/JWT/toast/Datadog behavior across apps.

Exceler8 shows the core pain clearly. Its ratecard UI keeps base lookup
subscriptions (`ratesets`, `station`, `network`, `market`, etc.), dynamic
detail subscriptions for the currently edited rateset, one-shot detail queries,
mutation handlers that manually set `:dirty?`, and local optimistic patches
where Hasura subscription delivery may lag.

Maxim8 and Dash8 show the same family of pattern: user/profile/bootstrap queries,
campaign-header subscriptions, dynamic detail subscriptions, manual
unsubscribe/resubscribe, and app-db result buckets.

rf8 is important because it already demonstrates the right re-frame2 direction:
`re_graph2` owns the JavaScript `WebSocket` in a host-side registry, not in
app-db, and models connection/reconnect/resubscribe with a state machine and a
spawned socket actor. That should be treated as a prototype for the Hasura
library, not as the final resource-layer API.

### re-frame2 Constraints

The resource EP makes the central policy decision:

- resources are runtime-managed server-state read models;
- views are passive;
- route metadata and events cause work;
- GraphQL query is a v1 built-in transport;
- GraphQL mutation belongs in the mutation slice;
- generic transport extension is later;
- subscription-driven fetching should not be the default causal model.

The WebSocket pattern makes the long-lived connection decision:

- connection lifecycle is state-machine-shaped;
- the socket object is a host handle outside frame-state;
- serializable connection facts live in state;
- stale socket events are suppressed by an epoch/source-socket id.

The app-db/runtime partition EP reinforces that distinction:

- durable app state and durable runtime state are separate frame partitions;
- host handles, timers, abort controllers, sockets, and protocol handles are not
  serialized frame-state;
- runtime facts remain inspectable and replayable where possible.

## Problems To Solve

### 1. Hasura State Is Currently App-Specific State Buckets

Existing apps store server-state snapshots under app-specific paths such as
`[:subs :hasura :ratesets]` or `[:hasura/query :user]`. That works, but it loses
standard resource semantics: cache key identity, stale/fresh state, active
owners, route ownership, SSR hydration, GC, dedupe, invalidation, and Xray
visibility.

The migrated shape should be:

```clojure
(rf/reg-resource
  :exceler8/ratesets
  {:transport :rf.hasura/subscription
   ...})
```

The app can still define ordinary subscriptions over
`[:rf.resource/data {:resource :exceler8/ratesets ...}]`, but the cache entry is
owned by the resource runtime rather than a custom `[:subs :hasura]` convention.

### 2. Loading And Dirty State Are Hand-Rolled

The current `:dirty?` flags and boot async-flow barriers are manually maintained.
They do not distinguish first-load failure, background refresh failure, stale
data, disconnected-but-showing-last-data, and active refetch.

re-frame2 resources already have the right vocabulary:

- `:loading` for first load;
- `:fetching` for refresh while data remains visible;
- `:loaded` with `:stale-at` for stale but usable data;
- `:error` for first-load failure;
- `:refresh-error` for failed refresh while preserving prior data.

For Hasura live queries, a disconnected socket should usually preserve the last
known data and attach connection/resource warnings, not erase the data or force
views to infer stale/error state from `:dirty?`.

### 3. Connection Lifecycle Is Duplicated And Leaky

JWT fetch/refresh, WebSocket open/close, connection-init, reconnect, and
resubscribe are copied across Dash8, Exceler8, Maxim8, and rf8 variants.

That lifecycle should be a reusable Hasura endpoint machine:

```text
:idle
  -> :authenticating
  -> :active / :connecting
  -> :active / :awaiting-ack
  -> :active / :connected
  -> :reconnecting
  -> :failed
```

The machine should own:

- current endpoint id;
- URL and selected WebSocket protocol;
- JWT expiry and refresh schedule;
- connection generation;
- operation registry;
- reconnect/backoff state;
- last connection error;
- redacted auth/session facts.

The socket actor owns the JavaScript `WebSocket` host handle. Operation handles
and timer ids live in side tables keyed by frame, endpoint id, operation id, and
generation.

### 4. Query Construction Is Too Stringly

Several app files build GraphQL strings with interpolation. That has three
costs:

- variables and sensitive values are mixed into documents;
- allow-list/persisted-operation adoption is harder;
- tools cannot reliably summarize operation identity and parameter shape.

The Hasura library should accept raw GraphQL document strings for migration, but
the recommended registration should separate document and variables:

```clojure
(rf/reg-resource
  :launcher/user-profile
  {:transport      :rf.hasura/query
   :endpoint       :day8/core
   :operation-name "UserProfile"
   :document       user-profile-query
   :variables      (fn [{:keys [user-id]} _ctx]
                     {:user_id user-id})
   :params-schema  [:map [:user-id :string]]
   :data-schema    :app/user-profile})
```

The registration can then carry operation name, document hash, variable schema,
redaction policy, and allow-list metadata.

### 5. Scopes Are Security-Critical

Hasura authorization depends on JWT/session variables and optional role headers.
Day8 apps also include site, sudo/admin/preshared-key, and multi-tenant routing
concerns.

Resource scope must include every fact that can change the visible result:

```clojure
[:rf.scope/hasura
 {:endpoint :day8/core
  :user-id  user-id
  :site-id  site-id
  :role     role
  :sudo     sudo-id}]
```

On logout, site switch, role switch, token principal change, or sudo change, the
library should clear the old Hasura scope and close/re-auth the corresponding
connection. Otherwise a cache hit can show data authorized for a previous
principal.

### 6. Tools And AIs Need Metadata, Not Raw Data

Current Hasura state is opaque app-db payload. Xray cannot easily answer:

- which route owns this query?
- why is this subscription active?
- which variables were used?
- what operation failed?
- did a stale response get suppressed?
- is this data retained by route, machine, or debug code?
- did a mutation invalidate the resources it should have invalidated?

The Hasura library should contribute resource/operation panels and trace rows
without exposing raw JWTs or sensitive variables.

## Target Architecture

### Layer 1: Hasura Endpoint Registration

Add a first-party registration surface in the Hasura library:

```clojure
(rf/reg-hasura-endpoint
  :day8/core
  {:doc "Primary Day8 Hasura endpoint."

   :http-url
   (fn [{:keys [db]}]
     (-> db :site-config :hasura/http-url))

   :ws-url
   (fn [{:keys [db]}]
     (-> db :site-config :hasura/ws-url))

   :auth
   {:token-resource :day8/hasura-jwt
    :headers        (fn [{:keys [token role site sudo]}]
                      (cond-> {"Authorization" (str "Bearer " token)}
                        role (assoc "X-Hasura-Role" role)
                        site (assoc "X-DAY8-SITE" site)
                        sudo (assoc "X-DAY8-ADMIN-SUDO" sudo)))}

   :websocket
   {:protocols [{:id :hasura/legacy-graphql-ws
                 :sec-websocket-protocol "graphql-ws"}
                {:id :graphql/transport-ws
                 :sec-websocket-protocol "graphql-transport-ws"}]
    :default-protocol :hasura/legacy-graphql-ws
    :ack-gate? true
    :reconnect {:base-ms 1000
                :max-ms 30000
                :max-retries nil}}

   :redact
   {:headers #{"Authorization" "X-DAY8-ADMIN-SUDO"}
    :variables #{:password :token :secret}}})
```

This registration defines endpoint-level behavior; it does not fetch data by
itself.

### Layer 2: Hasura Connection Machine

The library should include a reusable connection machine, building on rf8's
`re_graph2` work:

- spawn a socket actor at the active parent state;
- keep the JS `WebSocket` in a host-side registry;
- send `connection_init` with redacted auth payload;
- wait for `connection_ack` by default, with a compatibility flag for old
  deployments if needed;
- resubscribe all active live resources on reconnect;
- suppress late frames from stale socket generations;
- expose connection state as machine tags and Xray state;
- keep query/mutation-over-WebSocket as an optional internal capability, but
  prefer HTTP for one-shot query/mutation unless an app has a reason to use the
  socket.

The connection machine should not know about app-specific routes, toasts, or
boot flows. Apps can observe state through events or subscriptions.

### Layer 3: GraphQL Resource Transports

The resources artifact should own these built-ins:

```clojure
:rf.graphql/query
:rf.graphql/mutation
```

The Hasura library can provide Hasura-specialized wrappers:

```clojure
:rf.hasura/query
:rf.hasura/subscription
:rf.hasura/mutation
```

`:rf.hasura/query` should lower to HTTP POST by default. It gets standard
resource behavior: dedupe, stale suppression, route ownership, SSR preload,
hydration, and Xray traces.

`:rf.hasura/subscription` should be a live resource transport. An `ensure`
should register or join a WebSocket operation. Releasing the last active owner
sends a stop/complete frame and removes the operation from the active registry.
The latest payload updates the resource entry.

Hasura's single-root-field subscription caveat means each resource subscription
should map to one GraphQL subscription operation. Do not try to bundle unrelated
live resources into one query unless the resource itself intentionally models a
single aggregate snapshot.

### Layer 4: Mutation Runtime

Hasura writes should use the same `reg-mutation` runtime as HTTP writes:

```clojure
(rf/reg-mutation
  :rateset/rename
  {:transport      :rf.hasura/mutation
   :endpoint       :day8/core
   :operation-name "RenameRateset"
   :document       rename-rateset-mutation
   :params-schema  [:map
                    [:rateset-id :string]
                    [:name :string]]
   :variables      (fn [{:keys [rateset-id name]} _ctx]
                     {:rateset_id rateset-id
                      :name name})
   :invalidates    (fn [{:keys [rateset-id]} _result]
                     #{[:rateset/id rateset-id]
                       [:ratesets]})
   :optimistic     {:patches
                    (fn [{:keys [rateset-id name]}]
                      [{:resource :exceler8/ratesets
                        :patch    [:rename-rateset rateset-id name]}])}})
```

The mutation runtime should handle:

- instance ids for concurrent submissions;
- pending/error/result state;
- GraphQL partial success policy;
- explicit invalidation;
- optional optimistic patch/rollback;
- trace-visible affected resources.

Do not rely on Hasura live queries alone to repair every local state after a
write. Some current apps already have cases where a mutation's net result does
not trigger an observed subscription update. The write should explicitly patch,
populate, or invalidate the relevant resources.

### Layer 5: Route And Machine Ownership

Route-owned data should be declared in route metadata:

```clojure
(rf/reg-route
  :route/rateset-edit
  {:path "/ratesets/:id"
   :resources
   [{:resource  :exceler8/ratesets
     :blocking? true}
    {:resource  :exceler8/ratecards/by-rateset
     :params    (fn [route _ctx]
                  {:rateset-id (get-in route [:params :id])})
     :blocking? true}]})
```

Machine-owned resources should be used for workflows:

- publish ratecard;
- delete campaign;
- upload/import/parse/publish;
- long-running effects-table jobs;
- retryable background operations.

A machine can own a resource while it is in a workflow state. The resource
runtime handles cache mechanics; the machine handles semantic progress and
allowed transitions.

## How This Maps Existing Apps

### Exceler8

Current:

- `:hasura/initial-subs-queries` starts base lookup subscriptions and waits for
  arrival events.
- `[:subs :hasura :ratesets]`, `:station`, `:network`, `:market`, etc. hold
  data and `:dirty?`.
- ratecard editor dynamically subscribes to `:ratecards` for one rateset and
  unsubscribes on exit.
- mutations manually dirty `:ratesets` and `:ratecards`, and sometimes patch
  local data to compensate for live-query lag.

Target:

- base lookups are route/bootstrap resources with owners;
- `:exceler8/ratesets` is a live Hasura resource;
- `:exceler8/ratecards/by-rateset` is a route/editor-owned live resource scoped
  by `rateset-id`;
- one-shot details are query resources;
- `:dirty?` becomes `:fetching`, `:loaded`, `:stale?`, and `:refresh-error`;
- local compensation becomes explicit mutation optimistic patch or populate;
- editor exit releases the route/machine owner and the library unsubscribes.

### Maxim8

Current:

- header codes query;
- campaign header subscription;
- campaign detail subscription while editing;
- manual unsubscribe/resubscribe on filters;
- app-db result paths under `:hasura/query`.

Target:

- `:maxim8/day8-codes` query resource, probably boot/route owned;
- `:maxim8/campaign-headers` live resource keyed by status filter params;
- `:maxim8/campaign-detail` editor-owned live resource keyed by campaign id;
- filter change changes resource params; old owner releases and new owner
  ensures;
- stale edit warnings can become machine logic comparing edit snapshot to live
  resource generation.

### Dash8 / rf8

Current:

- Dash8 still has the older `re-graph` shape.
- rf8 has moved the WebSocket into `re_graph2` with a connection machine and
  socket actor, but result storage is still app-specific.

Target:

- lift `re_graph2` connection/socket work into `day8/re-frame2-hasura`;
- replace app-specific `:hasura/query` result buckets with resources;
- keep app-specific boot and notification decisions in app code.

## Should We Create A Library?

Yes. The duplication across Day8 apps is strong evidence that this should be a
library. It should be first-party because it needs to exercise and validate
re-frame2's resource, mutation, machine, routing, frame, Xray, SSR, and privacy
contracts together.

Proposed artifact:

```text
day8/re-frame2-hasura
```

Likely namespaces:

```text
re_frame.hasura
re_frame.hasura.endpoint
re_frame.hasura.connection
re_frame.hasura.socket
re_frame.hasura.codec
re_frame.hasura.transport.query
re_frame.hasura.transport.subscription
re_frame.hasura.transport.mutation
re_frame.hasura.resource
re_frame.hasura.xray
re_frame.hasura.test-support
```

The library should depend on:

- `day8/re-frame2-resources`;
- `day8/re-frame2-machines`;
- managed HTTP;
- routing integration when route resources are used;
- Xray only through an optional dev/tooling namespace.

It should not require every re-frame2 app to carry Hasura code.

## Should re-frame2 Have A Plugin Extension Feature?

Yes, but keep it narrow and explicit.

Hasura needs these extension points:

- register resource transports;
- register mutation transports;
- contribute route metadata keys or validators;
- contribute Xray panels and trace summarizers;
- contribute AI egress redactors and variable/header elision rules;
- contribute frame teardown hooks for side tables;
- contribute test-support stubs and fake transports.

That is not the same as an unrestricted plugin system. A generic "plugin can
hook anything" surface would make correctness, toolability, and privacy harder.
The better design is a small extension API per artifact:

```clojure
(rf/reg-resource-transport :rf.hasura/query ...)
(rf/reg-mutation-transport :rf.hasura/mutation ...)
(rf/reg-route-metadata-key :resources ...)
(rf/reg-xray-panel :hasura/resources ...)
(rf/reg-egress-redactor :rf.hasura/variables ...)
(rf/reg-frame-teardown-hook :rf.hasura/sockets ...)
```

The Hasura library can then be a proof that first-party extensions compose
without making core Hasura-specific.

## Live Queries, Streaming, And Sub-Resources

### Live Queries

Most current Day8 uses fit Hasura live queries: the UI wants the latest snapshot
of a query result.

Represent those as live resources:

```clojure
(rf/reg-resource
  :exceler8/ratesets
  {:transport      :rf.hasura/subscription
   :endpoint       :day8/core
   :operation-name "Ratesets"
   :document       ratesets-subscription
   :variables      (fn [_params _ctx] {})
   :stale-after-ms nil
   :gc-after-ms    300000
   :tags           (fn [_params _data]
                     #{[:ratesets]})})
```

`stale-after-ms nil` is appropriate when the WebSocket is connected and Hasura is
continuously pushing snapshots. If the connection drops, the entry remains
loaded with last-known data and connection warning/refresh-error metadata.

### Streaming Subscriptions

Hasura streaming subscriptions are different: they emit rows by cursor and
batch. That is useful for append-only feeds, logs, messages, audit trails, and
large incremental result sets.

I would not make streaming the default live-resource model. Add a distinct
transport mode when needed:

```clojure
:transport :rf.hasura/stream
```

It should define cursor persistence, duplicate suppression, append/merge policy,
and replay behavior explicitly. None of the reviewed Day8 code requires that as
the first migration slice.

### Sub-Resources

Do not invent a separate "sub-resource" lifecycle for Hasura. A child/detail
resource is still a resource with params, scope, owners, status, data, tags,
GC, and invalidation.

For example:

- `:exceler8/ratesets`
- `:exceler8/ratecards/by-rateset`
- `:exceler8/ratecard/detail`

The relationship can be expressed through params, tags, and route/machine
dependencies. A future grouped-resource convenience can exist, but it should
compile to ordinary resources.

## GraphQL Partial Success Policy

GraphQL can return `data` and `errors` together. The Hasura library should not
treat that as ordinary success.

Recommended policy:

- first load with errors and no usable data -> `:error`;
- refresh with errors but prior data remains usable -> preserve `:data`, set
  `:refresh-error`;
- response with partial data may become `:loaded` only if the resource declares
  a partial-data policy and schema/decoder accepts it;
- all errors should include operation name, endpoint id, request/operation id,
  generation, redacted variable summary, and GraphQL error paths.

This keeps views simple and gives tools enough context.

## Security And AI Egress

Hasura support must be privacy-first because Day8 apps include tenant, site,
user, JWT, sudo/admin, and potentially customer media data.

Minimum rules:

- never store raw JWTs in app-db user state;
- durable runtime may hold only redacted token summaries and expiry metadata;
- host connection payloads live in side tables or machine data with egress
  redaction;
- scope includes user/site/role/sudo facts;
- `:rf.resource/clear-scope` runs on principal changes;
- Xray shows operation names, document hashes, variables schemas, redacted
  variables, statuses, and owner/cause data;
- AI tool egress defaults to metadata summaries, not raw GraphQL payloads;
- resource registrations can mark variables or data fields as `:sensitive?` or
  `:large?`;
- allow-list/persisted operation metadata is visible so drift can be detected
  without exposing query bodies if an app chooses not to expose them.

## SSR And Routes

Hasura query resources should support SSR the same way HTTP resources do:

1. resolve route;
2. compute route resources;
3. issue GraphQL query resources server-side;
4. wait for blocking resources;
5. project/redact hydrated resource state into the page;
6. hydrate client resources by endpoint, scope, resource id, and params.

Hasura live subscriptions should not run as SSR WebSocket subscriptions by
default. Server render should preload the equivalent query resource where
needed, then the client can attach the live owner after hydration.

This implies a useful registration option:

```clojure
{:transport :rf.hasura/subscription
 :ssr       {:transport :rf.hasura/query
             :document  ratesets-query}}
```

Without that, SSR either skips the live resource or needs a one-shot query
fallback.

## Implementation Slices

### Slice 1: GraphQL Query Resource Transport

Implement `:rf.graphql/query` and/or `:rf.hasura/query` over HTTP POST.

Must include:

- endpoint registration;
- operation name/document/variables;
- request id/generation;
- resource success/failure events;
- GraphQL error envelope handling;
- redacted trace rows;
- tests for stale reply suppression and partial success.

### Slice 2: Hasura Connection Machine

Lift rf8 `re_graph2` ideas into a reusable library.

Must include:

- socket actor outside frame-state;
- connection machine;
- legacy Hasura WebSocket protocol support;
- optional newer protocol support or an explicit follow-up;
- `connection_init`, ack handling, keepalive handling;
- reconnect/backoff;
- stale socket suppression;
- Xray-visible connection state;
- teardown on frame destroy.

### Slice 3: Live Resource Subscription Transport

Add `:rf.hasura/subscription`.

Must include:

- owner attach -> register WebSocket operation;
- last-owner release -> stop operation;
- reconnect -> resubscribe active operations;
- incoming data -> resource state update with generation checks;
- incoming GraphQL errors -> resource error/refresh-error policy;
- no component/subscription-triggered fetching.

### Slice 4: Mutation Transport

Add `:rf.hasura/mutation` when `reg-mutation` lands.

Must include:

- variables and operation documents;
- mutation instance ids;
- error/result state;
- invalidation tags;
- patch/populate foundation;
- optimistic patch/rollback as a later sub-slice if needed.

### Slice 5: Migration Examples

Port one real app slice as proof:

- Exceler8 `ratesets` + `ratecards/by-rateset` is the best test because it has
  base live data, dynamic editor live data, mutations, dirty flags, and
  optimistic compensation.
- rf8 `launcher-user` is the smallest proof of connection-machine reuse.
- Maxim8 `campaign-headers` is a good filter-param/live-resource example.

### Slice 6: Xray And Privacy

Add Xray panels:

- endpoints and connection state;
- active operations;
- resource entries by endpoint/scope;
- route/resource ownership graph;
- mutation/invalidation graph;
- redaction diagnostics.

Add AI egress tests for JWT/header/variable redaction.

## Design Decisions To Make

1. Should `:rf.hasura/query` be a separate transport from `:rf.graphql/query`?

   Recommendation: yes for the library API, but implement it on top of the
   generic GraphQL transport. Hasura needs endpoint/session/allow-list/Xray
   conventions, but the resource runtime should not care that the server is
   Hasura.

2. Should one-shot queries/mutations go over HTTP or WebSocket?

   Recommendation: HTTP by default. Use WebSocket for live operations. Keep
   query/mutation-over-WebSocket as an internal/advanced option because rf8's
   scaffold already supports it, but do not make it the default.

3. Should live query resources be considered always fresh?

   Recommendation: fresh while connected and receiving frames; stale/warned
   while disconnected past policy. Keep prior data visible unless the app marks
   the resource unusable on disconnect.

4. Should Hasura Event Triggers appear in the client library?

   Recommendation: not directly. They are backend infrastructure. The client
   should model the user-visible workflow as a machine, execute a mutation that
   creates durable backend intent, and observe job/effects state through
   resources.

5. Should the library wrap `re-graph`?

   Recommendation: no for the final design. Existing apps can have migration
   adapters, but the re-frame2-native library should own the socket actor and
   connection machine so frame-state, replay, stale detection, teardown, Xray,
   and privacy are correct.

## Why This Fits re-frame2's Ethos

This design keeps the core re-frame2 mental model intact:

- views are declarative materialized views over state;
- events are causal;
- route entry declares remote data needs;
- finite state machines model workflows and long-lived lifecycles;
- runtime-managed server-state is not user app-db;
- tooling explains why work happened;
- AI assistance gets structured metadata and redacted summaries.

It also improves programmer productivity:

- less copied JWT/WebSocket/reconnect code;
- no hand-rolled `:dirty?` state machines in app-db;
- no hidden fetches from subscriptions;
- fewer string interpolation bugs;
- route data dependencies become visible and testable;
- mutation invalidation is explicit;
- Xray can debug stale data and connection issues directly.

## Open Risks

- The resource and mutation artifacts must exist first, or the Hasura library
  will recreate their semantics badly.
- Hasura protocol compatibility needs a real test matrix against the Day8
  deployed versions. Current apps rely on legacy behavior.
- Live-query snapshot replacement can be expensive for large result sets; the
  library needs structural sharing and later optional normalized/entity
  strategies.
- Allow-list/persisted operation support should not block migration, but the
  registration shape should reserve operation hashes from the start.
- Scopes must be correct. A missing role/site/sudo scope key is a security bug,
  not just a cache bug.

## Bottom Line

Create `day8/re-frame2-hasura` as a first-party extension library. Make it the
canonical migration path for Day8 Hasura apps, but keep all cache, ownership,
SSR, invalidation, route, frame, trace, and Xray semantics in the re-frame2
resource/mutation system.

Do not revive subscription-driven fetching. Hasura subscriptions should feed
resource entries that are explicitly owned by routes, machines, leases, or
events. That gives Day8 the realtime behavior it already relies on while making
the system more maintainable, inspectable, secure, and AI-friendly.
