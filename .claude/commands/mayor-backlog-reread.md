description: Mayor Loop — backlog reread (≈60m cadence). Read ALL open beads from the RAW list, not the ready view; re-test fences, dependencies, closures and holds.
---
MAYOR LOOP (backlog reread) — `docs/the-mayor-method/loops.md` §3 is the generic body; this file pins the concrete commands. **Dispatch reads the ready list; this loop reads everything else.** `bd ready` is a PROJECTION: it answers *what could go out right now*, and by construction omits held, blocked and in-progress beads. Those are the ones that fail quietly — a dispatchable bead that goes wrong is caught next tick because the tick is looking straight at it, while a held bead that should have been released is caught by nobody.

**Read the RAW list, every bead.** `bd list --status open,in_progress,blocked,deferred --limit 0 --flat --no-pager`. Not `bd ready`, not a saved filter, not what you remember filing — and note `--limit 0`, because the default caps at 50 and a cap silently truncates the very tail this loop exists to reach. **A homegrown filter that returns empty is not evidence the backlog is dry** — eyeball the raw list.

**On each bead, order the material by the tracker's own TIMESTAMPS — not by position, and not by dates written in the prose.** The description is USUALLY the oldest text and corrections accrete BELOW it, so a top-down read gets superseded instructions. But the bottom is not reliably the newest either, because audit notes append into the DESCRIPTION block while dated comments render after it — measured on `rf2-hic-047`, newest note at rendered line 79, older comment at line 111. **`bd show <id> | tail` is not a read-the-newest method.**

**Grepping the text for dates is not one either**, and that was this rule's own first repair. A date inside a bead is CONTENT, not a mutation time: an undated scope correction is invisible to it, an old description can cite a later release date, a fresh note can quote older evidence, and `bd update --description` can make the supposedly-oldest field the most recently edited one. Use `bd history <id>` — it lists real mutation times newest-first — and `bd comments <id> --json` for comment `created_at`. **That listing tells you a newer mutation EXISTS, not what it says**: it prints commit, time, author and the bead's title and status, and names no changed field. For the change itself use `bd history <id> --json`, which carries a full issue snapshot per commit. **Walk adjacent pairs newest-first until the first change to a TEXT-BEARING field** — description, notes, acceptance, design. The history holds duplicate checkpoint snapshots and status-only mutations, so the newest pair alone can truthfully report nothing changed while a still-current instruction change sits a few pairs back. Measured on `rf2-nj5bg`: the newest 2 pairs were byte-identical, the third changed `status` only, and the governing `notes` delta was the fourth.

**And re-enumerate a bead's CHILDREN before concluding a decision is absent** — a ruling is sometimes recorded as a NEW CHILD rather than a note. The `rf2-0yp7w` landing-order ruling arrived as `.11` and `.12`; the parent and its five known children were searched twice and showed nothing, while a live worker spent 20 minutes on the instruction that ruling had just superseded.

Four things surface here and nowhere else.

**A FENCE THAT HAS CLEARED.** The dispatch tick records a fence on the bead (`FENCED … CLEARS WHEN #NNNN MERGES`) and moves on; nothing removes it when the condition is met. A bead sequenced behind another's merge becomes dispatchable the instant that PR lands, and `bd` does not notice — the short tick keeps skipping it because it is still not *ready*, and the note is the only record that anything is being waited on at all. Re-testing those conditions is this loop's most productive minute: grep the notes for `CLEARS WHEN`, check each named PR with `gh pr view <n> --json state`, and dispatch the ones whose condition is met. **Recording a fence is worth nothing without the loop that reads it back.**

**A DEPENDENCY THAT HAS OUTLIVED WHAT IT WAS ENFORCING.** A bead blocked "until X lands" stays blocked when X is later reopened by a merged-PR audit for an unrelated residual — even though the thing it was waiting for shipped. Force the close and **write the reasoning on the bead**: what the dependency was enforcing, that it was satisfied, and why the reopen does not re-block work that already merged.

**A CLOSURE THAT REVERTED.** Verifying at the moment you close is not enough — a `bd close` evaporates when a `git checkout HEAD -- .beads` reverts the export and the next checkpoint re-imports it (CLAUDE.md, *Beads durability*). Re-check what this session closed with `bd show <id>` and re-close what genuinely reverted. **But read the bead's notes before re-closing anything.** This project audits every merged PR, so most reappearances are the audit working rather than a lost write, and re-closing one destroys a real finding while looking like tidiness. Grep the notes for `AUDIT-REOPEN`, unmet obligations and outstanding acceptance criteria first.

**A HOLD THAT IS COSTING MORE THAN IT IS HOLDING.** Separate *needs a decision from Mike* from *needs work under a decision already made* — the second is dispatchable NOW and it tends to sit in the first pile. For the ones that genuinely need the operator, record what the hold is costing: which beads are behind it and what stops if it stays. A hold with no cost written on it reads as free, and the cheapest-looking item in a list is the one that stays there longest. Surface those in chat and on the beads themselves — `ai/decisions.md` is retired.

In-progress beads are read here too, but their liveness question belongs to the STRANDED SWEEP in `mayor-posture.md`, not here. Read them for scope and for fences; leave *is this worker still alive?* to the loop that owns it. **Do not amend a bead that is in_progress** — a worker holds it and is reading it; file a follow-up instead.

**Most passes find nothing, and a pass that finds nothing is complete.** What is NOT complete is a pass that reports nothing without having read the raw list — inferring the backlog from the ready view is the exact failure this loop exists to go behind. Report the raw count, what you re-tested, and what you released or dispatched.
