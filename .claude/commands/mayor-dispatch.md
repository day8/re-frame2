MAYOR LOOP (bead dispatch pass).

**GOAL: drive the open backlog as close to 0 as possible**, up to **6 concurrent background workers**, refilling the instant a slot frees. Dispatch ALL clear-and-unblocked beads regardless of priority (P3/P4 included).

**SOLO vs CLUSTER — by PRIORITY first, then size:**
- **P1 → ALWAYS SOLO.** A dedicated worker, its own PR. A P1 gets focused attention and merges on its own green — never bundled where a cluster-sibling could block it.
- **P2 → SOLO by default.** Lean solo; only cluster several P2s when they are genuinely small, same-surface, and low-risk.
- **P3 / P4 that are small + same-surface → CLUSTER.** This is the primary clustering target: bundle the many small low-priority same-surface beads into **ONE cluster agent** (Shape 2) that works them in priority order → one PR, so you don't handle dozens of trivia serially.
- **Any LARGE bead → SOLO**, whatever its priority (a feature, a deep / multi-file fix — anything a worker spends its whole context on). Never pad a meaty bead into a cluster; never bundle two large beads (the agent times out).
- **A measurement / benchmark window → SOLO, Shape 6** — picked by KIND, not size, and never folded into a cluster. It is the one shape where the worker must NOT iterate until green: the controls arbitrate, a refusal is a correct deliverable, the rig does not change mid-window, and the runs go strictly one at a time.

Different surfaces run as **parallel** agents; same-surface work never runs as two concurrent workers (they merge-conflict). The serial exceptions: an EPIC deliberately structured serially, and a single tightly-coupled module whose core files (e.g. one big handler file) are touched by many beads — that surface is ITS OWN serial lane (sequence its workers as successive PRs, later ones rebasing on the earlier merges — never blind `--theirs`/`--ours`). Note the interaction: solo P1/P2 on a *coupled* surface still cannot run in parallel — sequence them one at a time on that surface (or, for a tight coupled set, one cluster-lane is the pragmatic call). Keep a cluster to ~3-6 small beads; if a surface has more, run successive cluster-PRs (each opens with what it finished + lists remaining). Genuinely-separable surfaces (`tools/xray`, `docs/*`, a distinct artefact dir, `examples/`) parallelize cleanly.

**Count current load first.** In-flight workers = active worker worktrees under the `re-frame2-worktrees` sibling (`git worktree list`) + running background tasks. Dispatch until 6 are busy OR the dispatchable queue is exhausted.

**Find + group.** Run `bd ready`. Filter OUT (NOT dispatchable): operator-decision beads, EPICs, release-coupled / v1.x, hot-zone-conflicting beads (spec/* + deps.edn + shadow-cljs.edn + .github/workflows/* — the fixed list; one toucher at a time, never parallel), and anything gated/blocked. Honor any active operator pause. Bucket the survivors by file-surface; within each bucket apply the SOLO-vs-CLUSTER rule above — solo every P1 (and any large bead / by-default P2), cluster the small P3/P4 remainder — respecting that a coupled surface serializes its workers. BEFORE dispatching, grep for the alleged broken symbol / missing file — if already landed, close as verified-duplicate; spot exact-title duplicates and consolidate. **A COUNT IS A CLAIM TOO, AND THE GREP THAT CHECKS IT IS A DIFFERENT ONE.** A census bead ("54 chains", "15 hits", "eleven sites") asserts a number, not a symbol, so a symbol-shaped grep passes while the number is stale — the symbol still resolves, and the count is zero. Re-run the bead's own census at origin/main HEAD, not at the bead's text and not at your branch point. On 2026-08-12 two beads went out in one wave against work already merged: rf2-sx7g and rf2-5zt9 were both discharged by rf2-e8kc / PR #7974 roughly fifteen hours before dispatch, and rf2-e8kc had PREDICTED the overlap in its own text ("the same rows counted twice, not 17 + 17. Repairing them once closes both censuses"). Both workers did the verification properly and returned a correct "already fixed" — the waste was two full dispatches, not a wrong result. **The sibling that discharges a bead is usually the one whose fence sent the work elsewhere**: a tree fenced off from bead A is exactly the tree bead B is free to take, so read ACROSS a split's siblings before dispatching any one child, and treat a parent's remainder table as stale until re-derived.

**Dispatch** each cluster per dispatch-prompt-template.md (Shape 2): a dedicated worktree under the worktree-root (`re-frame2-worktrees` sibling — derive via `git worktree list`, NEVER hardcode), branch `worker/<surface>-cluster`; paste the WORKTREE BOUNDARY block VERBATIM; paste the PROJECT STANCE block from mayor-posture.md VERBATIM — that file is its single source, and a paraphrase is not a lighter version of it but the defect itself, because it keeps the five lenses and drops the clauses that say when to STOP; give the ordered bead list (smallest-cleanup → biggest-correctness) with `bd show <id>` as authoritative; an explicit file-ownership fence + enumerate other in-flight clusters' surfaces; mandatory surface-gate menu + a `## Quality gates` PR section; "never edit the mayor checkout", "do not merge PRs"; the no-`git stash` guard; claim-each-then-commit-per-bead; partial-PR-on-timeout (open with DONE beads + list remaining, never a half-bead uncommitted); worker may close its own beads after opening the PR.

**A finding that lands on a live worker's file gets an EXACT BEAD OWNER FIRST and is then ROUTED rather than dispatched — and the routing is only HALF the move.** With six workers out, audits and worker reports keep turning up findings on files somebody already holds. START BY RESOLVING AN EXACT OWNER — update or reopen the bead that already owns the finding, or FILE one when none does. FILING IS NOT DISPATCHING; audit #7849 caught this rule's own first wording conflating them, and it is a second dispatch, not a second bead, that puts two workers on one file. Then route that owned item rather than waiting for the holder to finish and losing the context it was found in: message the holding worker and let the fix land inside the PR that is already open — but ALSO put ONE NOTE ON THE OWNING BEAD (the one just resolved, NEVER whatever unrelated bead the holder happens to be working, which is that same wrong object one step removed) saying WHAT was routed, TO WHOM, and WHAT HAPPENS IF IT DOES NOT LAND, because a message lives only in that agent's transcript and an agent that dies, times out, or reasonably declines the extra item (declining is often correct) takes the finding with it. AUDIT #7825 on rf2-hic-021 caught exactly this: the mayor had "identified this exact stale deferral but ROUTED IT ONLY TO A TRANSIENT WORKER, LEAVING NO DURABLE BEAD OWNER", the only record being a close reason on a DIFFERENT bead — a record on the wrong object, since nobody reads a closed bead looking for open work. When the holder's PR merges, VERIFY the routed item actually landed rather than assuming it did (audit #7827 verified it against landed main, which is how rf2-hic-021 legitimately closed), and only THEN close the owner; do NOT file a duplicate, because the note is already the record. AND SOMETIMES ROUTING IS THE WRONG MOVE: when the holder was dispatched under a deliberately BOUNDED fence, handing it a second finding widens that fence mid-flight, which is how a bounded repair becomes an unbounded one. Then leave that owner QUEUED OR SEQUENCED instead of routing it, and note the overlap on the in-flight bead, saying explicitly that the item is owned elsewhere and is NOT part of the in-flight repair, so a worker reading that bead bottom-up does not adopt it — rf2-kqls was fenced out of rf2-hic-076's bounded proof-paragraph repair that way, and rf2-jkdy's panel-retirement recommendation was noted onto rf2-hic-062, which owns donor-surface disposition. Route-and-note or queue-and-note: an exact owner in the tracker plus one note is common to both and is the entire safeguard. Keep it to one message and one note — no routing registry, no tracking field, no script.

Dispatch immediately on clear; don't queue for a later tick. When the dispatchable queue is exhausted below 6, say so in one line and stop.
