MAYOR LOOP (bead dispatch pass).

**GOAL: drive the open backlog as close to 0 as possible**, up to **6 concurrent background workers**, refilling the instant a slot frees. Dispatch ALL clear-and-unblocked beads regardless of priority (P3/P4 included).

**SOLO vs CLUSTER — by PRIORITY first, then size:**
- **P1 → ALWAYS SOLO.** A dedicated worker, its own PR. A P1 gets focused attention and merges on its own green — never bundled where a cluster-sibling could block it.
- **P2 → SOLO by default.** Lean solo; only cluster several P2s when they are genuinely small, same-surface, and low-risk.
- **P3 / P4 that are small + same-surface → CLUSTER.** This is the primary clustering target: bundle the many small low-priority same-surface beads into **ONE cluster agent** (Shape 2) that works them in priority order → one PR, so you don't handle dozens of trivia serially.
- **Any LARGE bead → SOLO**, whatever its priority (a feature, a deep / multi-file fix — anything a worker spends its whole context on). Never pad a meaty bead into a cluster; never bundle two large beads (the agent times out).
- **A measurement / benchmark window → SOLO, Shape 6** — picked by KIND, not size, and never folded into a cluster. It is the one shape where the worker must NOT iterate until green: the controls arbitrate, a refusal is a correct deliverable, the rig does not change mid-window, and the runs go strictly one at a time.

Different surfaces run as **parallel** agents; same-surface work never runs as two concurrent workers (they merge-conflict). The serial exceptions: an EPIC deliberately structured serially, and a single tightly-coupled module whose core files (e.g. one big handler file) are touched by many beads — that surface is ITS OWN serial lane (sequence its workers as successive PRs, later ones rebasing on the earlier merges — never blind `--theirs`/`--ours`). Note the interaction: solo P1/P2 on a *coupled* surface still cannot run in parallel — sequence them one at a time on that surface (or, for a tight coupled set, one cluster-lane is the pragmatic call). Keep a cluster to ~3-6 small beads; if a surface has more, run successive cluster-PRs (each opens with what it finished + lists remaining). Genuinely-separable surfaces (`tools/xray`, `docs/*`, a distinct artefact dir, `examples/`) parallelize cleanly.

**Count current load first.** In-flight workers = active worker worktrees under the `re-frame2-worktrees` sibling (`git worktree list`) + running background tasks. Dispatch until 6 are busy OR the dispatchable queue is exhausted.

**Find + group.** Run `bd ready`. Filter OUT (NOT dispatchable): operator-decision beads, EPICs, release-coupled / v1.x, hot-zone-conflicting beads (spec/* + deps.edn + shadow-cljs.edn + .github/workflows/* — the fixed list; one toucher at a time, never parallel), and anything gated/blocked. Honor any active operator pause. Bucket the survivors by file-surface; within each bucket apply the SOLO-vs-CLUSTER rule above — solo every P1 (and any large bead / by-default P2), cluster the small P3/P4 remainder — respecting that a coupled surface serializes its workers. BEFORE dispatching, grep for the alleged broken symbol / missing file — if already landed, close as verified-duplicate; spot exact-title duplicates and consolidate. **A COUNT IS A CLAIM TOO, AND THE GREP THAT CHECKS IT IS A DIFFERENT ONE.** A census bead ("54 chains", "15 hits", "eleven sites") asserts a number, not a symbol, so a symbol-shaped grep passes while the number is stale — the symbol still resolves, and the count is zero. Re-run the bead's own census at origin/main HEAD, not at the bead's text and not at your branch point. On 2026-08-12 two beads went out in one wave against work already merged: rf2-sx7g and rf2-5zt9 were both discharged by rf2-e8kc / PR #7974 roughly fifteen hours before dispatch, and rf2-e8kc had PREDICTED the overlap in its own text ("the same rows counted twice, not 17 + 17. Repairing them once closes both censuses"). Both workers did the verification properly and returned a correct "already fixed" — the waste was two full dispatches, not a wrong result. **The sibling that discharges a bead is usually the one whose fence sent the work elsewhere**: a tree fenced off from bead A is exactly the tree bead B is free to take, so read ACROSS a split's siblings before dispatching any one child, and treat a parent's remainder table as stale until re-derived. **A BEAD'S DESCRIPTION IS A HISTORICAL DOCUMENT AND ITS COMMENTS ARE THE CURRENT STATE, so ESTABLISH WHICH TEXT IS NEWEST BY TRACKER TIMESTAMP BEFORE YOU BRIEF FROM IT — never by position.** `bd comments <id> --json` by `created_at` descending, and `bd history <id> --json` walked newest-first to the first change in a text-bearing field; the mechanics belong to `docs/the-mayor-method/loops.md` under *Dispatch* and are not restated here. Every brief this file sends already tells the WORKER to do this, and mayor-backlog-reread.md tells the mayor to do it while rereading the backlog — the gap was HERE, at the one moment a brief is written FROM a bead, and **the mayor's own earlier note is the most dangerous stale source**, because it reads as authoritative and you recognise your own words. **Ordering the bead is only half of it: the brief's CONTENT is claims too, and they are verified at origin/main HEAD.** The count clause above is this same rule on one kind of claim; a route, a constant, a file path, a threshold, a prohibition and a table are each another, and a bead saying "the two routes left" was written when two routes were left. Four instances in one night, all the mayor's own: rf2-lo7uy was dispatched on an 03:02Z triage comment that a 04:55Z comment had already superseded, where proceeding would have DISCARDED a merged layout rather than merely wasting a dispatch; rf2-2rtt6.140 was ordered correctly for SCHEDULING — every dependency re-read newest-first — and then briefed off a nine-day-old description whose "two routes left" had both shipped in PR #7702, so the decision was right and only its content was stale. All four failed safe, two of them because a worker walked the history itself and refused — that is "where the bead and this brief disagree, the BEAD governs" doing work it should not have had to do.

**Dispatch** each cluster per dispatch-prompt-template.md (Shape 2): a dedicated worktree under the worktree-root (`re-frame2-worktrees` sibling — derive via `git worktree list`, NEVER hardcode), branch `worker/<surface>-cluster`; paste the WORKTREE BOUNDARY block VERBATIM; paste the PROJECT STANCE block from mayor-posture.md VERBATIM — that file is its single source, and a paraphrase is not a lighter version of it but the defect itself, because it keeps the five lenses and drops the clauses that say when to STOP; give the ordered bead list (smallest-cleanup → biggest-correctness) with `bd show <id>` as authoritative; an explicit file-ownership fence + enumerate other in-flight clusters' surfaces — **DERIVE that enumeration at dispatch time from `gh pr list --state open --json number,headRefName,files` plus `git worktree list`, never from your own memory of who you dispatched** — but note that `files` is PAGINATED AT 100 AND TRUNCATES SILENTLY, so for any PR above that it under-reports, in the stale-NARROW direction this rule names below as the expensive one; a round 100 is the tell, and the fix is `git diff --name-only origin/main...worker/<branch>` in the three-dot form, which reports all of them (measured 2026-08-16 on PR #8322: `files` returned exactly 100 with zero `spec/` paths, while the three-dot diff returned 722 including the compiled-grammar spec under `spec/`, the exact file a pending fence turned on — that spec has since been deleted by rf2-0yp7w.11, so the path is named here only as history), and **write each fence entry from the FILE LISTS, never from the branch names** — `files` is one more field on the one call, and it is the field a fence is actually about: a branch name cannot distinguish a PR holding four named files from one holding a whole tree, so a fence derived from names is still a guess about files, which is precisely the guess this derivation exists to eliminate. **Both directions of a file-level error were measured within an hour of this rule landing**, by three workers who each checked the changed files instead of the names: an OVER-BROAD entry costs COVERAGE where the worker obeys it — one found `implementation/hicasso/**` fenced as a whole tree when the open PR held four named files, neither of them the ones it needed, so obeying would have cost it the witness it was free to take — while an UNDER-BROAD one costs a CONFLICT, two workers on one file. **`git worktree list` answers WHO, not WHAT** — paths and branch names, no file information at all — so the worktree half of that derivation cannot be read off its output the way `files` answers the PR half; resolve a worktree with no open PR by diffing its branch against the trunk for the paths in question, `git diff --name-only origin/main...worker/<branch> -- <paths>`, **in the three-dot form**, because two-dot reports what MAIN changed since that branch forked and so names every branch that has not rebased since — run minutes after a change to this very file landed, two-dot named about seventy branches where three-dot named eight. **Then read each survivor's PR state**, because the diff alone cannot separate a live unpushed worker from a merged leftover whose fork point predates its own merge: on that same derivation all eight had MERGED PRs and the true fence was empty. **And an empty three-dot diff is not an empty worktree** — three-dot compares COMMIT TREES, so a worker that has edited but not yet committed reports no files at all and its branch ref still equals the trunk, which is the state every worker is in for its whole first stretch; `git status --porcelain` inside that worktree is the THIRD source, and its paths join the diff's. Measured in one derivation on this fleet: of five live workers whose committed diff read `<none yet>`, `worker/mount-7mtcf` held eighteen modified files (`implementation/hicasso/src/re_frame/hicasso.cljc`, `docs/design/hicasso/product/dispositions.md`, …) and `worker/docsguide-hic068` held ` M docs/core/hicasso/19-performance.md` plus two untracked pages. Omitting those is the stale-NARROW direction this rule already names as the expensive one. A worktree clean on BOTH sources has not started yet rather than owning nothing — its paths are in the bead it was dispatched under, not in Git. **The one carve-out to “never from your own memory” is a peer dispatched in the SAME MESSAGE or the same tick.** Such a peer has no open PR, no branch, no commits, no working tree and no worktree — all four sources blind at once — so there is nothing to derive from, and dispatch knowledge is not a stale substitute for derivation here but the only evidence that exists. The same `worker/mount-7mtcf` reported it from the other side: of the peers its own fence named, two “had no worktree at all — neither had started, so the check-its-file-list instruction had nothing to check”, and all three had gone out in one message. So NAME such a peer from what you just dispatched, and flag it as *dispatched alongside you, may not exist yet; re-derive at start-up and again before your first edit* — the worker's own re-derivation still governs everything else. Omitting it is the stale-NARROW direction once more, two workers on one file, where naming it costs one re-derivation. The carve-out is scoped to that single window, between dispatching a worker and that worker creating its worktree: a worker ALREADY RUNNING is read from the three sources and never from memory. And make the brief TELL THE WORKER to re-run those same two commands at start-up and treat what it finds as authoritative over the list the brief carries. A remembered list goes stale inside the dispatch's own lifetime: on a six-worker fleet with an 11-minute merge cadence it can be wrong by the time the brief is finished, and one worker reported that only one of the four holders its fence named still had an open PR while all three items in the bead's own fence had merged. **The worker's re-derivation is the half that matters, because the two staleness directions cost differently**: a stale-BROAD fence costs one re-derivation and some confusion — the worker is warned off a file nobody holds — while a stale-NARROW fence omits a worker dispatched after you last looked, and two workers on one file merge-conflict and can silently revert each other. An accurate list cannot fix the second, because accuracy expires between writing the brief and reading it; only the worker's own start-up check catches it. Both directions come from the same defect, and only one of them is expensive; mandatory surface-gate menu + a `## Quality gates` PR section; **name `scripts/check_fast_pr_gap.py` as the ONE path the brief cites for the FAST-SPINE-VERSUS-REQUIRED-CI gap** — its `--list` mode derives, at step granularity and with the local command for each, which required checks `scripts/test-fast-pr.sh` does not run (TESTING.md:121), so the worker cites that path rather than enumerating checks by hand or reading `.github/workflows/*` itself; **that is a fact about the SPINE, not a census of what THIS worker ran**, so the brief must ALSO require the PR body to state whether the spine ran at all plus any targeted gates run directly — those two facts alongside the derived gap are what let a reader compute real coverage, and citing the gap alone misreports in both directions: a worker that skipped the spine has the spine's own checks missing from its coverage yet absent from the report, and a check the worker ran directly is still listed there as unrun; paste the GATE MECHANICS block — dispatch-prompt-template.md, section "Quality gates — how a gate is run" — VERBATIM, on the same footing as the boundary and stance blocks, because the menu settles WHICH gate runs and only that section settles HOW it is run; "never edit the mayor checkout", "do not merge PRs"; the no-`git stash` guard; claim-each-then-commit-per-bead; partial-PR-on-timeout (open with DONE beads + list remaining, never a half-bead uncommitted); worker may close its own beads after opening the PR.

**Of everything enumerated above, the gate-mechanics block is the one a mayor is most tempted to PARAPHRASE — and a paraphrase of it is not a shorter version but an inverted one.** The block leads with the arithmetic and derives the permission from it: `scripts/test-fast-pr.sh` needs roughly twenty-five minutes against a harness ceiling of ten, so "foreground, to completion" is not on offer for the spine however a brief words it — which is why the block names detaching a long gate CORRECT and locates the defect in what comes after, ending the turn instead of polling the log and the `.exit` file in a bounded loop. **That ordering is the load-bearing part, and it is exactly what a summary destroys.** Reworded, the permission arrives as a grudging concession rather than a derived fact, and the grudge is what does the damage: on 2026-08-13 three workers stranded inside one hour — `shadow-kyum`, `ssrwitness-hic046`, `gatehyg-qzm8` — each having detached a gate and then ended its turn to wait for a completion event that nothing sends. All three had pushed first, so the cost was latency rather than data, and all three resumed correctly on a single message. **Two of the three APOLOGISED for detaching, which is precisely why the polling instruction had not landed**: a worker that believes it has already broken the rule reads whatever follows as a reprimand rather than as its next step, and reads straight past the sentence that would have saved it. The block was rewritten to stop grudging it; a paraphrase that puts the grudge back reinstates the failure, whatever it does to the word count — and a trim that keeps the arithmetic while dropping the sanction does the same thing by the shorter road. Paste it whole, and do not restate it here: the template owns this text, and a second copy in this file is the same drift one level down.

**A finding that lands on a live worker's file gets an EXACT BEAD OWNER FIRST and is then ROUTED rather than dispatched — and the routing is only HALF the move.** With six workers out, audits and worker reports keep turning up findings on files somebody already holds. START BY RESOLVING AN EXACT OWNER — update or reopen the bead that already owns the finding, or FILE one when none does. FILING IS NOT DISPATCHING; audit #7849 caught this rule's own first wording conflating them, and it is a second dispatch, not a second bead, that puts two workers on one file. Then route that owned item rather than waiting for the holder to finish and losing the context it was found in: message the holding worker and let the fix land inside the PR that is already open — but ALSO put ONE NOTE ON THE OWNING BEAD (the one just resolved, NEVER whatever unrelated bead the holder happens to be working, which is that same wrong object one step removed) saying WHAT was routed, TO WHOM, and WHAT HAPPENS IF IT DOES NOT LAND, because a message lives only in that agent's transcript and an agent that dies, times out, or reasonably declines the extra item (declining is often correct) takes the finding with it. AUDIT #7825 on rf2-hic-021 caught exactly this: the mayor had "identified this exact stale deferral but ROUTED IT ONLY TO A TRANSIENT WORKER, LEAVING NO DURABLE BEAD OWNER", the only record being a close reason on a DIFFERENT bead — a record on the wrong object, since nobody reads a closed bead looking for open work. When the holder's PR merges, VERIFY the routed item actually landed rather than assuming it did (audit #7827 verified it against landed main, which is how rf2-hic-021 legitimately closed), and only THEN close the owner; do NOT file a duplicate, because the note is already the record. AND SOMETIMES ROUTING IS THE WRONG MOVE: when the holder was dispatched under a deliberately BOUNDED fence, handing it a second finding widens that fence mid-flight, which is how a bounded repair becomes an unbounded one. Then leave that owner QUEUED OR SEQUENCED instead of routing it, and note the overlap on the in-flight bead, saying explicitly that the item is owned elsewhere and is NOT part of the in-flight repair, so a worker reading that bead's newest notes does not adopt it — rf2-kqls was fenced out of rf2-hic-076's bounded proof-paragraph repair that way, and rf2-jkdy's panel-retirement recommendation was noted onto rf2-hic-062, which owns donor-surface disposition. Route-and-note or queue-and-note: an exact owner in the tracker plus one note is common to both and is the entire safeguard. Keep it to one message and one note — no routing registry, no tracking field, no script.

Dispatch immediately on clear; don't queue for a later tick. When the dispatchable queue is exhausted below 6, say so in one line and stop.
