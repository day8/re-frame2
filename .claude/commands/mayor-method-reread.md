MAYOR LOOP (method reread) — `docs/the-mayor-method/loops.md` §6 is the generic body; this file pins the concrete commands. **This loop earns its place, but NOT by re-reading.** Re-reading unchanged files spends context for nothing and produces a confident "no drift" that was never a measurement. Do two things instead.

**1. CHECK WHAT CHANGED since the last pass** — in the method docs AND in the command files that execute them. `git log --oneline --since='60 minutes ago' -- docs/the-mayor-method .claude/commands` and read the diffs, not the subjects. **When a method rule changes, re-read the matching command file**, because the two layers drift apart silently: `docs/the-mayor-method/**` DESCRIBES the method and `.claude/commands/mayor-*.md` is what actually EXECUTES, and a link checker catches renamed files, not semantic drift. `scripts/check_readme_links.py` resolves every `.md` path a command file names, so a MOVED document is caught for you; a rule that changed meaning under an unchanged filename is not, and that is this step's whole job.

**2. CHECK THE RULES YOU HAVE BEEN ENFORCING against what the tree actually does.** That is where the drift lives, and it is the half that finds real defects. Twice this found a rule the documents asserted universally that the tree did not support — and one of those had been introduced by a merge the mayor itself approved. **Grade your own recent briefs**: pull what you dispatched this session and check whether the rules you pasted were satisfiable on the surface you sent them to.

Watch specifically for:

* **A MEASURED CONSTANT THAT HAS GONE STALE.** The check-count band in `mayor-merge.md` is the standing example — it is written down, it moves as the workflow matrix grows, and it goes stale exactly where it has to be right. Re-measure it on PRs merged AFTER the last `.github/workflows/*` change, because a PR branched before a new job landed is computed against the superseded matrix and legitimately reads band-minus-one.
* **UNSATISFIABLE QUANTIFIERS.** *"Every gate prints a root banner"* when a third of them do not; *"put all three sentences in every editing brief"* when the third names a control a prose-only brief does not have. Workers facing an unsatisfiable rule do not stop — they IMPROVISE, and the improvisation varies. **When a rule says *every*, check the quantifier.** Both examples above were found by this loop, and in both the improvisation showed up on the ENFORCING side first: briefs that quietly dropped the clause nobody could satisfy.
* **BLOCKS THAT HAVE DIVERGED FROM THE COMMAND FILES THAT PASTE THEM.** Two copies of one rule disagree within days. The worktree-boundary block and the gate-mechanics block are the two that matter, and `docs/the-mayor-method/dispatch-prompt-template.md` OWNS both — a second copy in a command file is the same drift one level down. Diff them rather than trusting that they match. **But on this checkout the search that LOOKS for the second copy fails OPEN, and this bullet is where it first bit.** `core.autocrlf` is true here, so every file `.gitattributes` does not pin carries a CR before each line ending, and a `git grep` pattern ending in a `$` straight after literal text therefore matches nothing — `git grep -l "^WORKTREE BOUNDARY — MANDATORY$" -- ':!.beads'` returns EMPTY while that heading sits at line 478 of `docs/the-mayor-method/dispatch-prompt-template.md`. **The repair is an EXACT pattern on a CR-free tree, not a looser one, and the two routes rank.** This loop reads `origin/main`, so name that tree object and the original pattern works unchanged, because committed blobs are LF: `git grep -l "^WORKTREE BOUNDARY — MANDATORY$" origin/main -- ':!.beads'` returns the one owning file. That is not an extra step but the one already prescribed, and it leaves nothing to remember. Where a WORKING-TREE search is genuinely needed, spend the CR explicitly with an optional-CR anchor, which needs `-P`: `git grep -lP "^WORKTREE BOUNDARY — MANDATORY\r?$"`. **Do NOT drop the `$` and do NOT append `.*$`.** Both turn an exact line into a PREFIX, and a duplicate-block census is an exact-line question, so that trades this false ZERO for a false HIGH — one failure mode for its mirror. On this heading the broadened form happens to return the right answer today, because nothing in the tree extends that prefix; that is a property of the CORPUS, not of the query, and one file whose line began `WORKTREE BOUNDARY — MANDATORY (v2)` would silently make it two. Where the prefix IS extensible the loss is already measurable: the same broadening on `mayor-dispatch.md`'s namespace census returns seventeen files where one is correct. What makes it dangerous rather than merely wrong is that ONE copy is the correct answer and NO copies reads identically: nothing on screen separates *I looked and there is no second copy* from *my pattern could not have matched one*. The EXTRACTION is unaffected and must not be "fixed" — `sed` strips the CR on read and still returns the block's 51 lines as clean LF, so only the verification was ever blind. **So control BOTH directions before believing this census, because a false zero and an inflated count fail differently and neither control can see the other's failure.** A positive control — the pattern once against something it MUST find — rules out a DEAD pattern, and that is ALL it rules out: every broadened form above passes it while counting the wrong population. So also read the HIT LIST rather than its length, and confirm each hit is a second COPY of the block rather than a file that merely NAMES it — these command files cite both headings in prose, this one included. That PAIR, not the `$` rule, is the load-bearing half, because the `$` is not the only way a `git grep` goes quietly empty on this checkout — Git Bash rewrites a pattern that looks like an absolute POSIX path before Git ever sees it, so the pattern `^#!/usr` finds nothing in a file whose first line is exactly that, and only `MSYS_NO_PATHCONV=1` restores it.
* **A CONCLUSION THAT DOES NOT FOLLOW FROM ITS OWN PREMISE.** Rules written in a hurry can establish exactly the right thing and then draw the wrong inference from it. Read the reasoning, not just the instruction.

**Fix what you find; do not merely note it.** A finding recorded and not actioned is re-found next pass at full cost. Small corrections to the method docs or the command files go out as a worker dispatch under the normal fence rules — `docs/the-mayor-method/**` is a shared surface and two concurrent editors on it conflict by construction, so check for an open PR against the tree before dispatching and SEQUENCE if there is one. **Keep the two layers apart**: the generic method tree carries no repository names, bead ids, PR numbers, paths, tool names or OS mechanics, while these command files may name all of them freely.

Report one or two lines unless you find real drift. If you find drift, say what it was, what you changed or filed, and which of the two steps found it.
