MAYOR LOOP (merge PRs).

**Run this on MOST signals — not just the cadence.** Any time you're re-invoked (a worker completing, an operator message, a loop tick), do a quick open-PR sweep and merge whatever is already green. Checking is cheap; it keeps the pipeline flowing.

**NEVER block the session waiting on CI.** Do NOT launch `gh pr checks <pr> --watch` (it occupies a slot and stalls you). Use the three ONE-SHOT queries spelled out in the criterion below, per open PR: merge the ones that meet ALL FIVE clauses NOW; for any PR still short of it, leave it and re-check on the NEXT signal — the steady stream of worker-completions plus the cadence will catch it without a babysitting script.

**A green rollup must be COMPLETE, not merely clean — and a clean rollup is not a quiet branch.** Zero failures and zero pending is also what an EMPTY rollup reports — exactly what a PR shows in the seconds before its workflow runs are created, and what every PR shows while Actions is down. PR #7628 merged on a rollup read as 0/0/0 eleven seconds before its runs existed, and during the same day's Actions outage six PRs at once reported MERGEABLE with zero checks; the old wording would have taken all six. Two more ways the same read goes wrong, both learned since. CANCELLED IS NOT PASSED: a cancelled check is `status == COMPLETED`, so a tally keyed on completion counts it as green — one PR was reported here as "85 of 86 concluded, one check from complete" when the truth was 79 passed, 6 cancelled and 1 pending, six re-runs across four workflows from mergeable. AND A QUEUED RUN IS INVISIBLE TO THE ROLLUP: its checks are not attached to the head commit yet, so PR #7630 reported `ok=78 canc=0 fail=0 pend=0 total=78` — settled by every field it exposes — while `gh run list --branch` showed two runs QUEUED; merging there ships the PR two workflows short.

So the criterion is FIVE clauses and no one of them suffices. Resolve the head first — `gh pr view <pr> --json headRefName,headRefOid` — because clauses 4 and 5 are both keyed to it:

1. `total` non-empty and inside this repo's band — ~91 as measured 2026-08-11, when PRs #7874 and #7875 both carried 91 checks — and verify that with `gh pr checks` on recently merged PRs rather than trusting the number written here; a partial rollup of 11 is not a green one. The band MOVES as the workflow matrix grows: this line read ~86 earlier in the same programme, which is exactly why the clause tells you to measure rather than trust the constant.
2. Every check `state` in {`SUCCESS`, `SKIPPED`}, via `gh pr checks <pr> --json name,state,bucket`. The field is `state` — there is no `conclusion` field on this command, so ask for the one that exists. CANCELLED is not passed, and neither is anything else.
3. Nothing nonterminal in the rollup.
4. AND `gh run list --branch <headRefName> --commit <headRefOid> --limit 25 --json status,headSha,name` returns runs whose `status` is all `COMPLETED`. `--commit` is what keys this to the current head; the plain table has no `headSha` column at all, so request it in `--json` and compare it rather than eyeballing a listing that cannot show it.
5. AND the check set was computed against the workflow matrix that is on `main` NOW — see below.

Do not test clauses 3 and 4 by listing the states that block. `QUEUED` and `IN_PROGRESS` are not the whole vocabulary — the CLI also returns `REQUESTED`, `WAITING` and `PENDING` — and a criterion enumerating the bad states fails open on the first one nobody wrote down, which is the very defect class this whole section exists to close. Require the terminal state instead: `COMPLETED`, and anything else blocks and is re-checked on the next signal.

Clause 4 fails in both directions and both have cost ticks here. Never substitute a global `gh run list --limit 40` grouped by branch: the window truncates, and a branch with four queued runs did not appear in it at all because other branches filled it — the check reported "no live runs" for a branch that had four. And never key on the branch alone: two PRs sat at 86/86 for three ticks on runs still queued against a sha from before a re-trigger commit, and a stale-sha run is not evidence about this head — which is exactly what `--commit <headRefOid>` filters away. A guard that blocks forever is not safe, it is differently wrong.

Clause 5 is the newest and the least visible, because every field you can read says green. Two PRs merged four minutes apart here: the first added a required browser job plus a new three-engine arm, and the second was still checked against the base from before it — so the browser check it should have run came back SKIPPED, and the newly required one never appeared in its rollup at all. "All required checks passed" was a true statement about the old matrix and said nothing about the matrix already on `main`. That tree happened to be green, but only an audit running the suites by hand afterwards established it; the guard had not known. This is the direct cost of MERGE THE WHOLE QUEUE FIRST below — a burst is precisely when the base moves under a check set. So when a merge changes the workflow matrix (a new required job, a changed classifier, a re-scoped path filter), the PRs behind it whose surface that change covers do NOT inherit its verdict: `gh pr update-branch` them and re-check, and never infer coverage from an aggregate built against the superseded matrix.

A gate that verifies the absence of bad news rather than the presence of good news is the same fail-open class we hunt everywhere else in this repo, and the merge decision is not exempt from it. A rollup that is empty, short, carrying a cancellation, shadowed by a live run on the current sha, or computed against a matrix `main` has since replaced is a re-check on the next signal — never `--admin`, and never reported as green.

Run `gh pr list --state open`. For each PR: confirm the five-clause criterion above, the diff matches its bead, scope did not sprawl, failure output stays actionable, and a `## Quality gates` section is present. Merge on green — on all five clauses, none of which has an `--admin` bypass. A pending check is a re-check on the next signal however structurally irrelevant to the diff it looks: clauses 2 and 3 reject it, and one tick is the entire cost of respecting them, which is cheaper than the judgement call — every clause above exists because someone was sure a signal could not matter and was wrong. The ONLY `--admin` this loop sanctions is `MERGEABLE=UNKNOWN`, GitHub's own merge-state recompute lag: not a check, so it bypasses no clause, and it waits for all five like everything else. A failing test on the touched surface is NEVER an --admin candidate. Merge with `gh pr merge --rebase` — this repo rebases, and `--squash` would collapse a worker's commits into one. **No `--delete-branch`, and its absence is the fix rather than an omission.** This repository sets `delete_branch_on_merge`, so GitHub deletes the head branch SERVER-SIDE the instant the merge lands, and the server does not care that a worktree still holds that branch locally. `--delete-branch` did: a branch checked out in a worktree cannot be deleted locally, and gh abandons the REMOTE deletion along with the local one, so the flag orphaned an origin branch on every merge whose worker had not yet reported — three for three in the session that measured it, against roughly twenty manual `git push origin --delete` cleanups that were skipped more often than they were run. Server-side deletion yields zero orphans by construction and asks nothing of the merge path. So `git push origin --delete <branch>` is now ONLY the post-`MERGED` fallback for the rare remote ref that survives the merge — head-ref branch protection, or a cross-repo PR whose head lives in a fork the server will not touch. Check for one and delete only that ref; **a surviving remote ref is never grounds to reap a worktree early**, because the worktree and the local branch belong to the hygiene loop and only the agent's own completion report authorises touching them. A merge rejected with `Base branch was modified` usually means the PR branch is STALE, not that a race occurred — run `gh pr update-branch`, then re-check; retrying the merge does not help, and seven retries here proved it. DURING A MERGE BURST IT IS A REAL RACE, AND `update-branch` MAKES IT WORSE FIRST: a post-merge hook commits `chore(beads): audit merged PR NNNN` and pushes it to `main` asynchronously seconds after each merge, so the base never holds still, and updating the branch restarts CI for long enough that another audit commit lands inside that window. One PR was refused THIRTY times; both transports agree (GraphQL `mergePullRequest`, and REST `PUT /pulls/{n}/merge` with an explicit sha returning HTTP 405), so it is not a client quirk. The remedy is counterintuitive: MERGE THE WHOLE QUEUE FIRST, then give the straggler a genuinely empty window — raising its nominal priority does the opposite of what it looks like, because priority without an empty window is just more attempts against a moving base. If a PR refuses more than about three times and nothing is blocked on it, SHELVE it and take it opportunistically on a later signal; persistence on an item that is blocking nothing is its own gold-plating. NEVER `git push origin --delete <branch>` before the merge succeeds (it auto-closes the PR). Verify state==MERGED via `gh pr view` before any branch cleanup. After EACH merge (don't batch): `git pull --ff-only origin main` immediately — NAME the remote and branch, because the bare form silently no-ops when the audit-hook push races it — then VERIFY THE TREE, NOT THE MESSAGE: `git rev-parse HEAD` must equal `git rev-parse origin/main`. It printed `Updating <old>..<new>` twice in one session here while HEAD had not moved at all. That comparison also false-alarms, from the same audit-hook push described above: it can land BETWEEN the two `rev-parse` reads, so a synchronised checkout reports a mismatch — after #7774 both refs, `FETCH_HEAD` and `ls-remote` all read the same sha and `rev-list --left-right --count` gave `0 0`. One disagreement is not yet evidence; re-read both refs and believe it only if it survives. Read the FETCH's own exit code for the same reason, because a failed fetch and a subsequent `Already up to date` print into the same output and the reassuring line is the lie. **AN ABORTED PULL HAS TWO CAUSES WITH DIFFERENT REMEDIES, AND THE MESSAGE SAYS WHICH** — naming the remote and branch cures the bare form's silent no-op but neither abort, so read the text git printed before reaching for the familiar fix. `local changes would be overwritten` is UNCOMMITTED tracker state: `sh scripts/beads-checkpoint.sh`, then `git checkout HEAD -- .beads`, then pull — that order and no other, because clearing `.beads` after a `bd close` reverts the close (CLAUDE.md, Beads durability). `fatal: Not possible to fast-forward, aborting.` is the opposite case and now the common one, because the checkpoint COMMITS: `.beads` is already clean, there is nothing to clear, and the divergence is between your own checkpoint commit and the audit-hook commits `origin` gained while you made it — measured here at `div=1/2`, then `div=2/9`, three separate times in one session. Clearing a file that is not dirty does nothing for that, and `--ff-only` cannot fast-forward a divergent branch however carefully you name the remote, so: `git pull --rebase origin main` — AND THEN PUSH IT, because the rebase replays your checkpoint commit on top of `origin` and leaves you AHEAD BY ONE. **That is the EXPECTED intermediate state, not a second failure**: `git rev-list --left-right --count HEAD...origin/main` reads `1 0`, and the equality check below cannot be satisfied until the push lands. The first live use of this drill hit exactly that — `084e142164`, subject `chore(beads): checkpoint`, sole parent `450dae1c` (#7833) — and both obvious reflexes are wrong: repeating the pull stays ahead, and forcing equality would discard the very checkpoint the drill exists to protect. `git push` is the step that makes the check answerable, and if the audit-hook writer wins the race again the push is REJECTED, which is this same divergence one turn later — fetch, rebase, push again. ONLY THEN verify the OUTCOME by four reads rather than the message — no rebase in progress (`.git/rebase-merge` and `.git/rebase-apply` both absent), `git status` clean, `HEAD` equal to `origin/main`, and the tracker row count equal in the working `.beads/issues.jsonl` and at `HEAD`. Do not wire either remedy behind a pipe: `git pull --ff-only origin main | tail -1 || <fallback>` NEVER RUNS THE FALLBACK, because a pipeline's exit status is `tail`'s and `tail` succeeds on a failed pull — redirect to a file, capture `$?` on the same command line, then trim for display. Then verify the worker closed its bead (close it with a concrete cross-ref reason if not), and record the decision in the bead. IF ANYTHING WAS ROUTED INTO THIS PR — a finding messaged to its holder rather than dispatched, with a note left on the bead that owns it — VERIFY IT LANDED IN THE DIFF before closing that owner, rather than assuming: a routed item is exactly the kind a worker may reasonably decline, and if it did not land the owner stays OPEN and is re-routed or dispatched, never duplicated (see `mayor-dispatch.md`). A real, repeated touched-surface failure is NOT a flake — dispatch a fix-worker to the same branch (run the ACTUAL failing gate, not a local proxy), never --admin past it. Honor any active operator pause. If no open PRs, say so and stop.
