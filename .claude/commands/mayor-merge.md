MAYOR LOOP (merge PRs).

**Run this on MOST signals — not just the cadence.** Any time you're re-invoked (a worker completing, an operator message, a loop tick), do a quick open-PR sweep and merge whatever is already green. Checking is cheap; it keeps the pipeline flowing.

**NEVER block the session waiting on CI.** Do NOT launch `gh pr checks <pr> --watch` (it occupies a slot and stalls you). Use a ONE-SHOT `gh pr checks <pr>` plus a ONE-SHOT `gh run list --branch <headRefName> --limit 25` per open PR: merge the ones that meet ALL FOUR clauses of the criterion below NOW; for any PR still short of it, leave it and re-check on the NEXT signal — the steady stream of worker-completions plus the cadence will catch it without a babysitting script.

**A green rollup must be COMPLETE, not merely clean — and a clean rollup is not a quiet branch.** Zero failures and zero pending is also what an EMPTY rollup reports — exactly what a PR shows in the seconds before its workflow runs are created, and what every PR shows while Actions is down. PR #7628 merged on a rollup read as 0/0/0 eleven seconds before its runs existed, and during the same day's Actions outage six PRs at once reported MERGEABLE with zero checks; the old wording would have taken all six. Two more ways the same read goes wrong, both learned since. CANCELLED IS NOT PASSED: a cancelled check is `status == COMPLETED`, so a tally keyed on completion counts it as green — one PR was reported here as "85 of 86 concluded, one check from complete" when the truth was 79 passed, 6 cancelled and 1 pending, six re-runs across four workflows from mergeable. AND A QUEUED RUN IS INVISIBLE TO THE ROLLUP: its checks are not attached to the head commit yet, so PR #7630 reported `ok=78 canc=0 fail=0 pend=0 total=78` — settled by every field it exposes — while `gh run list --branch` showed two runs QUEUED; merging there ships the PR two workflows short.

So the criterion is FOUR clauses and no one of them suffices:

1. `total` non-empty and inside this repo's band — ~86, and verify that with `gh pr checks` on recently merged PRs rather than trusting the number written here; a partial rollup of 11 is not a green one.
2. Every conclusion in {`SUCCESS`, `SKIPPED`}. CANCELLED is not passed, and neither is anything else.
3. Zero `QUEUED` and zero `IN_PROGRESS` entries in the rollup.
4. AND `gh run list --branch <headRefName> --limit 25` shows no queued or in-progress run whose `headSha` equals the PR's current `headRefOid`.

Clause 4 fails in both directions and both have cost ticks here. Never substitute a global `gh run list --limit 40` grouped by branch: the window truncates, and a branch with four queued runs did not appear in it at all because other branches filled it — the check reported "no live runs" for a branch that had four. And never key on the branch alone: two PRs sat at 86/86 for three ticks on runs still queued against a sha from before a re-trigger commit, and a stale-sha run is not evidence about this head. A guard that blocks forever is not safe, it is differently wrong.

A gate that verifies the absence of bad news rather than the presence of good news is the same fail-open class we hunt everywhere else in this repo, and the merge decision is not exempt from it. A rollup that is empty, short, carrying a cancellation, or shadowed by a live run on the current sha is a re-check on the next signal — never `--admin`, and never reported as green.

Run `gh pr list --state open`. For each PR: confirm the four-clause criterion above, the diff matches its bead, scope did not sprawl, failure output stays actionable, and a `## Quality gates` section is present. Merge on green. Use `--admin` ONLY when a pending check is structurally irrelevant to the diff — name the gate, name why the diff cannot affect it, then merge; a failing test on the touched surface is NEVER an --admin candidate (and `MERGEABLE=UNKNOWN` is GitHub's recompute lag, which `--admin` may bypass once the four clauses above are met). A merge rejected with `Base branch was modified` usually means the PR branch is STALE, not that a race occurred — run `gh pr update-branch`, then re-check; retrying the merge does not help, and seven retries here proved it. NEVER `git push origin --delete <branch>` before the merge succeeds (it auto-closes the PR). Verify state==MERGED via `gh pr view` before any branch cleanup. After EACH merge (don't batch): `git pull --ff-only` immediately — and read the FETCH's own exit code, because a failed fetch and a subsequent `Already up to date` print into the same output, and the reassuring line is the lie — verify the worker closed its bead (close it with a concrete cross-ref reason if not), and record the decision in the bead. A real, repeated touched-surface failure is NOT a flake — dispatch a fix-worker to the same branch (run the ACTUAL failing gate, not a local proxy), never --admin past it. Honor any active operator pause. If no open PRs, say so and stop.
