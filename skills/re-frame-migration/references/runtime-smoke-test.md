# runtime-smoke-test — "compiles" is NOT the done-bar

**"Compiles clean" is not even a registration check, which is what makes the runtime boot-smoke MANDATORY.** The retired `reg-event-db` / `reg-event-fx` / `reg-event-ctx` names are the proof: a v1 app calls them at the top of nearly every event namespace and can still compile 0-error / 0-warning, because the vars resolve and only throw when called at registration. Mechanism and the static pre-boot grep have a single owner in [`breaking-changes.md` §Compile-silent façade retirements](breaking-changes.md#compile-silent-façade-retirements--public-symbols-that-resolve-but-throw-at-registration); the consequence *here* is that verification needs a runtime — loop step 1 below, and row 7 of the checklist in [`silent-runtime-failures.md`](silent-runtime-failures.md).

This leaf is the **procedure half** of Phase 4 — Verify (SKILL.md). The **reference half** — the nine silent-failure modes this loop hunts, and why a compile cannot see them — is the sibling leaf [`silent-runtime-failures.md`](silent-runtime-failures.md).

## The boot smoke-test phase — live introspection, not just "it loads"

A migrated app needs a **runtime smoke-test** as a distinct verification step, separate from "the compile passed" and "the unit tests pass." The unit suite re-baselines counts (M-12) and exercises handlers in isolation; it does **not** prove the *assembled, booted* app wires up. The boot smoke-test does.

The cheapest tool that can see these failures is **live `app-db` + machine-snapshot inspection** — because every failure in the [checklist](silent-runtime-failures.md) is invisible in the build log and shows only in the running runtime's state. Two equivalent surfaces:

- **The `re-frame2-pair` MCP** (the Tool-Pair contract) — attach to the running shadow-cljs build's nREPL and read the live frame. `orient` for the app shape, then drill with **the read that matches the partition** — this is the crux, because Pair splits app-db and runtime-db and each read only sees one partition:
    - **app-db slots + subs** — `get-path {path: "[:some :app-db :slot]"}` (a `get-in` against the frame's **app-db** snapshot) and `read-sub {sub: "[:some/sub]"}`.
    - **runtime-db machine snapshots** — the canonical `read-sub {sub: "[:rf/machine <id>]"}`. Machine snapshots live in the **runtime-db** partition, so `get-path` reads app-db and will **not** find them, and `snapshot`'s `path:` argument slices only the app-db slice — **neither can reach** `[:rf.runtime/machines :snapshots]` (both return `:path-not-found` on a perfectly healthy machine). For a multi-machine inventory, read the gated machines slice: `snapshot {include: ["machines"], modes: {"machines": "full"}}` — this requires the server launched with `--allow-sensitive-reads` **and** the call passing `include-sensitive: true`. A redacted or summary slice is **inconclusive, never machine absence** — the verdict rule below is the authority on what counts as a pass.

  This is the recommended surface for a migration check — it speaks the exact slices the checklist needs and refuses ambiguous-frame reads. (Switch to the **`re-frame2-pair` skill** for a live session — see the post-migration hand-off in SKILL.md.)
- **A bare shadow-cljs nREPL** if Tool-Pair isn't wired — eval `(re-frame.core/app-db-value :rf/default)` for the app-db partition, `(:rf.db/runtime (re-frame.core/frame-state-value :rf/default))` for the runtime-db partition (machine snapshots at `[:rf.runtime/machines :snapshots]`). Same reads, less ergonomics.

**The "does it boot without throwing?" half needs no pair-MCP setup.** Steps 1 and 7 below are a **plain browser-console** job: load the dev build, watch the console for the `:rf.error/*` throws step 1 enumerates, and reload with an injected `window` `'error'` listener to capture the throwing stacks. Any CDP / devtools tool (or manual devtools) does it — no global server install, no fresh session to register it, no preload. The pair MCP is *optional richer tooling*: it earns its setup for the live `app-db` slice reads in steps 2–5 and deeper interactive debugging, not for the boot-without-throwing gate. (**One exception it cannot catch: checklist #9** — the async-callback `:rf.error/no-frame-context` fires only when its listener / timer / error path is *triggered*, never at boot; step 6 exercises those paths.) ([`re-frame2-pair` SKILL.md §Setup](../../re-frame2-pair/SKILL.md).)

**The smoke-test loop** (Cardinal rule 5: drive it yourself when a runtime is connected — a `re-frame2-pair` MCP or a shadow-cljs nREPL. With none to drive, the seven steps below ARE the one compact checklist you hand the programmer, and the report says the smoke is **pending** until they confirm it):

1. **Boot the app** in a dev build with `interop/debug-enabled?` true (so the loud diagnostics — `:rf.error/*-missing`, `:rf.error/sub-input-fn-bad-return` — actually fire and reach the trace). Note the M-70 registration-shape errors (`:rf.error/reg-event-bare-interceptor`, `:rf.error/reg-event-bad-middle-slot`, `:rf.error/reg-event-bad-arity`, #6), the M-73 retired-registrar errors (`:rf.error/reg-event-db-removed`, `:rf.error/reg-event-fx-removed`, `:rf.error/reg-event-ctx-removed`, #7), the reg-sub flat-sub-sugar error `:rf.error/reg-sub-bad-args` (#8), the **M-30 flow-vs-sub mis-triage** error `:rf.error/flow-bad-id` (a per-instance / parameterized v1 flow mechanically run through M-30 instead of routed to a parameterized `reg-sub` — a non-keyword `:id`; the view-only mis-conversion throws nothing and is caught by the inventory triage, not this boot scan), and `:rf.error/legacy-runtime-root` (M-15b, #3) throw unconditionally regardless of the debug flag — they surface on the console at first boot either way.
2. **Read each expected boot/singleton machine's snapshot** — via the canonical `read-sub {sub: "[:rf/machine <id>]"}` per machine (the snapshots live in the **runtime-db** partition, so an app-db read — `get-path`, or `snapshot`'s `path:` selector — will not reach `[:rf.runtime/machines :snapshots]`; for a multi-machine sweep use the gated machines slice from the Pair bullet above, or the raw-nREPL runtime partition of `frame-state-value`). Every boot/singleton machine the app started should have a live snapshot. **Empty-where-you-expected-one** means the machine never started (an `init!`/ordering problem, not a clobber — a `:db` replace cannot wipe runtime-db). And for each snapshot that IS present, assert the machine has **left its `:initial` state** — a converted machine still sitting in `:initial` after boot is a **silently-stalled await**: its awaited event is being produced in the un-addressed plain-global form, so it never arrives (the #1 machine-conversion silent failure; see [`async-flow-to-machines.md`](async-flow-to-machines.md)). If a boot event throws `:rf.error/legacy-runtime-root` it returned a `:rf/runtime`-bearing `:db` (checklist #3).
3. **Read the seed slots** the init handlers were supposed to write (`get-path` each one). **`nil`-where-you-seeded is #5** (the `(when …)` nil-thread) — or **#4** with an `:rf.error/effect-map-shape` beside it, where an unfolded top-level key aborted the whole init event and took its `:db` write with it.
4. **Deref the subs** the first screen depends on (`read-sub`). **`nil`-or-error is #1 or #2** (signal-fn `reg-sub` / artefact-missing).
5. **Dispatch one real event per feature surface** (a machine event, a managed-HTTP request, a route change) and re-read the affected slot. **No-op-with-no-error is the artefact-missing or clobber tell.**
6. **Exercise each async entry point installed outside a view** — fire a route change (popstate / hashchange), let a `setTimeout` / `setInterval` / `requestAnimationFrame` callback run, raise a `window 'error'`, trigger a JS-lib lifecycle callback — and watch the console for `:rf.error/no-frame-context` (**checklist #9**). These throw only at **first FIRE**, not at boot, so a boot-without-firing scan misses them; the smoke must *trigger* the paths, not just load the page.
7. **Scan the dev trace** for any `:rf.error/*` / `:rf.warning/*` emitted during boot — these are the loud half of the failure surface and name the exact subsystem.

A migration is **not done when it compiles**. It is done when this loop comes back clean: every expected snapshot present, every seeded slot populated, every first-screen sub producing a value, and a clean boot trace.

**Worked example — one boot machine, partition-correct.** App frame `:app/main` boots a singleton machine `:app/boot` that should leave its `:initial` state once its coeffects resolve. Verify it through the runtime-db-aware read — **not** an app-db path:

```
# app-db seed slot (app-db partition) — get-path is correct here:
get-path {path: "[:session :ready?]"}          ; => true

# the boot machine (runtime-db partition) — read-sub is the canonical read:
read-sub {sub: "[:rf/machine :app/boot]"}       ; => {:state :running :data {…}}
```

The machine snapshot came back with `:state :running` — it **left `:initial`**, so the boot completed. Had the migration pointed an app-db read — `get-path`, or `snapshot`'s `path:` selector — at `[:rf.runtime/machines :snapshots :app/boot]` instead, it would query app-db and return `:path-not-found` **while the machine was perfectly healthy** — a false "machine never started" verdict driving an unnecessary M-40/O-16 boot-machine rewrite. (Raw-nREPL equivalent, if Tool-Pair isn't wired: `(get-in (:rf.db/runtime (rf/frame-state-value :app/main)) [:rf.runtime/machines :snapshots :app/boot])`.)

> **Verdict rule — what counts as a PASS vs INCONCLUSIVE.** A machine gate PASSES only when a **partition-correct** read returns the live snapshot *and* shows it left `:initial`. The following results are **INCONCLUSIVE — never report them as empty, clean, or passed:** a `:path-not-found` from `get-path` / a `snapshot` `path:` read (you queried the wrong partition), a `:rf/redacted` machines slice (the server wasn't launched `--allow-sensitive-reads`, or the call didn't pass `include-sensitive: true`), a **summary**-mode machines slice (you didn't request `modes {"machines":"full"}`), and any ambiguous- / no-frame result. Re-issue a partition-correct read before ruling on the machine.

## The done-bar is more than the local dev build

The boot smoke-test loop above clears the **booted dev build** — necessary, but only one axis of "done." A migration run entirely on the author's own machine can show a green dev build *and* a clean boot smoke and **still** be unshippable, because the done-bar reaches past the local dev build. The gates below are not optional polish — each catches a class the dev-build boot smoke structurally cannot: the **test suite**, then **CI green on a clean checkout**, and — because every gate named so far runs a dev (`:none`) build — the **optimized / release compile**, which gets its own section [below](#the-dev-compile-is-not-the-optimized-compile--the-fourth-done-bar-gate).

### The test suite is a THIRD gate the compiler and boot-smoke both miss

The M-rule sweep targets the application's `src/`; the boot smoke verifies the *booting* app. **Both can be green while the test-support / fixtures / `*_test` namespaces still run v1 test API the sweep never touched** — that layer is its own Phase-0a sweep target ([`inventory-and-plan.md`](inventory-and-plan.md)), carrying a v1 test-API subset a `src/`-focused grep misses. It is invisible to **both** existing gates:

- **The compiler passes.** The retired `reg-event-db` registrar is a facade-exported throwing stub — it *resolves*, so the compile stays clean. `make-restore-fn` / `add-post-event-callback` / `remove-post-event-callback` are undeclared vars on the v2 facade, which CLJS reports as **warnings, not errors** — the build "completes with N warnings" and proceeds.
- **The boot smoke passes.** Fixtures and `*_test` namespaces load only under the **test runner**, never at app boot — so the booted-app smoke never executes a line of them.

Neither gate covers the test layer. It surfaces only when the **suite RUNS**: the first fixture `:before` throws on the undefined v1 var, and the runner reports **"No test results found"** — a runner crash with zero results, not a failed assertion. So **running the test suite on a clean checkout is a required third gate, after the compile and the boot smoke.** The v1 test-API → v2 mapping (M-25, M-26, M-64, M-73, and the `:async? true` fixture requirement for `(async …)` suites) has one owner: [`auto-call-site-rewrites.md` §Test-layer v1 API to v2 mapping](auto-call-site-rewrites.md#test-layer-v1-api-to-v2-mapping). Sweep it as its own Phase-0a row ([`inventory-and-plan.md`](inventory-and-plan.md)).

### CI green on a clean checkout is the real done-signal

Every gate above is **local** — they run on the author's machine. The actual done-signal is off-machine: **CI green on a clean checkout**, and the gap that hides is the consumption coordinates. A tree consuming re-frame2 through `:local/root` absolute paths compiles, boots and smokes clean locally while every CI run is red from the first step, because those paths exist only on the author's disk. Repinning every re-frame2 and forked-upstream dep to a clean-runner-resolvable coordinate is the done-gate, and it has one owner: [`setup.md` §The consumability done-gate](setup.md#the-consumability-done-gate).


## The dev compile is NOT the optimized compile — the fourth done-bar gate

Everything above separates "compiles" from "boots and runs." There is a **second** split, *inside* "compiles" itself: the convergence compile, the `watch` the boot smoke-test boots under, and the unit suite all run a **dev (`:none`) build**, which does not run Closure's whole-program passes. Tree-shaking (`RemoveUnusedCode` and its siblings) and the deep recursive AST traversals it performs fire **only** under an optimized compile. So a tree green on every dev gate can still fail the optimized one, and no dev gate can see it — which makes **the optimized / release compile a fourth done-bar gate**, run explicitly after the other three.

**Why a migration is the build most likely to trip it.** A re-frame2 migration *enlarges and deepens* the compiled output along exactly the axes those recursive passes are sensitive to. The v2 substrate splits into **per-feature add-on artefacts** (core / reagent-adapter / machines / http / flows), each contributing namespaces and re-exports; the **M-11** conversion wraps the *whole* subscribing view tree in `reg-view`; and vendored shims for dropped v1 add-ons add still more. More and deeper code makes Closure's **recursive** optimization passes recurse deeper — deep enough that a traversal can exceed the JVM compile thread's stack and throw a **`StackOverflowError`** from inside a pass such as `RemoveUnusedCode` (`…RemoveUnusedCode/traverseChildren`). It is invisible in dev / `:none`, in `watch`, in the unit suite, and in the boot smoke-test; it surfaces only when the **optimized** compile runs — commonly CI's optimized release / browser-test build.

This is a real field outcome, not a hypothetical: a migration went green on the dev compile (1200+ files, 0 warnings), 126 passing unit tests, and a clean boot smoke-test, **while CI was red on every branch** with `StackOverflowError at com.google.javascript.jscomp.RemoveUnusedCode/traverseChildren` in the optimized browser-test compile. The dev done-bar reported "done"; the optimized gate did not.

The cure — raise the **compile** JVM's thread stack with `-Xss` — plus the placement gotcha that decides whether it reaches the compile JVM at all, the `:simple`-vs-`:advanced` stack budgets, and the non-convergent case where `-Xss` is masking a structural problem, all live in [`release-compile-gate.md` §The optimized / release compile gate](release-compile-gate.md#the-optimized--release-compile-gate--raise--xss-for-the-stackoverflow-class).
