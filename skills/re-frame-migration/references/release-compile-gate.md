# release compile gate

The Phase-4 done-bar gate the dev build never runs: the **optimized / release** compile, the `StackOverflowError` class of failure a migration is unusually likely to hit there, and the `-Xss` remedy — with its placement gotcha and the non-convergent case that means `-Xss` is masking a structural problem rather than curing it. The M-0 coord swap lives in [`setup.md`](setup.md); the surrounding done-bar checklist is in [`runtime-smoke-test.md`](runtime-smoke-test.md).

---

## The optimized / release compile gate — raise `-Xss` for the StackOverflow class

The post-M-0 compile gate and the Phase-4 done-bar are **two compiles, not one**: the dev (`:none`) build that every other gate runs (the convergence compile, the `watch` the boot smoke-test boots under, the unit suite), and the **optimized / release compile** (`:simple` / `:advanced` — `shadow-cljs release`, or whatever command CI runs). Only the optimized compile runs Closure's whole-program passes, so it is a **separate done-bar gate** — see [`runtime-smoke-test.md` §The dev compile is NOT the optimized compile](runtime-smoke-test.md#the-dev-compile-is-not-the-optimized-compile--the-fourth-done-bar-gate) for why a migration is the build most likely to fail it (the artefact-split + `reg-view` enlargement deepens the AST until a recursive Closure pass like `RemoveUnusedCode` overruns the JVM compile thread's stack and throws `StackOverflowError`).

**The remedy: raise the compile JVM's thread stack.** Give the JVM that runs the optimized compile a larger `-Xss` (thread stack size) — start at `8m`, go to `16m` if it still overruns (those are starting rungs, not a ceiling — see the `:simple` / `:advanced` split next). That buys headroom for the deeper recursion the enlarged AST drives; it changes not a byte of the emitted output. But `-Xss` is the *first* move, not always the *whole* fix — past a point it stops converging, and a non-convergent overflow is a structural signal, covered below.

**`:simple` (test) vs `:advanced` (release) are two different stack budgets — size for the `:advanced` leg.** A migration typically runs *two* optimized compiles, not one: the `:simple` test / browser-test compile, and the `:advanced` **release** compile (`shadow-cljs release app`, or whatever command CI's production build runs). They are separate passes with very different stack appetites, and **the `:advanced` / release leg is the binding one** — `:advanced` runs the full aggressive whole-program optimization, so it recurses far deeper than `:simple` on the same tree. Treat `8m → 16m` as the *first rungs of a ladder, not a ceiling*: in the field the `:simple` leg cleared at `16m` while the `:advanced` release leg kept overflowing until the stack was raised by **orders of magnitude** (illustratively past `256m` — many times the `16m` you might assume is "plenty"; the exact numbers are workload-specific). Size `-Xss` for whichever leg overflows last, which is almost always `:advanced` — a value that greens `:simple` tells you nothing about `:advanced`.

**The shadow-cljs `:jvm-opts` placement gotcha — get this exactly right, or the `-Xss` silently does not apply.** *Where* you set `-Xss` decides whether it reaches the compile JVM at all, because shadow-cljs compiles via two different JVM-launch paths:

- **`shadow-cljs.edn`'s `:jvm-opts`** applies **only** when the **node launcher** (`npx shadow-cljs …`) starts the JVM.
- It does **not** apply when the compile runs through the **Clojure CLI** (`clojure -M… -m shadow.cljs.devtools.cli compile|release`): there the JVM is launched by `clojure`, which reads its `-Xss` from the **`deps.edn` alias `:jvm-opts`** instead (or from `JAVA_TOOL_OPTIONS`, or a `-J-Xss…` flag on the command line).

**CI commonly drives the optimized compile through the Clojure-CLI path**, so an `-Xss` set only in `shadow-cljs.edn` silently has no effect there — the optimized compile keeps overflowing while the config *looks* correct. Set `-Xss` on **whichever launcher actually starts the compile**: the `shadow-cljs.edn` `:jvm-opts` for the `npx shadow-cljs` path, the consuming alias's `deps.edn` `:jvm-opts` (or `JAVA_TOOL_OPTIONS` / a `-J-Xss…` flag) for the `clojure -M` path. When unsure which path CI uses, set both.

**`-Xss` can be *non-convergent* — and a non-convergent overflow is a structural signal, not a tuning knob.** Raising `-Xss` can *paper over* the overflow rather than cure it, leaving the release build balanced on a knife-edge. The proof is reproducible: at a large stack (illustratively `512m`) a migrated tree compiled clean, yet a single **behaviour-preserving one-line edit** — e.g. `(f args)` → `(f (first args))` — *deterministically* re-tripped the same `:advanced` `StackOverflowError`, while the identical tree *without* that line compiled fine at the *same* setting. So "raise `-Xss` until it goes green" can yield a build that is green today and broken by the next trivial edit — the headroom you bought is spent by an unrelated change. **Warning sign:** an `:advanced` overflow that *recurs* — re-trips after a small edit, or only a huge `-Xss` quiets it — means `-Xss` is *masking* a structural problem, not solving it. **Stop escalating the stack** and diagnose instead.

**Diagnose before you remediate — capture the recursive frame *above* the leaf.** The overflow's leaf frame is uninformative: it is usually a cheap accessor the recursive pass calls on every node (e.g. `…Node.getProp` / `rhino.Node.getProp`), which tells you nothing about *what* is being traversed. The signal is the **repeating caller frame** just above the leaf — the recursive method that names *what* the pass is deep-traversing: your migrated CLJS, versus a single bundled vendor file. Capturing that frame pattern is the step that actually identifies the driver. It is easy to skip and costly to skip — in the field case a bundled vendor megafile was the *leading hypothesis*, but the decisive frame pattern was never captured, so the driver was never confirmed. That is exactly why "diagnose before remediating" earns its place here rather than guessing at the cause.

**Structural remedy — keep prebuilt / minified vendor JS out of the `:advanced` graph.** When the captured frames show the deep traversal is over a large **prebuilt, already-minified vendor bundle** dragged into the whole-program graph — commonly a heavyweight spreadsheet / data-grid / charting library shipped as a single multi-megabyte one-line `.min.js` — the fix is structural, not more stack. Have Closure treat that bundle as a **prebuilt external** instead of re-optimizing an already-minified file. In shadow-cljs that is the `:js-options` surface: point the dependency at the prebuilt artefact with a per-package `:resolve` (e.g. to a global or a file), or push JS through `:js-provider :external` for an all-external split — paired with Closure `:externs` (under `:compiler-options`) so `:advanced` renaming leaves the external's surface untouched. (The legacy ClojureScript `:foreign-libs` mechanism is *not* a current shadow-cljs surface — shadow-cljs dropped it — so reach for `:js-options` / `:externs`, not `:foreign-libs`.) Two adjacent things are worth a look while you are here: whether the migration changed *how* that module is required (a different import shape can pull it into the optimized graph where it was previously left alone), and whether **M-0's toolchain bump regressed the pass** — M-0 often bumps shadow-cljs, which pulls a newer Closure Compiler, and a Closure version change can shift a recursive pass's depth on the same input.

(This is a stack-**depth** `StackOverflowError` in the **optimized** compile of the migrated *app's own* code, cured by `-Xss` headroom *when it converges* — a distinct failure from any dev-build transpile-down error, which `-Xss` would not touch.)
