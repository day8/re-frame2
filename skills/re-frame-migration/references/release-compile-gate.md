# release compile gate

The Phase-4 done-bar gate the dev build never runs: the **optimized / release** compile, the `StackOverflowError` a build can hit inside the Closure Compiler there, how to tell which compile path overflowed before attributing it, and the `-Xss` stack experiment — with its placement gotcha and the non-convergent case that means a stack raise is masking a structural problem rather than curing it. The M-0 coord swap lives in [`setup.md`](setup.md); the surrounding done-bar checklist is in [`runtime-smoke-test.md`](runtime-smoke-test.md).

## The optimized / release compile gate

The post-M-0 compile gate and the Phase-4 done-bar are **two compiles, not one**: the dev (`:none`) build that every other gate runs (the convergence compile, the `watch` the boot smoke-test boots under, the unit suite), and the **optimized / release compile** (`:simple` / `:advanced` — `shadow-cljs release`, or whatever command CI runs). Only the optimized compile runs Closure's whole-program passes over the application, so it is a **separate done-bar gate** — see [`runtime-smoke-test.md` §The dev compile is NOT the optimized compile](runtime-smoke-test.md#the-dev-compile-is-not-the-optimized-compile--the-fourth-done-bar-gate) for why a tree green on every dev gate can still fail it.

**A Closure frame does not say which compile failed.** A shadow-cljs build reaches the Closure Compiler by two paths:

- **The application's optimization** — the build's own `:simple` / `:advanced` setting, in a release or optimized test build. A dev build skips it.
- **The npm conversion** — under the `:shadow` JS provider, the `:browser` target's default, `node_modules` sources are converted by a separate Closure `:simple` run, in every build mode including dev, and the result is cached. The shadow-cljs User's Guide says these sources "do not go through `:advanced` compilation"; the `:closure` provider instead sends them through the application's `:advanced`.

Closure's `:simple` level runs `RemoveUnusedCode` as well, so an overflow in `…RemoveUnusedCode/traverseChildren` can come from either path, and a cold cache runs a conversion a warm one skips. The command does not settle it either: `shadow-cljs release` runs both.

**Before attributing or treating an overflow, record:**

- the complete error report — for a Clojure CLI launch, the full report file it names, not only the summary line;
- the selected shadow-cljs, Closure Compiler and ClojureScript versions;
- the effective stack setting of the JVM that ran the compile (the placement gotcha below is why the configured value and the effective one can differ);
- the cache state (cold or warm) and the JS provider;
- which path failed — npm conversion or application optimization, and for the latter which leg (`:simple` or `:advanced`). The frames below the recursion name the shadow-cljs step that called Closure when the trace reaches them; otherwise the build's own output, or an isolation run, decides it.

Where one of these cannot be measured, say so in the report rather than inferring it.

**A stack raise is an experiment, not a diagnosis.** Change one variable: raise the stack of the JVM that runs the failing compile by a modest step, and re-run identical inputs — the same source, versions, cache state and command. Record both runs and both values. A pass means headroom was the limit on that input (the stack changes not a byte of the emitted output); it does not say what drove the depth. A failure, or a pass the next small edit undoes, means stop raising and diagnose (the non-convergent case below). Do not climb a ladder of values until the build goes green. The `:simple` and `:advanced` legs can differ widely in stack appetite, so a value that clears one says nothing about the other.

**The shadow-cljs `:jvm-opts` placement gotcha — get this exactly right, or the `-Xss` silently does not apply.** *Where* you set `-Xss` decides whether it reaches the compile JVM at all, because shadow-cljs compiles via two different JVM-launch paths:

- **`shadow-cljs.edn`'s `:jvm-opts`** applies **only** when the **node launcher** (`npx shadow-cljs …`) starts the JVM.
- It does **not** apply when the compile runs through the **Clojure CLI** (`clojure -M… -m shadow.cljs.devtools.cli compile|release`): there the JVM is launched by `clojure`, which reads its `-Xss` from the **`deps.edn` alias `:jvm-opts`** instead (or from `JAVA_TOOL_OPTIONS`, or a `-J-Xss…` flag on the command line).

**CI commonly drives the optimized compile through the Clojure-CLI path**, so an `-Xss` set only in `shadow-cljs.edn` silently has no effect there — the optimized compile keeps overflowing while the config *looks* correct. Set `-Xss` on **whichever launcher actually starts the compile**: the `shadow-cljs.edn` `:jvm-opts` for the `npx shadow-cljs` path, the consuming alias's `deps.edn` `:jvm-opts` (or `JAVA_TOOL_OPTIONS` / a `-J-Xss…` flag) for the `clojure -M` path. When unsure which path CI uses, set both.

**`-Xss` can be *non-convergent* — and a non-convergent overflow is a structural signal, not a tuning knob.** Raising `-Xss` can *paper over* the overflow rather than cure it, leaving the release build balanced on a knife-edge. The proof is reproducible: at a large stack (illustratively `512m`) a migrated tree compiled clean, yet a single **behaviour-preserving one-line edit** — e.g. `(f args)` → `(f (first args))` — *deterministically* re-tripped the same `:advanced` `StackOverflowError`, while the identical tree *without* that line compiled fine at the *same* setting. So "raise `-Xss` until it goes green" can yield a build that is green today and broken by the next trivial edit — the headroom you bought is spent by an unrelated change. **Warning sign:** an overflow that *recurs* — re-trips after a small edit, or only a huge `-Xss` quiets it — means `-Xss` is *masking* a structural problem, not solving it. **Stop escalating the stack** and diagnose instead.

**Frames name the algorithm, not the input.** The leaf frame is usually a cheap accessor the recursive pass calls on every node (e.g. `…Node.getProp`), and the repeating frames above it name the pass and its recursion — `RemoveUnusedCode.traverseChildren` simply calls `traverseNode` on each child node, and nothing in that frame says whether the nodes came from migrated CLJS or from a vendor file. Treat the repeating frames as the route into diagnosis, not its result. Naming an offending input takes one of two kinds of evidence: a **resource mapping** — output tying the failure to the file the failing step was processing — or a **controlled isolation** — the same build, inputs and settings with one suspect removed or swapped, failing with it and passing without. Until one of those confirms it, a suspected provider, a large package or one recursive method name is a hypothesis.

**Structural remedy — keep prebuilt / minified vendor JS out of the Closure path that overflowed.** When a resource mapping or controlled isolation shows the deep traversal is over a large **prebuilt, already-minified vendor bundle** — commonly a heavyweight spreadsheet / data-grid / charting library shipped as a single multi-megabyte one-line `.min.js` — the fix is structural, not more stack. Have Closure treat that bundle as a **prebuilt external** instead of re-optimizing an already-minified file. In shadow-cljs that is the `:js-options` surface: point the dependency at the prebuilt artefact with a per-package `:resolve` (e.g. to a global or a file), or push JS through `:js-provider :external` for an all-external split — paired with Closure `:externs` (under `:compiler-options`) so `:advanced` renaming leaves the external's surface untouched. Under the default `:shadow` provider an npm-installed bundle never enters the application's `:advanced` graph, so an overflow traced to it sits in the npm conversion; under `:closure` it sits in the application's optimization. (The legacy ClojureScript `:foreign-libs` mechanism is *not* a current shadow-cljs surface — shadow-cljs dropped it — so reach for `:js-options` / `:externs`, not `:foreign-libs`.) Two adjacent things are worth a look while you are here: whether the migration changed *how* that module is required (a different import shape can move it onto a different path), and whether **M-0's toolchain bump changed the compiler** — M-0 often bumps shadow-cljs, which pulls a newer Closure Compiler, and a Closure version change can shift a recursive pass's depth on the same input. The recorded versions answer that one.

(This is a stack-**depth** `StackOverflowError` inside a Closure pass — on the application's optimization path or the npm conversion path — and a distinct failure from any dev-build transpile-down error, which a stack change would not touch.)
