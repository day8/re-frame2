# Pre-rename upgrades — v2-pre-rename-only rules (NOT for a v1→v2 migration)

## When to load

Only when the codebase being upgraded is a **pre-release v2 build** moving to a newer pre-release v2 build, or an agent is auditing an `M-id` cite from that family. **A v1→v2 migration never loads this leaf** — every rule here governs surfaces that only ever existed in pre-release v2 builds (trace/epoch listeners, the machine substrate, the routing substrate, the schema-validator family, managed-HTTP interceptors, the frame-affordance surface, the test-fixture builders, the Xray configuration surface); v1 had none of them. The Phase-0a inventory flags these surfaces when it finds them; [`breaking-changes.md`](breaking-changes.md) carries the authoritative v1→v2 rule index and points here.

## The rules (M-44, M-55–M-61, M-31a, M-31b, M-63–M-65, M-67–M-69, M-74)

These M-rules govern surfaces that **only ever existed in pre-release v2 builds** — trace/epoch listeners, the machine substrate, the routing substrate, the schema-validator family, managed-HTTP interceptors, the frame-affordance surface, the test-fixture builders, the Xray configuration surface. **v1 had none of them**, so a codebase migrating *from re-frame v1* can never trip them. They appear here only so a codebase upgrading **between two pre-release v2 builds** (or an agent auditing an M-id cite) can still find the rule. Each keeps its `M-N` id and its full description; the only change versus the main table is location. (Triggers, types, and the Type-A/Type-B at-a-glance lines above all still cover them.)

### Data-classification retirements (v2-pre-rename only)

**A v1→v2 migration reader can skip this — v1 had no data-classification API.** The data-classification redesign replaced the earlier marking-site / frame-annotation models with a **path-based, fail-open** one and **removed** these surfaces. A codebase upgrading between two pre-release v2 builds rewrites them as:

- `rf/add-marks` / `rf/set-marks` / `rf/clear-app-db-marks!` (imperative per-frame app-db path-marks) **and** the frame `:sensitive` / `:large {:app-db …}` durable annotation → return the durable-app-db classification effect from the writing event: `(rf/reg-event :auth/init (fn [{:keys [db]} _] {:db (assoc db :auth {}) :sensitive [[:auth :token]] :large [[:docs :csv-upload]]}))`. The event is app-db's definition site; a frame config `:sensitive` carrying an `:app-db` block is rejected fail-loud. Wire known-path classification via `:initial-events`.
- `rf/declare-sensitive-header!` / `rf/declare-sensitive-query-param!` (and the `clear-*!` pair) → declare the app-specific carrier NAMES on the managed-HTTP effect's `reg-fx` registration (the transient-payload case): `(rf/reg-fx :rf.http/managed {:carriers {:headers ["X-Honeycomb-Team"] :query-params ["shop_token"]}} h)`. The earlier frame `:sensitive {:http …}` block is also gone — carriers ride the `:rf.http/managed` registration now. Built-in HTTP denylists remain immutable framework defaults the carriers union onto.
- `rf/redact-interceptor` (positional payload-path scrub) → classify the transient payload with registration metadata: `(rf/reg-event :auth/login {:sensitive [[:password] [:totp-code]]} …)`. There is no positional redaction interceptor in the shipped surface.
- schema-attached app-db `:sensitive?` / `:large?` (a route into durable classification) → durable app-db is the `:sensitive` / `:large` classification effects; durable machine `:data` snapshot egress is the **projection-relative `:sensitive` / `:large` declaration on the `reg-machine` definition** (`reg-machine` now DOES take top-level `:sensitive` / `:large` keys). Per-slot `:sensitive?` / `:large?` props **remain** the route for HTTP request `:decode` bodies (transient) and for a schema's own validation-failure-trace redaction — NOT for durable app-db or machine `:data` snapshot egress.
- **all sensitivity propagation** — input → output inheritance through subs / flows, and the `:rf.egress/output-sensitivity` declassification claim → classify the output path directly; nothing propagates. A derived secret is just a classified db path.

The contract is **fail-open**: a path you never classify ships raw (no propagation, no taint). At the boundary, every off-box record routes through `rf/project-egress` (closed six-member `:rf.egress/*` profile enum) — the one public projection primitive — and production sinks register via `rf/register-observability-sink!` under a frame's `:observability` policy. See [`spec/015-Data-Classification.md`](https://github.com/day8/re-frame2/blob/main/spec/015-Data-Classification.md) and [`spec/API.md` §Privacy](https://github.com/day8/re-frame2/blob/main/spec/API.md) for the shipped contract. (These retirements carry no `M-NN` id — they govern only pre-release v2 surfaces and never appear in a from-v1 migration; the M-rule table is the authoritative list for v1→v2 breakages.)

## Where these rules ride in the sweep order

[`sequencing.md`](sequencing.md) interleaves most of the pre-rename rules as lettered rows inside the main order (9a — M-64; 18a/18b — M-56/M-60; 21a/21b/21c — M-58/M-59/M-55+M-69; 38a/38b — M-63/M-65), so a pre-rename upgrade follows the same one-pass sweep as a v1→v2 migration. The remainder carry no lettered row of their own: **M-44** rides the main order at unlettered step 25; **M-31a** applies beside 38b (M-65) — the same `re-frame.http.test-support` require, reached from the same test namespaces; **M-74** has no ordering constraint of its own — apply it beside 18a (M-56), the other machine-vocabulary rename; **M-67** is a standalone config-key drop with no sweep dependency at all; **M-31b** and **M-68** are single-surface rewrites that sit wherever their trigger surface does. The full M-55/M-69 listener-verb rename table (with the trace-stream correctness notes) lives in [`auto-cross-cutting.md` §Listener-registration verb unification](auto-cross-cutting.md#listener-registration-verb-unification-m-55) — that leaf remains the mechanical-rewrite home; this leaf is the rule index.
