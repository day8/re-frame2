A one-page index keyed to v1 trigger surfaces. The author asks *"is `X` covered by a rule?"* — you grep here, find the rule id, then load that rule's full text from [`MIGRATION.md`](../../../migration/from-re-frame-v1/README.md).

**This leaf does not replace [`MIGRATION.md`](../../../migration/from-re-frame-v1/README.md).** It points at it. The authoritative `What to look for` / `What to do` / `Why` per rule lives in MIGRATION.md. Every entry here gives just enough to identify the rule.

## v1 add-on libraries fail to COMPILE on v2 — replacement/removal is FORCED, not opt-in

> **This is a required pre-step, not an O-rule.** Several widely-used v1 add-on libraries `:refer` or call **`re-frame.core/console`** — the v1 logging-indirection symbol. **re-frame2 removes `re-frame.core/console` entirely** (the public façade defines no `console`; there is no alias and **no back-compat shim** — per the pre-alpha posture, these v1 add-ons are *superseded*, not propped up). The moment `day8/re-frame2` is on the classpath, any such add-on **fails to compile** — `re-frame.core/console` does not resolve. **The add-on does NOT keep working; the app does NOT compile** until the add-on is removed or replaced. This is independent of whether the app has converted its own call sites.

Confirmed-broken v1 add-ons (each references the removed `re-frame.core/console`):

| v1 add-on (Maven coord) | Breaks because | v2 replacement path | Conversion rule |
|---|---|---|---|
| `day8.re-frame/http-fx` (`:http-xhrio`) | `:refer [… console]` | re-frame2 **managed HTTP** (`:rf.http/managed`, `day8/re-frame2-http`, M-31) | **O-17** (the conversion is the modernisation; doing *something* — convert or remove — is forced) |
| `day8.re-frame/async-flow-fx` (`:async-flow`) | calls `(re-frame/console :error/:warn …)` | re-frame2 **machines / flows** (`reg-machine` Spec 005, M-28; or `reg-flow` Spec 013, M-30) | **O-16** (same — convert or remove is forced) |
| `day8.re-frame/undo` | calls `re-frame.core/console` | no drop-in v2 equivalent — re-implement undo via app-db snapshots / Tool-Pair time-travel (`day8/re-frame2-epoch`), or **remove** | document the v2 path or removal (no O-rule) |
| `day8.re-frame/forward-events-fx` | transitive of async-flow-fx | folds into the machine/flow conversion (forward-events orchestration → machine transitions), or **remove** | folds into O-16, or removal |

**What this means for the migration flow.** The O-16 / O-17 *conversion to the v2 successor* stays opt-in (the operator chooses whether to modernise to machines / managed-HTTP). But **removing or replacing the broken add-on is FORCED** — the app cannot compile with the v1 add-on on the v2 classpath, so a "drop in re-frame2, modernise the add-ons at leisure" plan is **not available**. The agent must surface, as a **required** step at the compile gate:

1. **Detect** the broken add-on coords in the dep file(s) (`day8.re-frame/http-fx`, `async-flow-fx`, `undo`, `forward-events-fx`) and their fx fingerprints (`:http-xhrio`, `:async-flow`).
2. **State plainly** that each fails to compile on v2 (removed `re-frame.core/console`) and must be removed or converted *before the project will compile* — this is not deferrable.
3. **Offer the conversion path** (O-16 / O-17 / undo re-implementation) as the modernisation, or **removal** if the feature is no longer needed — and let the operator choose *which*, but not *whether* to act.

(Distinct from the **classpath-collision** failure mode in [`setup.md` §Edge cases](setup.md) — a v1-built add-on can also root a transitive `re-frame/re-frame` coord. That is a *separate* breakage; an add-on can hit both. The `console` break here is a **compile error inside the add-on's own source**, not a coord conflict.)

This surface is keyed off dep-/application-level triggers (Maven coords + fx ids), so it pairs with the O-16 / O-17 detection — but the removal/replacement is required, not gated behind the opt-in question.

## Compile-only façade removals — public `re-frame.core` symbols that no longer resolve

A short register of **public v1 `re-frame.core` symbols that simply do not exist on the v2 façade**. They are a pure **compile-only** class: the var does not resolve, so the call site is an *unresolved-symbol compile error* — never a runtime surprise. This is the **loud-fail / march-the-wall** shape (the compiler names the missing symbol; swap it, recompile, repeat — the opposite of the silent-fail register further down). They get their own register because each is a *public* surface an author would not expect to have moved — unlike the off-contract **private**-namespace requires of M-1 — and because the M-rule table is keyed by trigger *surface*, so grepping it does not surface the bare symbol names below.

| Removed public symbol (v1) | What happens in v2 | Replacement | Rule |
|---|---|---|---|
| `clear-subscription-cache!` (the no-arg public form) | Gone from `re-frame.core` — unresolved symbol at compile. | `(rf/clear-sub-cache! :rf/default)` — the v2 name takes a **required frame-id** (the v1 zero-arg form is gone; every frame now has its own sub-cache). `:rf/default` is the like-for-like target for code that never addressed frames. Per [`spec/API.md`](../../../spec/API.md#dispatch-and-subscribe) §`clear-sub-cache!`. | **M-1** |
| `get-coeffect` / `get-effect` | Removed from the `re-frame.core` façade — unresolved symbol at compile. | Inside a `reg-interceptor` `:before`/`:after` fn, **read the context map directly**: `(get-in ctx [:coeffects k])` / `(get-in ctx [:effects k])`. | [`spec/API.md`](../../../spec/API.md) §Removed |
| `assoc-coeffect` / `assoc-effect` | Removed from the façade — unresolved symbol at compile. | Inside a `reg-interceptor` `:before`/`:after` fn, **write the context map directly**: `(assoc-in ctx [:coeffects k] v)` / `(assoc-in ctx [:effects k] v)`. | [`spec/API.md`](../../../spec/API.md) §Removed |
| public `->interceptor` (and any inline interceptor **value** in a chain) | No public authoring form — `->interceptor` is internal-only, and EP-0022 chains are reference-only, so an inline value is also rejected. | Author the before/after work with `(rf/reg-interceptor id descriptor)` and reference it by **id** in the event/frame `:interceptors` chain. | **M-21** |

**These accessors are removed, NOT relocated — do not chase a public successor namespace.** The owning-namespace fns (`re-frame.interceptor/get-coeffect`, `…/assoc-effect`, the internal `->interceptor` constructor) **remain framework-internal**. They are off-contract, so a `(:require [re-frame.interceptor …])` reaching for them is itself an **M-1** off-contract-namespace break, not a fix. The supported destination is the direct `get-in` / `assoc-in` context-map access shown above (for the accessors) or a registered interceptor referenced by id (for `->interceptor`). The interceptor-surface shrink that retires `->interceptor` and inline chain values is [M-21](../../../migration/from-re-frame-v1/README.md#m-21-drop-debug-trim-v-on-changes-enrich-after-interceptors); the `clear-subscription-cache!` rename rides [M-1](../../../migration/from-re-frame-v1/README.md) (the private-namespace rule, which folds in this one public rename because every codebase that uses it trips the same mechanical rewrite).

## Compile-silent façade retirements — public symbols that resolve but throw at registration

The register above is **compile-CAUGHT**: a deleted public symbol no longer resolves, so the call site is an unresolved-symbol error the compiler names — march-the-wall finds it. There is a **complementary, opposite-visibility** class: public v1 symbols that re-frame2 **retired but kept as facade-exported `^:no-doc` throwing stubs**. The var still *resolves* (the compiler stays silent — no undeclared-var), and it throws its always-on hard error **only when called at registration (boot)**. The compile passes clean; the failure is a runtime throw at first namespace load. The two classes are a **pair** — same "removed v1 API", opposite detector:

| Class | The retired var… | Compiler | Detector |
|---|---|---|---|
| **Compile-CAUGHT** (deleted symbol) | does **not** resolve | names the unresolved symbol | march-the-wall (compile *is* the to-do list) |
| **Compile-SILENT** (throwing stub) | resolves, then throws when called | says **nothing** | static pre-boot grep **+** the boot smoke-test |

The headline members are the **retired event registrars** — `reg-event-db` / `reg-event-fx` / `reg-event-ctx`, collapsed into the one `reg-event` under EP-0018 ([M-73](#required-m-rules-by-trigger-surface)). Each survives as a `^:no-doc` facade stub that throws its always-on naming hard error the instant it is **called at registration**:

| Retired symbol (v1) | Throws at registration | Replacement |
|---|---|---|
| `reg-event-db` | `:rf.error/reg-event-db-removed` (names `reg-event`; shows the two-line conversion — destructure `:db` from the coeffects map, wrap the return `{:db …}`) | `reg-event` |
| `reg-event-fx` | `:rf.error/reg-event-fx-removed` (`reg-event` is the identical shape under the bare name) | `reg-event` |
| `reg-event-ctx` | `:rf.error/reg-event-ctx-removed` (names `reg-interceptor` — register a `context -> context` interceptor, reference it by id from a `reg-event` chain) | `reg-interceptor` (referenced by id) |

The throw is **`:no-recovery`** — the call is rejected, the handler is **not** registered, and (like M-70's chain-shape throws) it **aborts the rest of that namespace's load**, so a boot machine's `reg-machine` after it never registers and the app hangs at boot. Because a v1 app calls these at the top of nearly **every** event namespace, this is the compile-silent class with the **widest blast radius** — an app can compile 0-error / 0-warning and then throw in many namespaces at first load.

**Find them WITHOUT a runtime — the static pre-boot grep:**

```bash
# Every retired-registrar call site. A hit that is still reg-event-(db|fx|ctx),
# not yet reg-event, is a boot-time :rf.error/reg-event-*-removed throw.
rg -n '\(rf/reg-event-(db|fx|ctx)\b' src
```

The grep is the cheap up-front detector (the same shape M-70 uses for interceptor-chain shapes); the [boot smoke-test](runtime-smoke-test.md) is the runtime backstop that surfaces any survivor's throw on the console. Both are needed because the compile gate, by construction, sees neither. This is the **loud-at-runtime / not-loud-at-compile** shape — the same family as **M-70** and **M-15b** in the failure-visibility axis below; it is *not* a silent-fail row (it throws), but the compile is silent about it just the same.

## Failure-visibility axis — loud-fail vs silent-fail (orthogonal to Type A/B)

Type A/B answers *"auto-apply or ask?"*. This second axis answers a **different** question — *"if I miss this rule, will anything tell me?"* — and it drives **how you sweep**, not whether you ask. The two axes are independent: a rule can be Type A loud (M-1 off-contract ns), Type A silent (M-8 fold), Type B loud (M-3 run-to-completion → an exception you'll hit; M-15b → a `:rf/runtime`-bearing `:db` hard-errors), or Type B silent (M-71 signal-fn → a `nil`-yielding sub).

- **LOUD-fail rules** surface at **compile or first-run** — removed namespaces, `console`/`unwrap` add-on refs, undefined vars, unresolved renamed symbols. **March-the-wall works**: swap the coord, compile, fix the error the compiler points at, recompile, repeat. The compile *is* the to-do list. The default M-rule population is loud.
- **SILENT-fail rules** compile **clean** and misbehave only when a specific runtime path executes. March-the-wall **cannot find them** — the compile never gives you a wall to hit. Evidence: a real migration compiled with zero errors then had five-plus runtime breaks, most silent (see [`runtime-smoke-test.md`](runtime-smoke-test.md)).

**The silent-fail register (the planning column — these are the rules that need different handling):**

| Rule | Silent because | The miss looks like |
|---|---|---|
| **M-8** | v2 reads **only** `:db` + `:fx` at the effect-map top level; any other top-level key (`:dispatch`, `:dispatch-n`, a custom fx id) is silently ignored, not errored | the side-effect that key drove never fires; no error |
| **M-16a** | a missed `^:flush-dom` metadata key in an effect map is simply ignored — the synchronous-flush timing silently changes. **Also** a wrong-key rewrite: `:dispatch-later {:ms 0 :dispatch …}` (the v1 key) compiles + runs but the fx reads `:event` — the dispatch never fires | a render that depended on the pre-flush no longer flushes; or (wrong-key) the deferred event silently never dispatches — intermittent visual/timing glitch |
| **M-16b** | distinct from M-16a — a top-level `(rf/dispatch ^:flush-dom …)` ported to `(rf/dispatch-later …)` is **loud, not silent**: `dispatch-later` is fx-id-only, not a fn, so the form **throws at runtime** (resolves to `nil` / arity error). It compiles clean (CLJS doesn't arity-check), so march-the-wall misses it; the boot smoke-test surfaces the throw | the boot/callback dispatch throws instead of firing — a hard error at first page-load, not a silent miss |
| **M-51** | a unary `reg-fx` handler `(fn [args] …)` parses fine; v2 invokes every fx with **two** args, so on CLJS (no arity check) the runtime's context-map binds to `args` and the **real fx args are silently dropped** — the handler runs against the wrong value, no error (on JVM it throws an ArityException — loud — but v1 migration targets are CLJS) | the fx fires but reads garbage (the ctx-map) instead of its args; the side effect mis-behaves or no-ops with no error |
| **M-71** (signal-fn) | the v1 two-function `reg-sub` form parses fine and **registers as a parametric sub**; the live-reaction return is only rejected at **first materialization** (first subscribe/deref), not at registration / ns-load and not at compile | the sub registers cleanly, then the first deref throws `:rf.error/sub-input-fn-bad-return` (the `input-fn` returned reactions, not a vector of query vectors); views that catch/ignore see no value |
| **M-28 / M-29 / M-30 / M-31 / M-32** | the call site resolves through the `re-frame.core` re-export even when the per-feature artefact dep + its `:require` are absent | first dispatch to the surface throws `:rf.error/<artefact>-missing` (machine events silent-no-op) — M-31's `re-frame.http` vs `re-frame.http.managed` two-require trap is the classic |
| **M-54** | the dual-key `(or :schema :spec)` read was stripped — a leftover `:spec` slot is **silently ignored**, so a partial `:spec`→`:schema` rewrite is a correctness hazard | the schema the `:spec` slot named stops validating; no error |

> **M-51's second silent hazard — external direct callers (cross-file caller check).** A converted fx handler frequently *doubles* as a plain-fn API called directly from OTHER files: the common pattern is a util/logging fn (`log!`, `track!`) registered as an fx **and** invoked directly as a unary `(log! req)` by N other namespaces. Mechanically re-arity-ing the fn itself to the binary `(fn [_ args] …)` shape silently breaks every external direct caller — each now passes its real argument into the ignored first slot (CLJS does not arity-check), so the call no-ops or misbehaves with no error. **Check for cross-file callers first:** before re-arity-ing (or otherwise changing) a converted handler's signature, grep for callers OUTSIDE its own file; if it is such a dual-purpose fn, PRESERVE the external signature by WRAPPING the fx around the existing fn — `(rf/reg-fx :id (fn [_ req] (existing-fn req)))` — rather than changing the fn's arity. The same caution applies to any rule that changes a public fn/fx signature (e.g. an O-17 fx re-registration).

> **M-70 left this register (the registration guard landed and the positional vector was retired).** Bare interceptors used to be silently dropped, and old vector-chain shapes used to be accepted. They are now **LOUD-at-runtime**: `reg-event-*` throws `:rf.error/reg-event-bare-interceptor`, `:rf.error/reg-event-bad-middle-slot`, or `:rf.error/reg-event-bad-arity` at registration / ns-load. **But it is *not* loud-at-compile** — the compile still passes; the throw fires only at first page-load, aborting the offending ns's load (and everything after it — a boot machine's `reg-machine` never registers, the app hangs). So march-the-wall (compile) still cannot find it; the **boot smoke-test** ([`runtime-smoke-test.md`](runtime-smoke-test.md)) catches it instantly via the console error. The detector is the same as the silent-fail rules' (a **structural up-front grep**, see M-70), but the failure mode is loud-at-runtime, not silent — which is why M-70 is no longer a silent-fail row.

> **M-15b also left this register (the partition split landed).** The wholesale-replace clobber it described is **structurally gone** — framework runtime moved to a separate runtime-db partition a `:db` return cannot touch. What remains is **LOUD-at-runtime**: a `:db` carrying the retired `:rf/runtime` app-db root throws `:rf.error/legacy-runtime-root` (always-on). Like M-70 it is *not* loud-at-compile — the throw fires at event-dispatch; the boot smoke-test / a structural grep for handlers writing `:rf/runtime` catches it.

**Everything not in this register is loud** — it announces itself at compile or first-run, so march-the-wall is the right tool for it. The two exceptions are **M-70** and **M-15b** (loud-at-*runtime*-only, per the notes just above): the structural grep + boot smoke-test, not march-the-wall.

**Three disciplines follow from the axis:**

1. **Silent-fail rules get an EXHAUSTIVE up-front grep, never march-the-wall.** Grep every site in one pass *before* the sweep — the compile will not surface a second occurrence after you fix the first. (Loud rules can ride the march-the-wall loop; silent ones cannot.)
2. **The inventory phase (Phase 0a) greps the APP source for these patterns**, not only the dependency surfaces. Silent-fail patterns (top-level `:dispatch` keys, signal-fn `reg-sub`, `^:flush-dom`, unary `reg-fx` handlers) — plus the loud-at-runtime-only ones (handlers writing a `:rf/runtime` app-db root, event interceptor-chain shape errors) — live in **application code** and won't show up in a dependency scan.
3. **The runtime smoke-test with live introspection is a first-class gate** ([`runtime-smoke-test.md`](runtime-smoke-test.md)) — for silent-fail rules it is the **only** detector. Reading the booted app's `app-db` + machine snapshots is what confirms the rewrite actually landed; the compiler structurally cannot.

This axis is the organizing insight behind the Phase 4 silent-failure checklist — see [`runtime-smoke-test.md`](runtime-smoke-test.md) for the symptom→cite→confirming-read checklist and the boot smoke-test loop.

## M-30 also carries the flow-map conversion

**M-30 is two halves, not one — hence the table row's `A/B`.** The **Type A** half is the artefact-add (`day8/re-frame2-flows` + `(:require [re-frame.flows])`); [MIGRATION.md §M-30](../../../migration/from-re-frame-v1/README.md#m-30-flows-spec-013-ships-in-a-separate-artefact--day8re-frame2-flows) is the authority for that dep-add and its late-bind require. But the dep-add alone does **not** make a v1 flow run on v2: the **flow-map shape changed**, so a literal v1 `(reg-flow {…})` site is not a no-op.

**Triage FIRST — is this v1 flow even a v2 flow?** The shape rewrite below assumes the answer is *yes*; for a large fraction of v1 flows it is **no**, and converting them mechanically ships the wrong primitive. A v2 flow is a **keyword-id singleton** materialising to **one `app-db` output path** and consumed by **everything** — event handlers, other flows, schemas, the SSR payload. Per [`spec/013-Flows.md` §When (and when not) to use a flow](../../../spec/013-Flows.md#when-and-when-not-to-use-a-flow) and [§What flows are NOT](../../../spec/013-Flows.md#what-flows-are-not), that singleton shape is the *only* thing a flow is for; a v1 flow that does not fit it is a **subscription** in v2, not a flow. Classify each `reg-flow` site **before** any shape rewrite:

- **Consumed only by views** → a **`reg-sub`**, not a flow. spec/013 §When-(and-when-not) is explicit — *"consumed only by views → use a subscription"* (lighter, sub-cache native, no `app-db` write); §What-flows-are-NOT draws the same line — *"view rendering only → use a sub."* This mis-conversion is **silent**: it parses, compiles, and boots, so nothing flags it — the value just parks in `app-db`, paying a write per recompute, where a sub belonged. (spec/013's *"tens of flows is a smell"* is usually exactly this misclassification at scale.)
- **Per-instance / parameterized** — the derivation is keyed by a runtime argument (one value *per id*, the v1 author addressed the flow by a computed/arg-keyed identity) → a **parameterized `reg-sub`** with a vector query (`[::the-sub args]`), not a flow. A flow has **one** output path and **one** keyword identity; it cannot carry a per-instance, arg-keyed family. Mechanical conversion here is a **hard runtime failure**: a runtime-arg-keyed / vector `:id` run through the M-30 shape rewrite throws **`:rf.error/flow-bad-id`** at registration — `reg-flow` rejects a non-keyword `:id` (the public FlowMeta schema requires `[:id :keyword]`, and the `:flow-id` slot is emitted unchanged into `:rf.flow/*` trace + error payloads). Like M-70 / M-73 the throw is **loud-at-runtime, not loud-at-compile**, and it **aborts the rest of that namespace's load** (later `reg-*` in the ns never register → the app hangs at boot) — so a boot-without-throwing smoke can miss it when the offending ns isn't loaded.

**Only a genuine app-STATE singleton takes the M-30 shape conversion below** — a keyword id, one `:output-path`, read by handlers / other flows / schemas / SSR (not by views alone), worth surviving SSR hydration + time-travel revert + `app-db` serialisation. Everything else is a sub (parameterized when it was arg-keyed). This is the same **classify-then-route** discipline the skill already applies to `reg-sub-raw` (M-18's four bodies → sub / fx-driven / machine / anti-pattern) and to the v1 signal-fn (M-71's three return shapes): decide *the right v2 primitive* per site, **before** the mechanical rewrite.

The authoritative v1→v2 mapping table — for a flow that survives the triage — is [`spec/013-Flows.md` §Migration from v1 alpha flows](../../../spec/013-Flows.md#migration-from-v1-alpha-flows) — read it for the exact rows. The summary here is the *shape*, not a restatement:

- **Mechanical key renames (Type A):** `:output` → `:derive` (a fn of *positional* inputs, not a resolved-inputs map); `:path` → `:output-path`; `:inputs` **map → vector** of paths (map-keyed `flow<-` inputs collapse to plain `:output-path` refs — the topological sort orders dependencies automatically). The unprefixed `:reg-flow` / `:clear-flow` fx-ids become `:rf.fx/reg-flow` / `:rf.fx/clear-flow`; `flow<-` / `get-flow` are gone.
- **Dropped / re-homed v1 keys (the judgment-bearing, Type B part):**
  - `:live?` / `:live-inputs` — **dropped.** Re-home as a **wrapping event-handler** that calls `:rf.fx/clear-flow` when the predicate flips false (and `:rf.fx/reg-flow` to toggle back on). Authoring that predicate handler is intent static analysis can't recover — flag it for human review.
  - `:cleanup` — **dropped.** Teardown is now always a `dissoc-in` on `:output-path` (no opt-out); copy the value elsewhere first if it must survive the clear.
  - per-flow `:fx` — **dropped.** Dispatch a follow-up event whose handler reads the flow's output and emits the effect.

So M-30's Type column is **A/B**: the dep-add is automatic, but the `:live?` re-home (and any per-flow `:fx` → follow-up-event rewrite) is a judgment call — present it for human review like the other Type-B rules, citing **M-30** plus the spec/013 table.

## What stays the same (do not change)

[`MIGRATION.md`](../../../migration/from-re-frame-v1/README.md) has a fully-enumerated *"What stays the same"* section near the end of Part 1. The headline non-changes:

- `reg-fx` / `reg-cofx` direct invocation — same names, same call shapes. **The event registrars are the carve-out:** `reg-event-db` / `reg-event-fx` / `reg-event-ctx` are **not** preserved — they collapse to one public form, **`reg-event`**, per **M-73** (codemod-handled for the mechanical cases).
- `reg-sub` direct invocation — same name, but the preserved v1 shapes are the layer-1 `(fn [db q])` and static `:<-` chains. The v1 **two-function signal-function form** `(reg-sub :id signal-fn computation-fn)` is **not preserved as-is**: the first fn is now a v2 **`input-fn`** that returns a **vector of query vectors** (data), not live `subscribe` reactions. Treat every signal-fn site as **M-71** Type B (vector / map / single-signal return shapes each rewrite differently; an `app-db`-reading signal fn must thread the parameter through the outer query vector). `reg-sub-raw` removal is the separate **M-18**.
- Handler signatures: the one v2 event handler is `(fn [coeffects event-vec] ...)` returning a closed effects map (the former `reg-event-fx` shape); the v1 `reg-event-db` `(fn [db [_ args]] ...)` shape migrates to it under **M-73**.
- `dispatch` / `dispatch-sync` (optional second `opts` arg is additive).
- `subscribe`; `@(subscribe [...])` deref-to-read pattern. **In-handler carve-out:** an `@(subscribe …)` deref *inside* a `reg-event` handler reads from app-db, which the handler already holds as the `:db` coeffect — recompute the value from `:db` rather than deref a sub in the fold; see [`causal-world-inputs.md` §source triage](causal-world-inputs.md#triage-in-handler-reads-by-source).
- `:<-` chained subs stay the same — the **static** `:<-` chain and the layer-1 fn-tail. **The `:->` / `:=>` flat-sub `reg-sub` sugar variants do NOT stay the same — they are REMOVED:** v2's `reg-sub` parser accepts only `:<-` chains, the two-fn parametric form, and a single trailing computation fn, so a `(reg-sub :id :-> f)` / `:=>` site throws `:rf.error/reg-sub-bad-args` at registration (loud-at-load, aborts the ns — same blast-radius class as M-70 / M-73). Desugar each to the explicit computation fn — see [`auto-call-site-rewrites.md` §reg-sub flat-sub sugar removed](auto-call-site-rewrites.md#reg-sub-flat-sub-sugar-removed). The dynamic two-function signal-function form is the *other* carve-out: see the `reg-sub` line above.
- Path focusing and full-context interceptor authoring — but **not** the v1 surface. Under EP-0022 there is no public `rf/path` value constructor (use the standard `[:rf.interceptor/path [...]]` ref in a `:interceptors` chain), and `->interceptor` is internal-only (author with `reg-interceptor`, reference by id — chains are reference-only). **v1's `unwrap` migrates to handler destructuring or a project-registered interceptor.** The framework ships an `unwrap-interceptor` interceptor **value** (the same `[<id> <payload-map>]` shape-assertion behaviour; the `:unwrap` interceptor `:id` is unchanged), but it is **not** a standard built-in chain entry (EP-0022 §No standard `unwrap`) and, like every interceptor under EP-0022, can never appear inline in a chain. A `unwrap`-using v1 handler is already at the M-19 canonical dispatch shape, so the simplest v2 destination is plain **handler destructuring** — `(fn [_ {:keys [a b]}] ...)` — with no interceptor at all; a project that genuinely wants chain-wide event reshaping registers the shipped value once and references it by id (`(reg-interceptor :app/unwrap unwrap-interceptor)` → `{:interceptors [:app/unwrap]}`). The bare `unwrap` → `unwrap-interceptor` Var rename in **M-59** is the *pre-rename* upgrade path, not the v1→v2 path. **`inject-cofx` is NOT preserved** — EP-0017 removed it (`:rf.error/inject-cofx-removed`); coeffect delivery is the `:rf.cofx/requires` registration declaration. See **M-72** and [`causal-world-inputs.md`](causal-world-inputs.md).
- The `:fx` slot in effect maps (the inner shape `[[fx-id args] ...]`).
- `reg-fx` without `:platforms` (defaults to universal). **`reg-cofx` is preserved as a surface but its CONTRACT changed (EP-0017):** the supplier is **value-returning** (`(fn [] value)` / `(fn [arg] value)`), not the v1 ctx→ctx shape, and a cofx whose host-read value lands in durable state must be a recorded fact — see **M-72** / [`causal-world-inputs.md`](causal-world-inputs.md).
- `reg-flow` / `clear-flow` — the **surface** is preserved (the `re-frame.core` symbols stay; underlying impl ships under `re-frame2-flows`). **But a literal v1 `(reg-flow {…})` site is NOT a no-op:** the v1→v2 flow-map **shape** changed (`:output`→`:derive`, `:path`→`:output-path`, `:inputs` map→vector) and several v1 keys are dropped/re-homed (`:live?` / `:live-inputs`, `:cleanup`, per-flow `:fx`, the unprefixed `:reg-flow` / `:clear-flow` fx-ids). Treat every `reg-flow` site under **M-30** — the artefact-add is mechanical, the `:live?` re-home is judgment-bearing; see [§M-30 also carries the flow-map conversion](#m-30-also-carries-the-flow-map-conversion) and the authoritative [`spec/013-Flows.md` §Migration from v1 alpha flows](../../../spec/013-Flows.md#migration-from-v1-alpha-flows). (v1's `flow<-` / `get-flow` are dropped — there is no `flow<-` surface in v2; `flow<-` inputs collapse to plain `:output-path` refs.)
- `re-frame.std-interceptors` namespace.
- JVM interop layer (`re-frame.interop`).
- Hot-reload semantics on the default frame.

If a usage doesn't match any M-rule in this table AND isn't on the preserved list, **flag it for human review** rather than guessing. The MIGRATION.md preserved list is non-exhaustive; the M-rule list is the authoritative list of breakages.

### Data-classification retirements (v2-pre-rename only)

**A v1→v2 migration reader can skip this — v1 had no data-classification API.** The data-classification redesign replaced the earlier marking-site / frame-annotation models with a **path-based, fail-open** one and **removed** these surfaces. A codebase upgrading between two pre-release v2 builds rewrites them as:

- `rf/add-marks` / `rf/set-marks` / `rf/clear-app-db-marks!` (imperative per-frame app-db path-marks) **and** the frame `:sensitive` / `:large {:app-db …}` durable annotation → return the durable-app-db classification effect from the writing event: `(rf/reg-event :auth/init (fn [{:keys [db]} _] {:db (assoc db :auth {}) :sensitive [[:auth :token]] :large [[:docs :csv-upload]]}))`. The event is app-db's definition site; a `reg-frame` `:sensitive` carrying an `:app-db` block is rejected fail-loud. Wire known-path classification via `:initial-events`.
- `rf/declare-sensitive-header!` / `rf/declare-sensitive-query-param!` (and the `clear-*!` pair) → declare the app-specific carrier NAMES on the managed-HTTP effect's `reg-fx` registration (the transient-payload case): `(rf/reg-fx :rf.http/managed {:carriers {:headers ["X-Honeycomb-Team"] :query-params ["shop_token"]}} h)`. The earlier frame `:sensitive {:http …}` block is also gone — carriers ride the `:rf.http/managed` registration now. Built-in HTTP denylists remain immutable framework defaults the carriers union onto.
- `rf/redact-interceptor` (positional payload-path scrub) → classify the transient payload with registration metadata: `(rf/reg-event :auth/login {:sensitive [[:password] [:totp-code]]} …)`. There is no positional redaction interceptor in the shipped surface.
- schema-attached app-db `:sensitive?` / `:large?` (a route into durable classification) → durable app-db is the `:sensitive` / `:large` classification effects; durable machine `:data` snapshot egress is the **projection-relative `:sensitive` / `:large` declaration on the `reg-machine` definition** (`reg-machine` now DOES take top-level `:sensitive` / `:large` keys). Per-slot `:sensitive?` / `:large?` props **remain** the route for HTTP request `:decode` bodies (transient) and for a schema's own validation-failure-trace redaction — NOT for durable app-db or machine `:data` snapshot egress.
- **all sensitivity propagation** — input → output inheritance through subs / flows, and the `:rf.egress/output-sensitivity` declassification claim → classify the output path directly; nothing propagates. A derived secret is just a classified db path.

The contract is **fail-open**: a path you never classify ships raw (no propagation, no taint).
