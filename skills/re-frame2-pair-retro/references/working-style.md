# Working style — diagnostic posture

The retro's *what* (the deliverable shape — findings, root-cause classification, 2-5 improvement ideas) is governed by the workflow in [`SKILL.md`](../SKILL.md) and the shared [`../../shared/retro-protocol.md`](../../shared/retro-protocol.md). The rules below govern the *how* — the diagnostic posture the AI holds while conducting the retro conversation. They lock the skill against degenerating into vibes-driven editorialising or reflexive solutionism. Apply them **per finding**.

- **Evidence over vibes.** Cite concrete moments: retries, clarifications, fallbacks to lower-level tools, stale outputs, empty outputs, waits, manual workarounds. *"That was annoying"* with no evidence trail is not actionable — name the turn, the command, the result.
- **Symptom vs cause.** *"We had to retry the attach three times"* is the symptom; *"discovery was brittle on this platform"* is the likely cause. Name both; the improvement idea (and any filed GitHub issue) targets the cause, not the symptom.
- **Direct and indirect friction.** Direct = the user says something was frustrating. Indirect = repeated commands, repeated explanations, fallback to lower-level tools, manual reconstruction, hidden prerequisites, partial results, confusing contracts. Both count as evidence.
- **Positive gaps too.** What almost worked? What required too much expert knowledge? What capability existed but was undiscoverable? What should have been the default? Negative-space evidence is as load-bearing as failure evidence.
- **Be creatively ambitious — but only after diagnosis.** Start with grounded fixes; then ask what would make this workflow feel nearly automatic or hard to misuse. Include 1-2 higher-upside ideas when warranted, even if they reshape the workflow rather than patch a local symptom. Keep them in the separate `Bolder ideas` output section so the user can triage them differently. Bolder is not vague: even a speculative idea needs a concrete change and a believable path to value.
