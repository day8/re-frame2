# Tool-Pair surfaces — shared enumeration

The canonical list of the **consumer-facing Tool-Pair surfaces** re-frame2 exposes to tools (pair, pair-retro, Xray, …). This is the single home for the surface enumeration that several skills otherwise restate from memory and let drift out of sync. The authoritative contract is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md); this leaf is the skills-corpus pointer at it, not a second source of truth.

When a finding routes **upstream to `re-frame2`** (the friction is in the framework's Tool-Pair contract, not the consuming tool or the author's code), name the specific surface here rather than gesturing at "the contract."

## The surfaces

- **The trace stream** — `re-frame.trace.tooling/register-listener!` registers a listener over the live trace-event bus; `trace-buffer` is the retain-N replay buffer. The default multi-tool posture is parallel listeners under distinct ids (per [`spec/009-Instrumentation.md`](../../spec/009-Instrumentation.md) §Listener ordering).
- **The registrar query API** — introspect what is registered: `registrations`, `handler-meta`, `handler-ids`, `frame-ids`, `frame-meta`, `frame-generation`, `machines`, `machine-meta`, `app-schemas`, `sub-cache`. (See [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md) and [`spec/002-Frames.md` §The public registrar query API](../../spec/002-Frames.md#the-public-registrar-query-api).) `sub-cache` is also a **direct value read** — when egressed off-box it carries the fail-closed wire contract under §Direct reads below, not just introspection-metadata semantics. The public address is the **frame** (EP-0023: `image → frame → event stream` — the frame id is the whole public address; there is no public realm coordinate). To read the registrations a *specific live frame* actually resolves, use the **frame-targeted** map form — `(registrations {:frame f :kind k})` / `(handler-meta {:frame f :kind k :id id})` / `(handler-ids {:frame f :kind k})`, resolved through that frame's sealed image generation — and the dedicated whole-generation read `(frame-generation f)`. A registrar-query map **without** `:frame` is an error (`:rf.error/registrar-query-needs-frame`); the retired EP-0013 `:realm` map arity is gone (the `rf/realm-ids` / `rf/frame-realm` facade exports were **removed**, EP-0023 pl97nd.2). The realm/`(realm, frame)` two-part address survives only as **labeled-internal installation substrate**, read from the internal `re-frame.realm` / `re-frame.frame` namespaces (which tooling may require directly), never from the public facade (see the operating-frame trio below).
- **Epoch history + restore** — the per-frame epoch ring buffer `(rf/epoch-history frame-id)`, the assembled-record listener `register-epoch-listener!`, and first-class time-travel `(rf/restore-epoch! frame-id epoch-id)`. `restore-epoch` rewinds the whole **frame-state** to the epoch's `:frame-state-after` — both partitions (app-db AND runtime-db), reinstalled atomically via `replace-frame-state!`, so machine snapshots / the route slice / elision declarations / SSR metadata revive alongside app-db (not the app-db projection alone). Effects already fired and transient host state are not reconstructed.
- **State injection — the four partition-aware mutators** — installing an arbitrary frame value the runtime never recorded, bypassing the dispatch loop (per [`spec/Tool-Pair.md` §Pair-tool writes](../../spec/Tool-Pair.md#pair-tool-writes--state-injection), the four-row table; the canonical API row table is [`spec/API.md` §Epoch history](../../spec/API.md#epoch-history-per-tool-pair)). They supersede the old single `reset-frame-db!`, whose db-shaped name would have silently replaced runtime-db too:
  - `(rf/replace-app-db! frame-id new-db)` — **app-db-only** injection (the direct rename of `reset-frame-db!`); live runtime-db survives.
  - `(rf/reset-app-db! frame-id)` — **app-db reset** to `{}`; live runtime-db survives.
  - `(rf/replace-runtime-db! frame-id runtime-db)` — **runtime-db-only** privileged write (subsystem state: machines / routes / elision / SSR).
  - `(rf/replace-frame-state! frame-id frame-state)` — **full-frame atomic install** of both partitions (`{:rf.db/app … :rf.db/runtime …}`) — the surface story tools and JSON-loaded bug repros use to seed machine snapshots / routes / elision / SSR metadata.
  The db-shaped names (`replace-app-db!` / `reset-app-db!`) **never silently touch runtime-db**; the explicit full-frame surface is `replace-frame-state!`, and it is also what a happy-path `restore-epoch` installs.
- **Schema reflection** — `app-schemas` returns the registered schemas for reflective validation / shape inspection.
- **Source-coord annotation** — `data-rf2-source-coord` bridges live DOM elements back to source `{:ns :line :file}` (with re-com's `data-rc-src` as a fallback).
- **Render driving + dispatch settle** — the optional substrate-adapter fn `flush-render!` synchronously commits pending renders (React `flushSync` / `reagent.core/flush`) so a headless `dispatch → observe-DOM` loop is deterministic even in a backgrounded tab; the framework's commitment is the fn, and the pair MCP's `dispatch` **`:settle`** mode builds on it (dispatch → `flush-render!` → return the settled epoch including its `:rf.view/render` / `:rf.view/unmounted` entries). Adapters with no live commit (plain-atom / SSR) ship no `flush-render!`; the call no-ops. (See [`spec/Tool-Pair.md` §Driving the render](../../spec/Tool-Pair.md#driving-the-render-headless-view-lifecycle) and [`spec/006-ReactiveSubstrate.md` §`flush-render!`](../../spec/006-ReactiveSubstrate.md#flush-render-f--nil).)
- **View-plane reads + view attribution** — the substrate stamps `data-rf-view="<id>"` on every registered view's rendered root (alongside `data-rf2-source-coord`), giving a view-id↔DOM map in both directions: forward (view-id → rendered root) and backward (arbitrary node → nearest `[data-rf-view]` ancestor → producing view). The framework's commitment is **the attributes**; the content-read helpers are tool-side, surfaced in the pair MCP as `read-dom` (query the rendered DOM by CSS selector → matched nodes) and `read-ui` (given a view-id / point / selector → the rendered subtree **plus** the producing re-frame2 entity, source-coord + `:subs-read`, in one round-trip). Read-only by construction. Off-box text egress rides the **same** fail-closed elision posture as direct reads (§Direct reads below). (See [`spec/Tool-Pair.md` §The view→content read](../../spec/Tool-Pair.md#reading-rendered-content--producing-entity--the-viewcontent-read) and [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Signal recorder + blocking watch** — two related but **mechanically distinct** surfaces over the same heterogeneous signal-set (`:app-db` path, `:sub`, `:dom`, `:focus`); the canonical move for intermittent / human-in-the-loop bugs. Do not conflate their contracts — a `watch-until` failure is not a recording-registry / rAF problem.
  - **`record` / `read-recording`** — the **background rAF recorder**. `record` installs a read-only `requestAnimationFrame` observer (falling back to `next-tick` on a rAF-absent headless / SSR target) and **returns immediately** with a `:recording-id`; the runtime samples once per animation frame and logs each **deduped** change (a steady signal yields one baseline entry) into a registry-held change log until a stop condition (`:ms` / `:changes` / `:pred`), then **tears itself down**. `read-recording` reads back / drains / stops that change log by its `:recording-id`. This is the rAF/dedup/teardown half — the browser-side recording machinery.
  - **`watch-until`** — the **blocking** counterpart, and it does **not** use the rAF recorder. The MCP **server polls** a cheap runtime read on a fixed cadence (~100 ms) — **no rAF loop, no browser-side mailbox, no recording registry / `:recording-id`** — evaluating a data predicate (`:equals` / `:changed` / `:contains` / `:path` …) over the signal-set server-side until it holds or `timeout-ms` (default 30000) elapses. It returns the held `:sample` on success, or the `:last-sample` on timeout (timeout is the normal terminal outcome, not a tool fault). Same polling shape as `tail-build`, not the `record` change-log path.

  Both are read-only by construction — **but read-only is not the same as egress-safe**: the recorded samples (`record`) and the returned `:sample` / `:last-sample` (`watch-until`) are value egress, so the `:app-db` / `:sub` values are run through `rf/elide-wire-value` before entering the change log / crossing the wire, under the same fail-closed posture as the one-shot direct reads (§Direct reads below). (See [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Operating-frame trio** — `set-operating-frame` / `reset-operating-frame` / `get-operating-frame` pin / clear / inspect a multi-frame session's operating frame so frame-targeted ops resolve without a per-call `:frame`. Required when a multi-app session would otherwise refuse with `{:ok? false :reason :ambiguous-frame}`. **The public address is the frame** ([EP-0023](../../docs/EP/EP-0023-image-loaded-frames.md) §Public API: `image → frame → event stream` — the frame id is the whole public address, with no realm dimension and no public realm pin): the resolver walks explicit override → session pin → **sole-registered app frame** → nil, reserved-frame-aware. The earlier EP-0013 `(realm, frame)` two-part address is **retained only as the labeled-internal installation substrate** that seats and routes frames (the container owning the registrar / adapter / capabilities), not the public model. In a multi-container installation a frame id is unique only *within* its container, so tier-3 sole-app-frame resolution counts only the **operating container's** app frames — two app frames in *different* containers are **not** ambiguous; two in the *same* container stay ambiguous.
  - `set-operating-frame` pins a **frame**; there is no public realm pin.
  - `reset-operating-frame` clears the frame pin (it also clears the runtime's internal installation-container pin) — ops fall back to tier 3 / 4 again.
  - `get-operating-frame` (inspect) surfaces the frame view, and MAY carry the **labeled-internal installation boundary** alongside it: `:realms` (the internal installation-container ids), `:operating-realm` (the container tier-3 scopes to), and `:frame-realms` (`{<frame-id> <container-id>}`). A tool reads these from the **internal** `re-frame.realm` / `re-frame.frame` namespaces (which tooling may require directly), **not** the public facade — the EP-0013 `rf/realm-ids` / `rf/frame-realm` facade exports were removed (pl97nd.2). There is no public realm pin, so `:selected-realm` is always nil — it MUST be labeled as internal structure, not the central model.

  A **single-container application** — the overwhelming common case, every frame in `:rf.realm/default` — reports `:realms [:rf.realm/default]`, every frame's container as the default, and the installation boundary collapses to a no-op (byte-identical to the pre-realm ladder). Single-frame apps never reach the refusal path. (See [`spec/Tool-Pair.md` §Operating frame](../../spec/Tool-Pair.md#operating-frame--multi-frame-resolution) and §Tool-surface obligations.)
- **Direct reads (`app-db` / `sub-cache` / run a sub)** — two layers, kept distinct.
  - **Framework primitives** (the raw runtime reads): `(rf/app-db-value frame-id)` reads a frame's current `app-db` value, `(re-frame.subs.tooling/sub-cache-snapshot frame-id)` (alias `subs/sub-cache-snapshot`) reads the cached-sub map, `(rf/compute-sub query-v db-value)` runs a sub against a db value. These are the surfaces the spec's MUST contract is written against — a third-party server shipping any direct-read surface inherits the posture by these primitive names.
  - **Current re-frame2-pair-mcp tool names** — the actual wire surfaces that egress live state off-box to an AI/MCP client. They fall into **distinct privacy-relevant categories**, not one flat "current set"; each routes its value(s) through a normative emission site server-side under the fail-closed posture below. **There is no standalone `get-app-db` / `sub-cache` tool** in the current catalogue — `get-app-db` survives only as a *generic / third-party* direct-read class name (a server that ships one inherits the same MUST), and the sub-cache is reached via `snapshot :sub-cache` + `list-subscriptions`. Always check the consuming tool's catalogue ([`re-frame2-pair-mcp/README.md` §Tool surface + §sensitive-reads gate](../../tools/re-frame2-pair-mcp/README.md) for the reference server) before naming a wire surface; the spec is the contract, the catalogue is the current shipped name. The categories:
    - **App-db / sub one-shot reads** — `snapshot` (wraps both `:app-db` and `:sub-cache`), `get-path` (one `get-in` at a path), `read-sub` (a validated one-shot subscription deref), `list-subscriptions` (the reactive sub-cache; `:include-values true` ships each `:value`). Each routes its returned value(s) through `rf/elide-wire-value` (the direct-value emission site).
    - **Epoch / trace streaming reads** — `trace-window` (the recent epoch-record window) and `watch-epochs` (poll-mode epoch matches) project egressed epoch records through `re-frame.core/projected-record`; the `subscribe` streaming tool forces server-side `elide-wire-value` on streamed event / cascade values when the gate is off. These are off-box reads under the **same** default-off gate as the one-shot reads — not outside the fail-closed boundary.
    - **Signal recorder reads** — `record` / `read-recording` / `watch-until` (see §Signal recorder above): read-only, but the recorded samples are elided via `elide-wire-value` before they enter the change log.
    - **View-plane reads** — `read-dom` / `read-ui` (see §View-plane reads above): rendered-content text egress under the same fail-closed elision posture.
    - **Simulated / dry-run egress** — `dispatch-dry-run` mutates nothing, but its `:db-state-after-simulation` (the would-be app-db) and `:would-fire-effects[*].args` (fx-derived data) are app-db-derived egress, gated by the same posture.

> **Off-box read egress is fail-closed (MUST).** Direct reads bypass the trace surface where `:sensitive?` stamping operates, so any pair-shaped tool that egresses a value-bearing read surface off-box **MUST** scrub it before it crosses the wire — the owner-declared classification (frame `:sensitive {:app-db}`, per-slot schema props, registration `:sensitive` metadata; per EP-0015) is projected at this boundary, not at a handler interceptor. The covered surfaces span the categories above — the one-shot direct reads `snapshot` / `get-path` / `read-sub` / `list-subscriptions` (`:include-values`), the streaming reads `subscribe` / `trace-window` / `watch-epochs`, the signal recorder `record` / `read-recording`, the view-plane reads `read-dom` / `read-ui`, the simulated `dispatch-dry-run`, and a third-party `get-app-db` / `sub-cache` surface. The **emission site depends on the value shape**: direct values, recorded samples, and dry-run / sub `:value` slots route through `rf/elide-wire-value` (the single normative direct-value emission site); egressed **epoch records** route through `re-frame.core/projected-record` (the epoch-record emission site, idempotent under `:rf/redacted`); view-plane text rides the same elision posture. The AI/MCP boundary — not `app-db` itself — is the trust boundary. Off-box defaults are **suppress-by-default**: `:rf.size/include-sensitive?` and `:rf.size/include-large?` both default `false`, so a sensitive slot returns `:rf/redacted` and an oversize value returns `:rf.size/large-elided`; when both match, **sensitive drop wins** (the size marker would leak `:path` / `:bytes` / `:digest`). Re-enabling is opt-in only: the cross-MCP boot gate `--allow-sensitive-reads` (default **OFF**) plus the per-call `include-sensitive` arg. Dropped values surface as the `:dropped-sensitive` / `:elided-large` indicators. The walker runs **app-side** (it reads the frame's `[:rf.runtime/elision …]` registries — durable **runtime-db** partition state per EP-0001, not the retired app-db `:rf/runtime` root), never in the MCP host. Full contract for the elide-wire-value egress MUST: [`spec/Tool-Pair.md` §Direct-read privacy posture for `sub-cache` and `get-path`](../../spec/Tool-Pair.md#direct-read-privacy-posture-for-sub-cache-and-get-path) (and the security framing in [`spec/Security.md` §Direct-read privacy posture](../../spec/Security.md#direct-read-privacy-posture-for-sub-cache-and-get-path)). The per-server `--allow-sensitive-reads` boot gate itself is not defined in those spec sections — its authoritative home is the cross-MCP catalogue ([`spec/Conventions.md` §Cross-MCP indicator-field vocabulary](../../spec/Conventions.md#cross-mcp-indicator-field-vocabulary-suppression-counters)) plus the conformance pins under [`tools/mcp-conformance/`](../../tools/mcp-conformance/) and each MCP server's tool catalogue.

The **current upstream-routing surface families** are exactly the ones above — trace stream, registrar query API, epoch-history / restore, state injection (the four partition-aware mutators), schema reflection, source-coord annotation, direct reads, render-driving / dispatch-settle, view-plane reads / view attribution, signal recorder, and the operating-frame trio. When a finding routes upstream, name the matching family from this list. Earlier versions of this leaf advertised only an abbreviated five-name subset (`register-listener!`, `register-epoch-listener!`, `epoch-history`, `restore-epoch`, `app-schemas` plus source-coord annotation); that subset omitted render-driving / settle, view-plane reads, the signal recorder, and the operating-frame trio, so a finding about deterministic `dispatch → settle → DOM`, `read-ui` / `read-dom` provenance, human-interaction recording, or multi-frame operating-frame ambiguity could be mislabeled as pair-tool friction and filed against the wrong layer. The fullest *tool-side* list lives in [`re-frame2-pair/README.md`](../re-frame2-pair/README.md); the authoritative *framework contract* is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md).

## Availability tiers

Naming the right surface is half the routing decision; the other half is its **availability** — a surface can be *named correctly* and still be the wrong thing to reach for under a given build / host. A flat catalogue silently teaches that every surface answers everywhere. It does not. Four orthogonal axes gate availability; a surface can sit on more than one. This matrix is a pointer at the authoritative tiers in [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md) — it does not redefine them. When you route a finding, check the tier so you don't (a) treat an absent epoch artefact like a broken pair tool, (b) assume `sub-cache` is portable to a JVM/SSR host, (c) expect `data-rf-view` / source-coord in a production build, or (d) abandon a usable production probe because the flat list hid which surfaces still answer.

The four axes:

- **Dev-gate** — `re-frame.interop/debug-enabled?` (CLJS: alias of `goog.DEBUG`; JVM: `-Dre-frame.debug` / `RE_FRAME_DEBUG`). Production builds (`:advanced` + `goog.DEBUG=false`) elide the whole gated branch via Closure DCE — zero overhead, zero code.
- **Epoch artefact** — ships in `day8/re-frame2-epoch`, required on the classpath (`require re-frame.epoch` at boot) for the time-travel surface; **absent-artefact behaviour splits by surface** (reads degrade to sentinels, writes raise).
- **Host** — CLJS-only vs portable. CLJS-host surfaces have no JVM (SSR / headless / conformance) equivalent.
- **Tool-side capability** — the framework's commitment is an *attribute* or *fn*; the read helper lives tool-side and needs the host to actually provide it (a live DOM for view-plane reads; a substrate `flush-render!` for `:settle`).

**The production-elision split, in one line.** Under `:advanced` + `goog.DEBUG=false` the **dev-gated** surfaces go dark — trace stream, schema reflection / validation, the epoch machinery (history / restore / injection / streaming), and the DOM annotations (`data-rf2-source-coord` / `data-rf-view`, so view-plane reads have an empty map). What **still answers**: the registrar query API (orientation / registry-frame shape), the direct-read primitives (`app-db-value` / `compute-sub` / `sub-cache`, under their own egress posture), the operating-frame trio, and the always-on event-emit and always-on error-emit substrate (`register-event-listener!` / `register-error-listener!`, per [009 §What IS available in production](../../spec/009-Instrumentation.md#production-builds-zero-overhead-zero-code)) — error **recovery** there is the framework's typed per-category default, not an app-steerable `:on-error` policy (that policy was removed). The error-emit listener is the production error-observability surface; SSR error **projection** (`reg-error-projector` / `project-error`) is a distinct SSR-only surface, named only when the host is actually an SSR build. A production-attached session is therefore a *mixed* result — name the dark surfaces as dev-gated, not as a broken tool, and keep using the surfaces that answer. (Pair-retro carries the same split as a consumer-side known-friction; this leaf is the shared home for the model.)

## Supersedes re-frame-10x

These surfaces are **first-class in re-frame2 itself** — v2 tooling does not depend on, recommend, or fall back to `re-frame-10x`. Where v1 tooling read 10x's epoch buffer it now reads `(rf/epoch-history frame-id)`; where it stepped through 10x navigation it now calls `(rf/restore-epoch! frame-id epoch-id)`; where it detected a 10x trace callback it now registers its own listener (multi-tool coexistence is the expected default). Consuming skills may keep their own audience-specific framing of this claim (dependency note / anti-pattern / structural successor / migration mechanics) and cite this paragraph for the underlying fact.
