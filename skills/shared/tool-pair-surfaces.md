# Tool-Pair surfaces — shared enumeration

The canonical list of the **consumer-facing Tool-Pair surfaces** re-frame2 exposes to tools (pair, pair-retro, Xray, …). This is the single home for the surface enumeration that several skills otherwise restate from memory and let drift out of sync. The authoritative contract is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md); this leaf is the skills-corpus pointer at it, not a second source of truth.

When a finding routes **upstream to `re-frame2`** (the friction is in the framework's Tool-Pair contract, not the consuming tool or the author's code), name the specific surface here rather than gesturing at "the contract."

## The surfaces

- **The trace stream** — `re-frame.trace.tooling/register-listener!` registers a listener over the live trace-event bus; `trace-buffer` is the retain-N replay buffer. The default multi-tool posture is parallel listeners under distinct ids (per [`spec/009-Instrumentation.md`](../../spec/009-Instrumentation.md) §Listener ordering).
- **The registrar query API** — introspect what is registered: `registrations`, `handler-meta`, `frame-ids`, `frame-meta`, `machines`, `machine-meta`, `app-schemas`, `sub-cache`. (See [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md) and [`spec/002-Frames.md` §The public registrar query API](../../spec/002-Frames.md#the-public-registrar-query-api).) `sub-cache` is also a **direct value read** — when egressed off-box it carries the fail-closed wire contract under §Direct reads below, not just introspection-metadata semantics.
- **Epoch history + restore** — the per-frame epoch ring buffer `(rf/epoch-history frame-id)`, the assembled-record listener `register-epoch-listener!`, and first-class time-travel `(rf/restore-epoch frame-id epoch-id)`. State injection bypassing the dispatch loop is `(rf/reset-frame-db! frame-id new-db)`.
- **Schema reflection** — `app-schemas` returns the registered schemas for reflective validation / shape inspection.
- **Source-coord annotation** — `data-rf2-source-coord` bridges live DOM elements back to source `{:ns :line :file}` (with re-com's `data-rc-src` as a fallback).
- **Render driving + dispatch settle** — the optional substrate-adapter fn `flush-render!` synchronously commits pending renders (React `flushSync` / `reagent.core/flush`) so a headless `dispatch → observe-DOM` loop is deterministic even in a backgrounded tab; the framework's commitment is the fn, and the pair MCP's `dispatch` **`:settle`** mode builds on it (dispatch → `flush-render!` → return the settled epoch including its `:rf.view/render` / `:rf.view/unmounted` entries). Adapters with no live commit (plain-atom / SSR) ship no `flush-render!`; the call no-ops. (See [`spec/Tool-Pair.md` §Driving the render](../../spec/Tool-Pair.md#driving-the-render-headless-view-lifecycle) and [`spec/006-ReactiveSubstrate.md` §`flush-render!`](../../spec/006-ReactiveSubstrate.md#flush-render-f--nil).)
- **View-plane reads + view attribution** — the substrate stamps `data-rf-view="<id>"` on every registered view's rendered root (alongside `data-rf2-source-coord`), giving a view-id↔DOM map in both directions: forward (view-id → rendered root) and backward (arbitrary node → nearest `[data-rf-view]` ancestor → producing view). The framework's commitment is **the attributes**; the content-read helpers are tool-side, surfaced in the pair MCP as `read-dom` (query the rendered DOM by CSS selector → matched nodes) and `read-ui` (given a view-id / point / selector → the rendered subtree **plus** the producing re-frame2 entity, source-coord + `:subs-read`, in one round-trip). Read-only by construction. Off-box text egress rides the **same** fail-closed elision posture as direct reads (§Direct reads below). (See [`spec/Tool-Pair.md` §The view→content read](../../spec/Tool-Pair.md#reading-rendered-content--producing-entity--the-viewcontent-read) and [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Signal recorder** — the pair MCP triplet `record` / `read-recording` / `watch-until` installs a read-only rAF observer over a heterogeneous signal-set (`:app-db` path, `:sub`, `:dom`, `:focus`): `record` returns immediately with a `:recording-id` and logs each deduped change until a stop condition (`:ms` / `:changes` / `:pred`); `read-recording` reads back / drains / tears down the change-log; `watch-until` is the blocking counterpart (block until a data predicate over the signal-set holds). The canonical move for intermittent / human-in-the-loop bugs. Read-only by construction. (See [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Operating-frame trio** — `set-operating-frame` / `reset-operating-frame` / `get-operating-frame` pin / clear / inspect a multi-frame session's operating frame so frame-targeted ops resolve without a per-call `:frame`. Required when a multi-app session would otherwise refuse with `{:ok? false :reason :ambiguous-frame}` (the resolver walks explicit override → session pin → sole-registered app frame → nil, reserved-frame-aware). Single-frame apps never reach the refusal path. (See [`spec/Tool-Pair.md` §Operating frame](../../spec/Tool-Pair.md#operating-frame).)
- **Direct reads (`app-db` / `sub-cache` / run a sub)** — two layers, kept distinct.
  - **Framework primitives** (the raw runtime reads): `(rf/app-db-value frame-id)` reads a frame's current `app-db` value, `(rf/sub-cache frame-id)` reads the cached-sub map, `(rf/compute-sub query-v db-value)` runs a sub against a db value. These are the surfaces the spec's MUST contract is written against — a third-party server shipping any direct-read surface inherits the posture by these primitive names.
  - **Current re-frame2-pair-mcp tool names** (the actual wire surfaces that egress those primitives off-box to an AI/MCP client): `snapshot` (wraps both `:app-db` and `:sub-cache`), `get-path` (one `get-in` at a path), `read-sub` (a validated one-shot subscription deref), and `list-subscriptions` (the reactive sub-cache; `:include-values true` ships each `:value`). Each routes its returned value(s) through `rf/elide-wire-value` server-side under the fail-closed posture below. `dispatch-dry-run` is also gated by the same posture — its `:db-state-after-simulation` (the would-be app-db) and `:would-fire-effects[*].args` (fx-derived data) are app-db-derived egress even though it mutates nothing. **There is no standalone `get-app-db` / `sub-cache` tool** in the current catalogue — `get-app-db` survives only as a *generic / third-party* direct-read class name (a server that ships one inherits the same MUST), and the sub-cache is reached via `snapshot :sub-cache` + `list-subscriptions`. Always check the consuming tool's catalogue ([`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md) for the reference server) before naming a wire surface; the spec is the contract, the catalogue is the current shipped name.

> **Direct-read egress is fail-closed (MUST).** Direct reads bypass the trace surface where `:sensitive?` stamping / `redact-interceptor` operate, so any pair-shaped tool that egresses a direct-read surface — the current re-frame2-pair-mcp set `snapshot` / `get-path` / `read-sub` / `list-subscriptions` (`:include-values`) / `dispatch-dry-run`, or a third-party `get-app-db` / `sub-cache` surface — off-box **MUST** route the returned value through `rf/elide-wire-value` (the single normative emission site) before it crosses the wire. The AI/MCP boundary — not `app-db` itself — is the trust boundary. Off-box defaults are **suppress-by-default**: `:rf.size/include-sensitive?` and `:rf.size/include-large?` both default `false`, so a sensitive slot returns `:rf/redacted` and an oversize value returns `:rf.size/large-elided`; when both match, **sensitive drop wins** (the size marker would leak `:path` / `:bytes` / `:digest`). Re-enabling is opt-in only: the cross-MCP boot gate `--allow-sensitive-reads` (default **OFF**) plus the per-call `include-sensitive` arg. Dropped values surface as the `:dropped-sensitive` / `:elided-large` indicators. The walker runs **app-side** (it reads the frame's `[:rf/runtime :elision …]` registries), never in the MCP host. Full contract for the elide-wire-value egress MUST: [`spec/Tool-Pair.md` §Direct-read privacy posture for `sub-cache` and `get-path`](../../spec/Tool-Pair.md#direct-read-privacy-posture-for-sub-cache-and-get-path) (and the security framing in [`spec/Security.md` §Direct-read privacy posture](../../spec/Security.md#direct-read-privacy-posture-for-sub-cache-and-get-path)). The per-server `--allow-sensitive-reads` boot gate itself is not defined in those spec sections — its authoritative home is the cross-MCP catalogue ([`spec/Conventions.md` §Cross-MCP indicator-field vocabulary](../../spec/Conventions.md#cross-mcp-indicator-field-vocabulary-suppression-counters)) plus the conformance pins under [`tools/mcp-conformance/`](../../tools/mcp-conformance/) and each MCP server's tool catalogue.

The **current upstream-routing surface families** are exactly the ones above — trace stream, registrar query API, epoch-history / restore, schema reflection, source-coord annotation, direct reads, render-driving / dispatch-settle, view-plane reads / view attribution, signal recorder, and the operating-frame trio. When a finding routes upstream, name the matching family from this list. Earlier versions of this leaf advertised only an abbreviated five-name subset (`register-listener!`, `register-epoch-listener!`, `epoch-history`, `restore-epoch`, `app-schemas` plus source-coord annotation); that subset omitted render-driving / settle, view-plane reads, the signal recorder, and the operating-frame trio, so a finding about deterministic `dispatch → settle → DOM`, `read-ui` / `read-dom` provenance, human-interaction recording, or multi-frame operating-frame ambiguity could be mislabeled as pair-tool friction and filed against the wrong layer. The fullest *tool-side* list lives in [`re-frame2-pair/README.md`](../re-frame2-pair/README.md); the authoritative *framework contract* is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md).

## Supersedes re-frame-10x

These surfaces are **first-class in re-frame2 itself** — v2 tooling does not depend on, recommend, or fall back to `re-frame-10x`. Where v1 tooling read 10x's epoch buffer it now reads `(rf/epoch-history frame-id)`; where it stepped through 10x navigation it now calls `(rf/restore-epoch frame-id epoch-id)`; where it detected a 10x trace callback it now registers its own listener (multi-tool coexistence is the expected default). Consuming skills may keep their own audience-specific framing of this claim (dependency note / anti-pattern / structural successor / migration mechanics) and cite this paragraph for the underlying fact.
