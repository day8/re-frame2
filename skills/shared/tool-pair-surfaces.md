# Tool-Pair surfaces — shared enumeration

The canonical list of the **consumer-facing Tool-Pair surfaces** re-frame2 exposes to tools (pair, pair-retro, Xray, …). This is the single home for the surface enumeration that several skills otherwise restate from memory and let drift out of sync. The authoritative contract is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md); this leaf is the skills-corpus pointer at it, not a second source of truth.

When a finding routes **upstream to `re-frame2`** (the friction is in the framework's Tool-Pair contract, not the consuming tool or the author's code), name the specific surface here rather than gesturing at "the contract."

## The surfaces

- **The trace stream** — `re-frame.trace.tooling/register-listener!` registers a listener over the live trace-event bus; `trace-buffer` is the retain-N replay buffer. The default multi-tool posture is parallel listeners under distinct ids (per [`spec/009-Instrumentation.md`](../../spec/009-Instrumentation.md) §Listener ordering).
- **The registrar query API** — introspect what is registered: `registrations`, `handler-meta`, `frame-ids`, `frame-meta`, `machines`, `machine-meta`, `app-schemas`, `sub-cache`. (See [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md) and [`spec/002-Frames.md` §The public registrar query API](../../spec/002-Frames.md#the-public-registrar-query-api).) `sub-cache` is also a **direct value read** — when egressed off-box it carries the fail-closed wire contract under §Direct reads below, not just introspection-metadata semantics.
- **Epoch history + restore** — the per-frame epoch ring buffer `(rf/epoch-history frame-id)`, the assembled-record listener `register-epoch-listener!`, and first-class time-travel `(rf/restore-epoch frame-id epoch-id)`. `restore-epoch` rewinds the whole **frame-state** to the epoch's `:frame-state-after` — both partitions (app-db AND runtime-db), reinstalled atomically via `replace-frame-state!`, so machine snapshots / the route slice / elision declarations / SSR metadata revive alongside app-db (not the app-db projection alone). Effects already fired and transient host state are not reconstructed.
- **State injection — the four partition-aware mutators** — installing an arbitrary frame value the runtime never recorded, bypassing the dispatch loop (per [`spec/Tool-Pair.md` §Pair-tool writes](../../spec/Tool-Pair.md#pair-tool-writes--state-injection), the four-row table; the canonical API row table is [`spec/API.md` §Epoch history](../../spec/API.md#epoch-history-per-tool-pair)). They supersede the old single `reset-frame-db!`, whose db-shaped name would have silently replaced runtime-db too:
  - `(rf/replace-app-db! frame-id new-db)` — **app-db-only** injection (the direct rename of `reset-frame-db!`); live runtime-db survives.
  - `(rf/reset-app-db! frame-id)` — **app-db reset** to `{}`; live runtime-db survives.
  - `(rf/replace-runtime-db! frame-id runtime-db)` — **runtime-db-only** privileged write (subsystem state: machines / routes / elision / SSR).
  - `(rf/replace-frame-state! frame-id frame-state)` — **full-frame atomic install** of both partitions (`{:rf.db/app … :rf.db/runtime …}`) — the surface story tools and JSON-loaded bug repros use to seed machine snapshots / routes / elision / SSR metadata.
  The db-shaped names (`replace-app-db!` / `reset-app-db!`) **never silently touch runtime-db**; the explicit full-frame surface is `replace-frame-state!`, and it is also what a happy-path `restore-epoch` installs.
- **Schema reflection** — `app-schemas` returns the registered schemas for reflective validation / shape inspection.
- **Source-coord annotation** — `data-rf2-source-coord` bridges live DOM elements back to source `{:ns :line :file}` (with re-com's `data-rc-src` as a fallback).
- **Render driving + dispatch settle** — the optional substrate-adapter fn `flush-render!` synchronously commits pending renders (React `flushSync` / `reagent.core/flush`) so a headless `dispatch → observe-DOM` loop is deterministic even in a backgrounded tab; the framework's commitment is the fn, and the pair MCP's `dispatch` **`:settle`** mode builds on it (dispatch → `flush-render!` → return the settled epoch including its `:rf.view/render` / `:rf.view/unmounted` entries). Adapters with no live commit (plain-atom / SSR) ship no `flush-render!`; the call no-ops. (See [`spec/Tool-Pair.md` §Driving the render](../../spec/Tool-Pair.md#driving-the-render-headless-view-lifecycle) and [`spec/006-ReactiveSubstrate.md` §`flush-render!`](../../spec/006-ReactiveSubstrate.md#flush-render-f--nil).)
- **View-plane reads + view attribution** — the substrate stamps `data-rf-view="<id>"` on every registered view's rendered root (alongside `data-rf2-source-coord`), giving a view-id↔DOM map in both directions: forward (view-id → rendered root) and backward (arbitrary node → nearest `[data-rf-view]` ancestor → producing view). The framework's commitment is **the attributes**; the content-read helpers are tool-side, surfaced in the pair MCP as `read-dom` (query the rendered DOM by CSS selector → matched nodes) and `read-ui` (given a view-id / point / selector → the rendered subtree **plus** the producing re-frame2 entity, source-coord + `:subs-read`, in one round-trip). Read-only by construction. Off-box text egress rides the **same** fail-closed elision posture as direct reads (§Direct reads below). (See [`spec/Tool-Pair.md` §The view→content read](../../spec/Tool-Pair.md#reading-rendered-content--producing-entity--the-viewcontent-read) and [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Signal recorder** — the pair MCP triplet `record` / `read-recording` / `watch-until` installs a read-only rAF observer over a heterogeneous signal-set (`:app-db` path, `:sub`, `:dom`, `:focus`): `record` returns immediately with a `:recording-id` and logs each deduped change until a stop condition (`:ms` / `:changes` / `:pred`); `read-recording` reads back / drains / tears down the change-log; `watch-until` is the blocking counterpart (block until a data predicate over the signal-set holds). The canonical move for intermittent / human-in-the-loop bugs. Read-only by construction — **but read-only is not the same as egress-safe**: the recorded samples are value egress, so they are run through `rf/elide-wire-value` before entering the change log under the same fail-closed posture as the one-shot direct reads (§Direct reads below). (See [`re-frame2-pair-mcp/README.md` §Tool surface](../../tools/re-frame2-pair-mcp/README.md).)
- **Operating-frame trio** — `set-operating-frame` / `reset-operating-frame` / `get-operating-frame` pin / clear / inspect a multi-frame session's operating frame so frame-targeted ops resolve without a per-call `:frame`. Required when a multi-app session would otherwise refuse with `{:ok? false :reason :ambiguous-frame}` (the resolver walks explicit override → session pin → sole-registered app frame → nil, reserved-frame-aware). Single-frame apps never reach the refusal path. (See [`spec/Tool-Pair.md` §Operating frame](../../spec/Tool-Pair.md#operating-frame).)
- **Direct reads (`app-db` / `sub-cache` / run a sub)** — two layers, kept distinct.
  - **Framework primitives** (the raw runtime reads): `(rf/app-db-value frame-id)` reads a frame's current `app-db` value, `(rf/sub-cache frame-id)` reads the cached-sub map, `(rf/compute-sub query-v db-value)` runs a sub against a db value. These are the surfaces the spec's MUST contract is written against — a third-party server shipping any direct-read surface inherits the posture by these primitive names.
  - **Current re-frame2-pair-mcp tool names** — the actual wire surfaces that egress live state off-box to an AI/MCP client. They fall into **distinct privacy-relevant categories**, not one flat "current set"; each routes its value(s) through a normative emission site server-side under the fail-closed posture below. **There is no standalone `get-app-db` / `sub-cache` tool** in the current catalogue — `get-app-db` survives only as a *generic / third-party* direct-read class name (a server that ships one inherits the same MUST), and the sub-cache is reached via `snapshot :sub-cache` + `list-subscriptions`. Always check the consuming tool's catalogue ([`re-frame2-pair-mcp/README.md` §Tool surface + §sensitive-reads gate](../../tools/re-frame2-pair-mcp/README.md) for the reference server) before naming a wire surface; the spec is the contract, the catalogue is the current shipped name. The categories:
    - **App-db / sub one-shot reads** — `snapshot` (wraps both `:app-db` and `:sub-cache`), `get-path` (one `get-in` at a path), `read-sub` (a validated one-shot subscription deref), `list-subscriptions` (the reactive sub-cache; `:include-values true` ships each `:value`). Each routes its returned value(s) through `rf/elide-wire-value` (the direct-value emission site).
    - **Epoch / trace streaming reads** — `trace-window` (the recent epoch-record window) and `watch-epochs` (poll-mode epoch matches) project egressed epoch records through `re-frame.core/projected-record`; the `subscribe` streaming tool forces server-side `elide-wire-value` on streamed event / cascade values when the gate is off. These are off-box reads under the **same** default-off gate as the one-shot reads — not outside the fail-closed boundary.
    - **Signal recorder reads** — `record` / `read-recording` / `watch-until` (see §Signal recorder above): read-only, but the recorded samples are elided via `elide-wire-value` before they enter the change log.
    - **View-plane reads** — `read-dom` / `read-ui` (see §View-plane reads above): rendered-content text egress under the same fail-closed elision posture.
    - **Simulated / dry-run egress** — `dispatch-dry-run` mutates nothing, but its `:db-state-after-simulation` (the would-be app-db) and `:would-fire-effects[*].args` (fx-derived data) are app-db-derived egress, gated by the same posture.

> **Off-box read egress is fail-closed (MUST).** Direct reads bypass the trace surface where `:sensitive?` stamping / `redact-interceptor` operate, so any pair-shaped tool that egresses a value-bearing read surface off-box **MUST** scrub it before it crosses the wire. The covered surfaces span the categories above — the one-shot direct reads `snapshot` / `get-path` / `read-sub` / `list-subscriptions` (`:include-values`), the streaming reads `subscribe` / `trace-window` / `watch-epochs`, the signal recorder `record` / `read-recording`, the view-plane reads `read-dom` / `read-ui`, the simulated `dispatch-dry-run`, and a third-party `get-app-db` / `sub-cache` surface. The **emission site depends on the value shape**: direct values, recorded samples, and dry-run / sub `:value` slots route through `rf/elide-wire-value` (the single normative direct-value emission site); egressed **epoch records** route through `re-frame.core/projected-record` (the epoch-record emission site, idempotent under `:rf/redacted`); view-plane text rides the same elision posture. The AI/MCP boundary — not `app-db` itself — is the trust boundary. Off-box defaults are **suppress-by-default**: `:rf.size/include-sensitive?` and `:rf.size/include-large?` both default `false`, so a sensitive slot returns `:rf/redacted` and an oversize value returns `:rf.size/large-elided`; when both match, **sensitive drop wins** (the size marker would leak `:path` / `:bytes` / `:digest`). Re-enabling is opt-in only: the cross-MCP boot gate `--allow-sensitive-reads` (default **OFF**) plus the per-call `include-sensitive` arg. Dropped values surface as the `:dropped-sensitive` / `:elided-large` indicators. The walker runs **app-side** (it reads the frame's `[:rf.runtime/elision …]` registries — durable **runtime-db** partition state per EP-0001, not the retired app-db `:rf/runtime` root), never in the MCP host. Full contract for the elide-wire-value egress MUST: [`spec/Tool-Pair.md` §Direct-read privacy posture for `sub-cache` and `get-path`](../../spec/Tool-Pair.md#direct-read-privacy-posture-for-sub-cache-and-get-path) (and the security framing in [`spec/Security.md` §Direct-read privacy posture](../../spec/Security.md#direct-read-privacy-posture-for-sub-cache-and-get-path)). The per-server `--allow-sensitive-reads` boot gate itself is not defined in those spec sections — its authoritative home is the cross-MCP catalogue ([`spec/Conventions.md` §Cross-MCP indicator-field vocabulary](../../spec/Conventions.md#cross-mcp-indicator-field-vocabulary-suppression-counters)) plus the conformance pins under [`tools/mcp-conformance/`](../../tools/mcp-conformance/) and each MCP server's tool catalogue.

The **current upstream-routing surface families** are exactly the ones above — trace stream, registrar query API, epoch-history / restore, state injection (the four partition-aware mutators), schema reflection, source-coord annotation, direct reads, render-driving / dispatch-settle, view-plane reads / view attribution, signal recorder, and the operating-frame trio. When a finding routes upstream, name the matching family from this list. Earlier versions of this leaf advertised only an abbreviated five-name subset (`register-listener!`, `register-epoch-listener!`, `epoch-history`, `restore-epoch`, `app-schemas` plus source-coord annotation); that subset omitted render-driving / settle, view-plane reads, the signal recorder, and the operating-frame trio, so a finding about deterministic `dispatch → settle → DOM`, `read-ui` / `read-dom` provenance, human-interaction recording, or multi-frame operating-frame ambiguity could be mislabeled as pair-tool friction and filed against the wrong layer. The fullest *tool-side* list lives in [`re-frame2-pair/README.md`](../re-frame2-pair/README.md); the authoritative *framework contract* is [`spec/Tool-Pair.md`](../../spec/Tool-Pair.md).

## Supersedes re-frame-10x

These surfaces are **first-class in re-frame2 itself** — v2 tooling does not depend on, recommend, or fall back to `re-frame-10x`. Where v1 tooling read 10x's epoch buffer it now reads `(rf/epoch-history frame-id)`; where it stepped through 10x navigation it now calls `(rf/restore-epoch frame-id epoch-id)`; where it detected a 10x trace callback it now registers its own listener (multi-tool coexistence is the expected default). Consuming skills may keep their own audience-specific framing of this claim (dependency note / anti-pattern / structural successor / migration mechanics) and cite this paragraph for the underlying fact.
