# Enhancement Proposals (EPs)

Design proposals for re-frame2 which follow the Python Enhancement Proposal model. The project goal is to drive the coding work using detailed specifications (which are just really good prompts), and these EPs are an example of such prompts.

The EP process itself — types, status lifecycle, durability rules, and the EP-worthiness bar — is normative in [EP-0009](EP-0009-the-ep-process.md). This README is only the index and summary.

## Authoring a new EP

Copy [`EP-template.md`](EP-template.md) to `EP-NNNN-<slug>.md`, fill it in, and add an index row below. The template encodes the active-process rules so a new EP follows them by construction: `Status:` is a [controlled lifecycle](EP-0009-the-ep-process.md#statuses) (not free text), `Type:` is `standards-track` or `process`, and graduation is per-type — standards-track into `spec/`, process into its named normative home (which may be the active EP itself). The full process — including the EP-worthiness bar and the [document conventions](EP-0009-the-ep-process.md#document-conventions) — is normative in [EP-0009](EP-0009-the-ep-process.md). `scripts/check_ep_status_sync.py` is the mechanical gate (status/Type grammar + README/header sync).

| [EP-0025](EP-0025-data-classification.md) | Data Classification | final | A lightweight hygiene helper (NOT security) to keep secrets and large payloads off observability sinks (Datadog, off-box logs) and AI tools (MCP, the trace bus). Mark a path **sensitive** / **large** in one bare-keyword vocabulary (`:sensitive` / `:large` / `:clear-sensitive` / `:clear-large`) at its **definition site** — durable app-db via handler effects or a subsystem registration; transient event / effect / coeffect payloads via the same keys on their registration. One `project-egress` choke point redacts at every default/safe boundary; no propagation, no resolver, no rollback. Removes durable-state Malli-prop classification, durable app-db frame annotations, the imperative marks API, and all sensitivity propagation. |
| [EP-0026](EP-0026-image-api-simplification.md) | Image API Simplification | accepted | Simplify the EP-0023 image surface: replace `:include-ns` / `:exclude-ns` with one `:select-ns` map, keep inline `:registrations` as the local-definition surface, replace `:replace` with deterministic image layer order plus a returned shadow report the programmer asserts on (resolvable shadows never fail; ambiguous/standard/malformed collisions still do), and remove `:rf.image/requires` capabilities end-to-end. The override/overlay vocabulary and the `rf/image` source-stamping macro are EP-0028. |
| [EP-0027](EP-0027-frame-initial-events.md) | Frame Initial Events | final | Add `:initial-events` as the single declarative frame-setup surface — an ordered vector of events dispatched synchronously, in order, during construction. Handler-time frame construction is forbidden (a Spec 002 change — frames are materialized by the view or at top level), and construction-time setup is **strict** — any step failure tears the partial frame down rather than recovering. Story keeps its own richer lifecycle and tagged setup grammar; this EP neither changes nor couples to it. |
| [EP-0028](EP-0028-registration-overlays-and-inline-authoring.md) | Registration Overlays and Inline Image Authoring | proposal | The override/overlay vocabulary and `rf/image` authoring macro split out of EP-0026: behaviour overrides at frame and dispatch scope under one `:registrations`-shaped vocabulary, and making `rf/image` a source-stamping macro for literal inline registrations. Gathers the contested, replay-sensitive surfaces (dispatch-overlay kind set, child inheritance, replay recording, masking-vs-definition naming) so EP-0026 can graduate independently. |
| [EP-0029](EP-0029-xstate-v6-machine-parity.md) | XState v6 Machine Parity | final | Retarget machine parity from XState v5 to the XState v6 alpha direction while preserving declarative topology. Embrace plain guard/action functions, broader optional `:schemas`, explicit state/spawn timeouts, choice states, internal events, spawn-ordering correctness, and final output as an `:on-done` completion payload (`:data-schema` retired for `[:schemas :data]`); leave only state input and durable workflow steps for later consideration (but probably not); reject opaque function-valued transitions, serialization/JSON parity, actor-trigger/emitted/listener conveniences, migration hooks, state-config wrappers, generic async timeout, public `:invoke` aliases, JavaScript Standard Schema, and full XState actor-object semantics. |
