## The objective you are researching, in Mike's words (2026-09-14)

**Parity, defined so it can be tested:** an experienced Storybook (or Histoire, Ladle, Cosmos, Lookbook) user can sit down at Story and accomplish the jobs they came for, at comparable or lower ceremony, without a map of re-frame2 internals. The chrome may differ, the authoring may be EDN rather than CSF, the debugger may be Xray rather than an Actions panel; those are not gaps. Being unable to do the job, or only able to do it through undocumented internals or disproportionate ceremony, is a gap. Parity does not require reproducing another product's API, plugin count, commercial service or accumulated complexity, and it does not permit quietly narrowing the comparison to the areas where Story already looks strong, or calling an inconvenient omission a deliberate divergence without a recorded reason.

**Better, defined so it can be tested:** some of those jobs are cheaper, more honest, or newly possible because a variant is a frame running real events against real handlers, with schemas, traces, epochs, machines and an agent-readable data body. Better is fewer concepts doing more work, and a failure that explains itself. It is not more panels.

## Question 1 — how do we test how close we are?

Design a re-runnable test, then take its first reading. Requirements:

- **Rows are JOBS a user does, not competitor nouns.** Start from `018`'s user stories S1–S11 and the audit's 33 axes, then add or cut on what the comparison set shows. Group by journey: first hour (install, first variant on screen); navigate a large catalogue; make a view-state cheaply (controls, args); see several states at once without leakage; mock a failure of any effect (`force-fx-stub` versus MSW and friends); document a component and its states; the visible state is a test in the UI and in CI; a failure explains itself (assertion to evidence to cause); record an interaction and keep it as data; share or export a state honestly (URL, static build, EDN, capture); an agent discovers, runs, reads a failure, proposes a fix, verifies, on the same artefact; a design-system matrix (theme by viewport by locale, or the nine canonical UI states); accessibility beside the example and in CI; a visual-regression hook without a service; extend the workshop without an addon marketplace; upgrade a cheap state toward real integration in place (the fidelity ladder). Roughly fifteen to twenty rows; more than that almost certainly means you are litigating minutiae. Scoring "do we have an Actions panel?" undercounts Story's wins and overcounts Storybook's — if a row is a noun rather than a job, delete it.
- **Status vocabulary**, used consistently and defined in `rubric.md` so two readers score a row the same way: `WIN` (Story does the job at lower ceremony, more honestly, or in a way the comparator cannot); `MATCH` (comparable ceremony; a Storybook user would not bounce); `GAP` (cannot be done, or only through undocumented internals or disproportionate ceremony); `SPEC-ONLY` (the contract exists; code or docs do not honestly ship it); `UNDERMARKETED` (shipped, but a user following `docs/story/` would not find it); `DIVERGENT` (refused on purpose and the job is served another way — cite the rationale); `OUT` (not a Story job); `TARGET` (`018`–`022` already require it and mark it not-yet). A `DIVERGENT` whose "other way" does not actually serve the job is a `GAP`; never record a refusal as a silent absence.
- **Four layers per row**, because a single status hides the interesting disagreements: SPEC (is the contract in Spec 007 or `tools/story/spec/`?), CODE (does `tools/story/src` implement it, and do tests in `tools/story/test/` pin it?), DOCS (can `docs/story/` plus the README get a new user there?), ERGONOMICS (is it the path of least resistance, or a power-user back door?). Add an EVIDENCE-STRENGTH column beside the status: exercised (you ran it), source-traced, documented-only, or unverified. A supported capability can be poorly evidenced and a confirmed gap can be high-confidence; keep the two axes apart.
- **Ceremony count** is part of the test: concepts the author must hold, encodings they must produce, files they must touch, boot calls they must remember. A `MATCH` at twice the ceremony is a `GAP` in disguise. Trust the programmer: "the programmer might misuse X" is not a gap.
- **Controls, or the test fails open.** Include at least one NEGATIVE control (a job Story should lose or refuse, so an all-green run is suspicious) and one POSITIVE control (a job everyone agrees Story already does, so an all-red run is suspicious). Where a row depends on a test or runtime path, apply the honesty prior from `story-review.md` and use a deliberate failure to show the claimed test detects the defect; a headless success cannot prove DOM interaction, and a skipped browser test cannot prove parity.
- **Weighting and the headline.** Not every row matters equally to a re-frame2 SPA author. Propose weights, defend each in one line, show the weighted and unweighted totals with their denominators, exclusions and how unverified rows are treated, and give a RANGE where the evidence is thin. Lead with an honest categorical reading (which jobs match, win, gap, diverge, or are only pretending) and treat the number as a summary of it, never the other way round. Do not let many minor successes cancel one essential failure.
- **Journeys, executed where you can.** For three canonical journeys — a first-hour author registering their first variant; a maintainer turning a bug report into a failing variant and a passing fix; an agent asked to "make the login error state match the design" — write the steps in Story and in Storybook side by side, count concepts and files, and time-box what you actually try. `docs/story/01-first-variant.md` is the first-hour script: follow it literally in this checkout and record every place it stalls. If `npx` and the network permit, run Storybook's own first-hour (`storybook init` on a throwaway React app) in the session scratchpad — NEVER inside this repository — and time it under the same conditions; report hardware, versions, cold or warm, and sample size, and treat a single run as an observation, not a benchmark. Inspect the real rendered UI when judging interaction or usability; if browser tools are available, a short walk of a testbed is worth more than another spec citation. Say which journeys you executed and which you only read; do not invent a walkthrough you did not take.
- **Re-verify the 2026-05-20 audit.** For each of its ten named gaps (C-1..C-5, D-1..D-3, I-1..I-2) and any "win" your rows contradict: fixed at commit X, still open under bead Y, or no longer a gap because Z. The rf2-2jdh9 close reason names what was actioned. Report material deltas only; do not recap the audit.
- **Make it re-runnable.** Write `matrix.md` (the rows, statuses, four layers, evidence strength, citations) and `rubric.md` (the definitions, weights, controls) BEFORE you write the report, so later reasoning cannot quietly rewrite the evidence; then say how long a re-measurement takes and what invalidates a row (a Storybook major; a Story spec file changing; the tutorial being rewritten; a `story-review.md` P1 landing or being fixed). A paragraph of vibes is not a test.
- **Automatable pieces.** Name which rows could be pinned by a structural test in `tools/story/test/` or by an eval fixture (Story's own `015-Test-Coverage.md` matrix is the template), so that parity, once reached, is guarded rather than re-audited. Do not propose a gate for anything that would need a human judgement per run.

## Question 2 — how do we imagine being better?

Reason from what re-frame2 HAS rather than from what Storybook lacks, and try to disprove each advantage before you claim it. Read the framework surfaces Story stands on: `spec/002-Frames.md` (per-variant frame isolation), `spec/009-Instrumentation.md` and `spec/Tool-Pair.md` (the trace bus, epochs, time-travel, the agent-facing contract), `spec/010-Schemas.md` (schema-derived controls), `spec/005-StateMachines.md` (machine states and tags as reachable-state enumerators), `spec/011-SSR.md`, and the Xray tool (`tools/xray/spec/000-Vision.md` and `008-Embedding-Contract.md`, which Story embeds). Then, for each strength, separate SUBSTRATE POTENTIAL from SPECIFIED CONTRACT from SHIPPED BEHAVIOUR from DISCOVERABLE BY A NEW USER:

- **Variants are data.** A Storybook story is a render function plus args; a Story variant is an EDN description of a world reached by events. What does that make possible that a function cannot (diffing two variants; generating variants from a schema or a machine; an agent editing a variant without a parser; replaying a production epoch as a variant)? Which of those does Story do today, with file:line?
- **Every state is reachable by events, and events are logged.** Can Story derive the variant set from a machine's states and tags, or from a recorded session, instead of the author writing them by hand? Storybook cannot, by construction. Built, specified, or only possible?
- **Frames.** Isolation without iframes; several variants of one app side by side in one page (`docs/story/02-every-state-side-by-side.md`). What does Storybook pay for its iframe isolation, and does Story's answer hold up for CSS, focus, portals and stale asynchronous results?
- **One plan, result and evidence path.** Human UI, `story/run` / `story/is`, CI, and Story-MCP are supposed to be entry points over one model. Are they, at trunk — or is that a finding?
- **Mock any effect.** `force-fx-stub` stubs any `reg-fx` (HTTP, websocket, storage, analytics, navigation) with one decorator where Storybook needs an addon per seam. Verified?
- **The variant is a test** (`017-Testing-Story.md`, `docs/story/04-the-variant-is-a-test.md`). Storybook is converging on this from the other direction. Who is further along on your run date, honestly, and on which sub-axis (assertion vocabulary; evidence artefacts; CI shape; the `:cannot-run` third state; record-don't-throw)? Apply the honesty prior here above all.
- **Xray earned at failure** (`docs/story/06-xray-earned-at-failure.md`): a failing variant opens the inspector on the epoch that failed. Name the Storybook-world equivalent and score it.
- **The agent loop.** Describe the loop an agent can run today (register a variant, run it, read the evidence, edit the app, re-run) with the exact tool names from `tool-descriptors.edn`, and what the loop still cannot do. Then imagine the loop it should run in a year, and say which pieces are cheap. AI-first is a property of the shape (queryable registry, serialisable variant, one plan and result path), not a bolt-on demo.
- **Schemas to controls.** The audit called schema-derived controls "THE controls story" and said it was undermarketed. Still true? What would make it obvious in the first ten minutes?
- **Fidelity ladder** (`docs/story/03-fidelity-ladder.md`) and **snapshot identity** (`08-snapshot-identity-and-sharing.md`): differentiators or vocabulary? Lower rungs must not be presented as stronger proof than they are.

Then write the advantage thesis: which jobs the comparators do poorly BECAUSE OF THEIR SUBSTRATE (not because a plugin has not shipped yet); which of those Story has productized (a user does it without knowing the substrate's name) versus latent (possible if you know re-frame2 well, invisible if you don't); what "better" looks like in a year as a handful of scenes (a design-system maintainer, an app developer, an agent, a tester), each impossible or humiliating in Storybook for a structural reason; and what Story should stop copying (`018` §3.1 already names addon sprawl, opaque decorator chains, examples disconnected from app state, and separate encodings for stories, tests, fixtures, repros and traces — confirm, extend or dissent with evidence). For each "better" claim state its tier: BUILT (file:line, and you ran it), SPECIFIED (spec section, not yet in code), or IMAGINED (your proposal, with a before-and-after workflow, a small idiomatic data sketch where it helps, and a falsifiable hypothesis about user benefit). These tiers are for advantage claims; the status vocabulary above is for matrix rows; do not invent a third jargon. Apply the stance to every proposal: a proposal that adds a concept, a second encoding, or a ceremony the programmer did not ask for must say what it removes, or be killed in one sentence rather than litigated into a recommendation. It is an acceptable outcome that a competitor is more ergonomic on a job, or that Story already has the right capability and only needs better presentation.
