## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

## Session Completion

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   ```bash
   git pull --rebase
   bd dolt push
   git push
   git status  # MUST show "up to date with origin"
   ```
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**
- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds

## Beads durability

`.beads/issues.jsonl` is a full-database export, not an ordinary source file. `bd` rewrites it in **every** checkout, so each worker worktree carries a snapshot of the tracker as it stood when that worktree was created. Committing that snapshot **time-travels the tracker**: beads closed since it reopen, beads filed since it vanish. PR #6677 landed exactly that — 135 insertions / 136 deletions of pure collateral.

- **The tracker database is the mayor's to commit.** Worker branches carry code, spec, docs and tests — never `.beads/issues.jsonl`, `.beads/metadata.json`, or any other database-derived path. The human-authored config (`.beads/README.md`, `.beads/config.yaml`, `.beads/.gitignore`, `.beads/hooks/**`) is fair game from anywhere. A pre-commit hook enforces this in linked worktrees **once installed** — run `sh scripts/install-git-hooks.sh` (or `scripts/install-git-hooks.ps1`) once per clone; worktrees share the primary checkout's hooks directory, so one run arms them all, and `--check` reports whether a checkout is currently guarded. `scripts/check-beads-pr-boundary.sh` is the CI arm. See `scripts/git-hooks/README.md`.
- **Never resolve a `.beads` conflict with `--theirs` or `--ours`.** Both sides are whole-database exports, so picking one wholesale discards every bead the other side recorded. Resolve then **regenerate**: take the incoming file (`git checkout --theirs .beads/issues.jsonl`), re-import it, and let `bd` re-export from the merged database.
- **Checkpoint first, then clear `.beads`, then pull — and never stash.** An uncommitted `.beads/issues.jsonl` makes `git pull` abort ("local changes would be overwritten"), silently freezing HEAD at a stale base, so the file does have to be cleared. But clearing it *after* a `bd close` or `bd create` reverts the export to its pre-close state, and the next checkpoint writes that revert back over the database — the close evaporates (rf2-51uz1: rf2-5e8zv was reopened exactly this way, and commit `e80786e007` records three more re-closed by hand). The order is therefore fixed, and a checkout of `.beads` must never follow a tracker mutation within a tick:

  ```bash
  sh scripts/beads-checkpoint.sh   # export from the database, verify, commit
  git checkout HEAD -- .beads      # now safe: HEAD carries the tracker
  git pull --rebase origin main    # name both: a bare pull reads the shared fetch-head file
  ```

  **Name remote and branch on that pull, and on the one in the session-completion block above** (that block is tool-generated, so read its bare form as the same command with both named). A bare `git pull --rebase` takes its target from `FETCH_HEAD`, which any fetch in this checkout rewrites — a branch fetch moments earlier leaves several refs in it, and the pull aborts with `Cannot rebase onto multiple branches` on a clean, undiverged tree where neither remedy above applies (measured 2026-08-29 22:31 AUSEST, mid-checkpoint, one line after a `git fetch origin worker/<branch>`). The abort is inert only because the push that follows still lands; the next step it silently skips is the rebase itself.

  `sh scripts/beads-checkpoint.sh --pre-pull` (or `-PrePull` on the `.ps1`) answers "would clearing `.beads` throw tracker state away?" — exit 0 means the checkout is safe. **Do not `git stash`**: stashes are repo-global and contaminate every other worktree in flight.

  **This sequence answers one abort message and only that one.** A pull that aborts with `Not possible to fast-forward` is the other cause — the checkpoint you just made has diverged from a racing push — and clearing an already-clean `.beads` is inert against it. Branch on the message; both branches are set out under *After each merge* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#after-each-merge).
- **A checkpoint re-exports; it never trusts the working file.** `scripts/beads-checkpoint.sh` (POSIX; `.ps1` sibling for Windows) runs `bd export`, refuses an empty or badly shrunken result, and commits only `.beads/issues.jsonl`. That ordering is what makes a reverted file unreachable: the export is regenerated from Dolt before anything reads it. A hand-rolled `git add .beads/issues.jsonl && git commit` cannot make that guarantee — it commits whatever the last checkout left behind.
- **The same floor is in the pre-commit hook, so a plain `git add` cannot route around it (rf2-or8te).** The checkpoint's guard only protects commits that go through the checkpoint, and twice an empty export reached main by a path that did not: `7aea52459` (2026-06-10, 7172 rows) and `4d8042d80d` (2026-07-26, 2573 rows), both plain `git add` from the mayor checkout, both leaving `git status` clean afterwards. The hook now refuses any staged `.beads/issues.jsonl` below 90% of HEAD, from every worktree. **An empty export is a REGENERATION event, not a data-loss one** — the Dolt database is the source of truth, `sh scripts/beads-checkpoint.sh` rebuilds it, and restoring an older export from git history would time-travel the tracker instead. For a genuine mass delete the message names the escape: inspect with `bd status`, then `git commit --no-verify`.
- **Do not set `git update-index --skip-worktree` on it.** It hides the local edit from `git status` but still blocks `git pull` — the same frozen HEAD, now with nothing on screen to explain it. Stage explicit paths instead of `git add -A`.
- **`bd update --notes` REPLACES the notes field; `--append-notes` is the flag that adds to it.** The loss path here is the bead's own content rather than the export, and it is silent in the same way: `--notes`' help text reads *"Additional notes"*, which is how a reader takes it, nothing errors, `bd` prints its normal success line, and the damage stays invisible until somebody re-reads the bead — on a held bead, possibly never. Measured across five beads in one session (~72,800 characters, `rf2-9wmqd` 46569→3294 the worst), and it had happened before: `rf2-y1jkm` carries an earlier account of the same mistake, surviving only because its author restored it by hand. **Recovery is complete and cheap, so this is not an occasion to panic** — `.beads/issues.jsonl` in git history is a full database export, so the pre-damage notes sit in any checkpoint commit predating the update: `git show <rev>:.beads/issues.jsonl`, rebuild as old + newline + current, write back. One trap in that recovery is worth knowing, because it fails silently where the rest of this is merely quiet: a value past roughly 27,000 characters is rejected by the shell with a non-zero exit and **no message at all**, so split at line boundaries into ~18,000-character chunks — `--notes` for the first, `--append-notes` for the rest — and confirm by probing for known content from the start, middle and end rather than by comparing lengths, which chunking shifts by a byte or two.

## Workflow

- **Always dispatch beads to a background agent when sensible.** Don't ask permission for clear-cut implementation work, mechanical fixes, or follow-on tasks where the direction is set. Keep the work flowing. Only pause for genuine decisions Mike hasn't made.
- **The dispatch ledger is `ai/worktree-agent-ids.tsv`, and THIS BULLET is its contract — the file is local-only and untracked, so its own header is not an authority and has already drifted from its rows.** One tab-separated line per dispatch, five fields, in this order: **`worktree`** (the absolute path, never the bare directory name), **`agentId`**, **`dispatched`** (timestamp), **`branch`**, **`beads`**. Per *Reaping* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#reaping) the reap test reads the **report**, never a field of this line; `agentId` is the route to it, and **there is no done-sentence field**, because whether to hold report text locally at all is still an unmade operator call. Both recorded drifts came from reading the header instead of this contract: taking the last field for a done-sentence returns a bead id — well-formed, reassuring, wrong, and it would have authorised reaping 17 of 30 worktrees on no report at all — and keying column 1 by bare name made a name-keyed grep return 0 rows for 28 worktrees that had rows (rf2-83z0). The header also cites `.claude/commands/mayor-hygiene.md`, under a directory that no longer exists. **The contract binds the NEXT line, and does not describe the file — when this was written, 34 of 261 rows matched it, 13%.** Measured at that same point: 44 rows did not carry five fields at all and 127 began with something other than an absolute path, because this shape only settled on 2026-08-21 and every conforming row postdates that. **Every figure here is a snapshot of a file that grows each tick, so re-measure rather than quoting them.** And binding the next line is not automatic: of the first TEN rows written after this contract merged, four conformed and **six did not, all six by the author of the contract** — because the shape has no spelling for a worktree the MAYOR occupies, which has neither an agent id nor beads, so the writer improvises, and that improvisation put the record's own timestamp in field 1 and shifted every field by one, which is the positional failure this bullet exists to stop. **A mayor-occupied row uses the same five fields**: the absolute path, `(mayor)`, the timestamp, the branch, `--`. **So read a row's fields; never address them by index.** A positional parse is right about one row in eight and wrong with a well-formed answer on the rest, which is the failure this bullet exists to stop, one level up. Normalising the history is explicitly NOT wanted: the contract is here so the next line is right, not so the old ones are.
- **Worker worktree guard is mandatory before edits.** Background workers must run the guard from their intended checkout before editing, and report the printed `WORKTREE_ROOT`. Use `sh scripts/assert-worker-worktree.sh` (POSIX primary) or `powershell -ExecutionPolicy Bypass -File scripts/assert-worker-worktree.ps1` (Windows). The guard derives the mayor checkout as the repository's primary worktree (`git worktree list`) and the worktree parent as its `re-frame2-worktrees` sibling — no hardcoded paths; both overridable via `RF2_MAYOR_ROOT` / `RF2_WORKTREE_PARENT`. It refuses the mayor checkout and any root outside the worktree parent. This mitigates observed harness path-resolution leaks; it is not a root-cause fix for the external edit/write bug.
- **Remove a worker worktree only via `scripts/remove-worker-worktree.sh`** (POSIX primary; `powershell -ExecutionPolicy Bypass -File scripts/remove-worker-worktree.ps1` on Windows). A worker worktree junctions `implementation/node_modules` at the mayor checkout's real one, and a bare `git worktree remove` follows that junction and empties the mayor's real `node_modules` — exit 0, silently, breaking every local build until `npm ci --prefix implementation` restores it. It has happened twice. The script unlinks the link first, removes the worktree second, then re-checks the mayor's `node_modules` counts and fails loudly if any dropped. **A worker that creates the junction removes it as its last act before reporting done**, so hygiene never meets one.
- **Minimise merge conflicts when dispatching.** Hot-zone files (`spec/Conventions.md`, `migration/from-re-frame-v1/README.md`, `spec/API.md`, `spec/Tool-Pair.md`, `spec/Spec-Schemas.md`, `spec/009-Instrumentation.md`, `spec/006-ReactiveSubstrate.md`, `spec/005-StateMachines.md`, `spec/002-Frames.md`, top-level `implementation/deps.edn`, `implementation/shadow-cljs.edn`, `.github/workflows/*`, `.github/scripts/report-changed-surfaces.sh` and its mirror `implementation/scripts/_changed-surfaces.test.cjs`) are sequential, never parallel — two beads touching the same hot file = sequence them, second waits for the first's PR to merge. **That last pair is one-toucher by construction rather than by convention, but only for a change that alters what the classifier OUTPUTS or what the test PINS about those outputs**: the test pins those outputs, so such a change lands a tree where the suite contradicts the script unless both halves move in ONE commit. **Read universally the rule blocks a legitimate repair, because a change can REMOVE a contradiction as readily as create one**: correcting the test to match the script's EXISTING, unchanged behaviour — a stale pin naming a path that has moved, an overstated test name — is correctly one file, and PR #8664 was exactly that, touching the mirror alone and merging green at 88/88. What stays UNCONDITIONAL is the concurrency half: two workers in that pair conflict every time, so sequence them even when one of the two diffs turns out to be a single file. Isolated surfaces (single-artefact `implementation/<feature>/src/`, new-file additions, test-only dirs `implementation/<feature>/test/`, `examples/<substrate>/<example>/`) are safe to parallel.
- **Do not maintain `ai/dashboard.md`.** The dashboard is retired (Mike, 2026-06-20): don't create or refresh it. (`ai/decisions.md` is likewise retired — see the Local working files section above.)
- **Fast-forward `main` onto `origin` immediately after every PR merge.** Run `git fetch origin main && git merge --ff-only origin/main` as the very next step after `gh pr merge --rebase` — name the remote and branch on the fetch, because the bare form silently no-ops when the asynchronous post-merge audit push races it, and keep the `&&` so a failed fetch can't be followed by a merge against a stale ref. **This replaced `git pull --ff-only origin main` deliberately; don't restore the pull form.** A pull takes its merge target from `FETCH_HEAD`, a scratch file any concurrent git process in the same checkout rewrites, and a contaminated one doesn't fail honestly — it either aborts wearing one of the two messages below on a clean, undiverged tree where that remedy is inert, or silently fast-forwards the trunk onto a feature branch. A ref can't be captured that way, and both aborts below reproduce verbatim under the merge form, so nothing is lost. No exceptions, no batching multiple merges before fast-forwarding. **When that merge ABORTS, the message names which of two causes it is, and their remedies are not interchangeable**: `local changes would be overwritten` is an uncommitted `.beads/issues.jsonl` (checkpoint, `git checkout HEAD -- .beads`, retry — see the bullet below), while `Not possible to fast-forward` is your own committed checkpoint diverging from that same racing push, for which the checkout is inert and naming the remote no help — `git pull --rebase origin main`, then verify. The full drill, its verification list and the reasoning for the merge form all live under *After each merge* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#after-each-merge); don't restate them here. Then verify the tree rather than the line git printed: `git rev-parse HEAD` must equal `git rev-parse origin/main` — movement is the wrong test, and one mismatch is not yet evidence either, because that same audit push can land between the two reads, so read both refs again before believing it. Mike glances at his local working tree to track progress; staleness leaves him with a wrong picture and breaks subsequent dispatches that worktree off `origin/main`. Same rule applies whether merge happened seconds ago or while another agent was running.
- **Three mechanical traps in the merge criterion are recorded here rather than left to the method doc, because each fails OPEN — each ADMITS a merge that should have been blocked, and each is one small step from correct.** The criterion itself is not restated here; it is [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#1-merge) §1, clauses 1–5. **(a) The job-key discriminator needs TWO LEADING SPACES**: `git diff <merge-base> origin/main -- .github/workflows/ | grep -cE '^\+  [a-z][a-z0-9_-]*:[[:space:]]*$'`. Job keys nest under `jobs:`, so the unindented form matches nothing at all — it read 0 across the last twenty `.github/workflows/` commits, including all five that genuinely added a job, and a constant zero is the reassuring answer, so nothing on screen betrays it. Exercised in both directions rather than only where the answer is zero: the two-space form reads `1` on `366e4fca79`, which added a job, and `0` on `4cf4d711a2`, which added none; the unindented form reads `0` on both. **(b) Pass the FULL 40-character head oid to `gh run list --commit`, taken from `gh pr view --json headRefOid` — never extended by hand from an abbreviated sha.** An abbreviated sha matches nothing, returns `[]`, and clears the live-runs check vacuously — and a hand-fabricated full-length sha returns the same `[]` while satisfying the full-40-characters rule in form (measured 2026-09-01: PR #8829 read a full 84-check rollup beside `[]` from a sha extended from a report's 10-char prefix; the re-queried oid returned 4 completed runs). A full rollup beside an empty run list is the tell — re-query, don't conclude. Clause 4 states the trap generically under *Abbreviated revisions*; what is here is the CLI concretion it does not name. **(c) `All required checks passed` is a REAL JOB — never subtract it from the band, and never merge on it alone.** It is `test.yml`'s `all-required-passed` aggregator (`if: ${{ always() }}`, `needs:` every gating job in that file), and it presents in the rollup as an ordinary three-second CheckRun in workflow `tests`, which is exactly what invites the misreading: it reads like a host-generated "everything is green" summary row, so the reflex is to discount it and derive a band one LOWER — after which a rollup genuinely one job short reads as at-band and merges. **It fails open in the opposite direction too, and that reading is the more tempting one**: GitHub's `needs:` cannot span workflow files, so the aggregator covers `test.yml` jobs ONLY, while `lint`, `docs` and `portability` are separate workflow runs outside it — a green aggregator is not a green rollup, and the five clauses still apply to the whole set. Measured 2026-09-01 across five PRs at once: totals of 82, 83 and 84 all occurred, the aggregator was PRESENT on a PR still carrying two non-terminal checks (#8857, total 82) and ABSENT on two still building their sets (#8855 and #8856, total 83) — so its presence tracks neither the total nor settledness, and **a raw count is not comparable across PRs mid-build**. Its own pass rule mirrors clause 2 (`needs.*.result`: `success` and `skipped` accepted, `failure` and `cancelled` refused), and `test.yml` deliberately keeps its `pull_request` trigger UNFILTERED so the aggregator is always scheduled — a path-filtered trigger would make it absent on filtered PRs, which is the phantom-pending trap rf2-dtvmb fixed.
- **Checkpoint, then clear `.beads`, then pull — never stash.** `.beads/issues.jsonl` carries uncommitted tracker state that aborts the pull with `local changes would be overwritten`, so it must be cleared; but clearing it after a `bd close` reverts that close, and the next checkpoint writes the revert back. (That message only — a `Not possible to fast-forward` abort is the other cause named in the bullet above, and this remedy does nothing for it.) Run `sh scripts/beads-checkpoint.sh` (it re-exports from the Dolt database rather than trusting the working file), *then* `git checkout HEAD -- .beads`, *then* pull. Stashes are repo-global and contaminate every worktree in flight — see [Beads durability](#beads-durability) for the full sequence and the `--pre-pull` pre-flight. (The `ai/` tree is local-only and won't show up in `git status`.)

Since rf2-i4nb2 that surface is **three** rosters rather than two — git-tracked non-`README.md` markdown beside source is the third (`implementation/SECURITY.md`, `examples/TESTING.md` and a handful more that no gate reached before), narrow by design, with `scripts/_test_fixtures/`, the docs-gate roots and `tools/*/spec/` all still excluded. **Both run in `test.yml`'s `verify-readme-links` job on every PR** — that job carries no surface guard, which is what rf2-v7fui secured for the docs gate — so the surface is gated, and the repair for a wrong nomination is to name the right gate, never to add one. Both also run in the fast-PR spine, but there they sit inside its **documentation tier, which is classifier-gated**: a green spine on a diff the classifier did not call documentation ran neither of them, so cite CI for these two rather than a local spine pass. But **that job's NAME reads as though it checks READMEs while the gate that actually does is the other one**, so nominate by PATH, never by job name: a broken target planted in `implementation/adapters/reagent/README.md` returns `check_doc_slugs.py` green and `check_readme_links.py --ci` red (rf2-8pb5k, measured twice). **And `mkdocs build --strict` does not validate heading ANCHORS at all — not even on a page it builds and publishes, so `exclude_docs` and `docs_dir` do not exhaust its non-coverage**: MkDocs grades a missing anchor, in-page or cross-file, at INFO (`validation.anchors` defaults to `info`, and `mkdocs.yml` sets no `anchors` key — only `links.unrecognized_links`), and `--strict` promotes WARNING but not INFO, so the strict build names the broken anchor on stdout and still exits 0. That leaves `check_doc_slugs.py` the only anchor gate for pages under `docs/` — **redundancy missing rather than coverage missing**, since it runs unguarded on every PR (rf2-zk50, measured on one planted anchor: docs gate exit 1 naming file, line and anchor; strict build exit 0). `scripts/check_provenance_pins.py` validates changed pages under `docs/design/hicasso/` as its own `docs.yml` job. **And neither gate looks inside a fenced code block at all**, which bounds every green above a second time and along a different axis than the rosters: both share one extractor, and it strips fences before it reads a single link, so a broken target or anchor written inside a fence is invisible and the exit 0 is silent about it (rf2-sodfq, measured in both directions — the identical broken anchor returns exit 0 inside a fence and exit 1 four lines above it in prose). The skip is deliberate and stays: well over a hundred in-repo doc links live inside fences, most of them in `spec/Spec-Schemas.md` as `;;` commentary inside schema samples, and a fence is code — this repo's own write-ups quote broken links on purpose. Only `docs/design/hicasso/` and `docs/the-mayor-method/` are held to more, and there the rule is the opposite one: a doc link inside a fence is itself reported, because those trees' fences are pasteable deliverables. **So for an edit CONFINED to a fenced block — and whole pages qualify, `spec/Spec-Schemas.md`'s schemas among them — neither gate is the gate**: nominating one returns a green that inspected nothing you changed, so check the links by hand and say so. Nothing validates any of this markdown's PROSE, tables, rendering or nav — link targets and anchors are the whole of what these gates check — so **the worker verifies anchors and table column counts by hand and says so in the PR body**.
