# Project Instructions for AI Agents

This file provides instructions and context for AI coding agents working on this project.

## Project stance

> Posture is that we are pre-alpha and focused on elegance, power and a masterpiece.
> But we are not over-engineering or gold plating. Also, we trust the programmer.
> We're trying to facilitate high productivity for them (and the AI they use) via a
> library with excellent ergonomics and low friction. We don't need to litigate every
> last fine detail and drown in the minutiae.

**Paste that quoted block VERBATIM into every dispatch preamble — never summarised, never trimmed to fit.** The lenses say what good looks like and everything after them says when to STOP; a paraphrase keeps the memorable half and drops the restraining one, and what survives reads as a stance that wants MORE of everything. Two clauses do the most work and are the first to be lost: *trust the programmer* rejects a nagging diagnostic, and *don't litigate the minutiae* lets an item die with its reasoning recorded instead of consuming a worker. **This file is the stance's only tracked home.** [`docs/the-mayor-method/dispatch-prompt-template.md`](docs/the-mayor-method/dispatch-prompt-template.md) deliberately does not carry it — that page is the project-neutral method — so when regenerating dispatch blocks from the template, take the other blocks from there and the stance from here.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

## Session Completion

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   ```bash
   git fetch origin main && git rebase origin/main
   bd dolt push
   git push
   git status  # MUST show "up to date with origin"
   ```
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**
- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds

## Beads durability

`.beads/issues.jsonl` is a full-database export, not an ordinary source file, **and it is a SNAPSHOT SOMETHING HAS TO INSTALL rather than a mirror `bd` keeps current. An ordinary tracker write does NOT regenerate it** (rf2-xmpm8): a `bd create`, `bd update` or `bd close` lands in the Dolt database, and the tracked file does not move. Measured at trunk `7bfa3bab2e` on `bd` 1.2.2 (6c124203e), taking the write from another agent's authorised update rather than one of the reader's own — the database and a stdout `bd export` carried this very bead at `in_progress` with a 2609-character `notes`, while the tracked `.beads/issues.jsonl` in BOTH the worker worktree and the primary checkout still read `open` at 689 characters, byte-identical to each other and unchanged in SHA256, size and mtime across that export; controls both ways, a third bead reading identically in all three and a nonexistent id absent from all three. **An explicit `bd export` does not write it either, because `bd export` DEFAULTS TO STDOUT** — its help reads `-o, --output string   Output file path (default: stdout)`, so it takes a redirect or an `-o` to land anywhere at all. What installs the tracked file is `scripts/beads-checkpoint.sh`, which exports to a TEMPORARY file (`bd export --include-memories > "$TMP_EXPORT"`, lines 497-505), validates it against a row-count floor and a divergence guard, and only then copies it over the tracked path (lines 694/699). A checkout therefore receives this file the way it receives any other tracked file, so each worker worktree carries a snapshot of the tracker as it stood at the commit that worktree was created from, and that snapshot goes stale as the tracker moves on. Committing that snapshot **time-travels the tracker**: beads closed since it reopen, beads filed since it vanish. PR #6677 landed exactly that — 135 insertions / 136 deletions of pure collateral. **A `bd` READ is not how a worktree acquires tracker state, and reading your own bead is safe** (rf2-oitjw): measured 2026-09-17 on `bd` 1.2.2, five reads — `bd show --json`, `bd ready`, `bd list`, `bd recall` and a plain `bd show` — run from a FRESHLY created worktree and again from one already in use each exited 0 and left that checkout at zero porcelain lines with `.beads/issues.jsonl` byte-identical, the same blob hash, the same size, an unchanged mtime and no file added to `.beads/`; an 18-byte append to that same file moved every one of those readings, so the zeros are the instrument working rather than a probe that cannot see. **Read that as a statement about READS ALONE** — not because a write would dirty your checkout, which is precisely what the measurement above refutes, but because a write from a worktree mutates the SHARED database every other worktree is reading. **So the tracked file is the wrong instrument for noticing one: a clean `git status` after a `bd` write is the EXPECTED reading, not evidence the write did nothing**, and it fails in the reassuring direction. **None of this licenses the converse that `bd` never writes a JSONL, and the scope is the CONFIGURATION rather than the tool**: `.beads/config.yaml` documents a `no-db` mode in which `.beads/issues.jsonl` IS the source of truth and every write therefore moves it, an `events-export` that appends `.beads/events.jsonl` on each flush, and a periodic JSONL backup "Auto-enabled when a git remote exists", which this repo's `sync.remote` satisfies. Those three are read off that file's own commentary rather than measured here, and that is the point — a changed setting, a `bd` upgrade, or an `-o` pointed at the tracked path would each falsify the measurement above with nothing on screen saying so. The staleness needs no `bd` invocation at all to arise — two live worktrees created seven minutes apart held export snapshots differing by 11 insertions / 7 deletions — so every prohibition below stands as written, and none of them was ever a reason not to read the tracker from a worktree.

- **The tracker database is the mayor's to commit.** Worker branches carry code, spec, docs and tests — never `.beads/issues.jsonl`, `.beads/metadata.json`, or any other database-derived path. The human-authored config (`.beads/README.md`, `.beads/config.yaml`, `.beads/.gitignore`, `.beads/hooks/**`, `.beads/PRIME.md`) is fair game from anywhere. **`.beads/PRIME.md` is hand-written prose, not an export**: `bd prime` reads it and emits it INSTEAD of its own ~1.8 MB default at SessionStart and PreCompact, so it is the file that decides what rides in every session's opening context — edit it like any other doc, and re-sync it by hand against `bd prime --export` after a `bd` upgrade, since the override suppresses upstream changes to that default. It is advice from a tool and **this file outranks it**; never cite it as "CLAUDE.md says". A pre-commit hook enforces this in linked worktrees **once installed** — run `sh scripts/install-git-hooks.sh` (or `scripts/install-git-hooks.ps1`) once per clone; worktrees share the primary checkout's hooks directory, so one run arms them all, and `--check` answers whether a checkout is currently guarded **through its EXIT CODE ALONE — on success it prints nothing at all** (0 installed and current, 1 otherwise; it writes only when it fails, as its own usage line says). **So never read it through a pipe.** `… --check | tail` hands back `tail`'s status, and empty output beside a 0 looks identical whether the hooks are armed or missing — which is the pipeline-status hazard this file catalogues elsewhere, arriving through a guard everyone is told to run. Measured 2026-09-08 on a checkout whose four hooks WERE installed: piped through `tail` it printed nothing and the pipeline exited 0; re-run bare it printed nothing on stdout, nothing on stderr, and exited 0 — so the piped form cannot separate that case from an unguarded one. Run it bare and read `$?`; to SEE the answer rather than infer it from silence, list the hooks directory and expect `commit-msg`, `post-merge`, `post-rewrite` and `pre-commit` (`core.hooksPath` unset means `.git/hooks`). `scripts/check-beads-pr-boundary.sh` is the CI arm. See `scripts/git-hooks/README.md`.
- **Never resolve a `.beads` conflict with `--theirs` or `--ours`.** Both sides are whole-database exports, so picking one wholesale discards every bead the other side recorded. Resolve then **regenerate**: take the incoming file (`git checkout --theirs .beads/issues.jsonl`), re-import it, and let `bd` re-export from the merged database.
- **Checkpoint first, then clear `.beads`, then update — and never stash.** An uncommitted `.beads/issues.jsonl` makes the rebase step below abort (`cannot rebase: You have unstaged changes`), freezing HEAD at a stale base, so the file does have to be cleared. Rebase refuses on *any* unstaged change, not only one the incoming commits would overwrite, so this bites even when nothing upstream touches the file. But clearing it *after* a `bd close` or `bd create` reverts the export to its pre-close state, and the next checkpoint writes that revert back over the database — the close evaporates (rf2-51uz1: rf2-5e8zv was reopened exactly this way, and commit `e80786e007` records three more re-closed by hand). The order is therefore fixed, and a checkout of `.beads` must never follow a tracker mutation within a tick:

  ```bash
  sh scripts/beads-checkpoint.sh                   # export from the database, verify, commit
  git checkout HEAD -- .beads                      # now safe: HEAD carries the tracker
  git fetch origin main && git rebase origin/main  # explicit ref, not a pull — see below
  ```

  **Take that third step's target from `origin/main`, and don't restore the `git pull --rebase origin main` it replaced — naming the remote and branch does not make a pull equivalent.** A pull is two steps: it fetches into `FETCH_HEAD`, then rebases onto whatever `FETCH_HEAD` says by the time the rebase reads it. Naming remote and branch constrains only the fetch half, so the rebase half still takes its target from a scratch file that any concurrent git process **in the same checkout** rewrites — which is why the named form was measured aborting with `Cannot rebase onto multiple branches` on a clean, undiverged tree, exactly as the bare form had (2026-09-01 22:4x AUSEST, mayor checkout, six worker worktrees live). The reasoning is the one already written out for the merge case in the fast-forward bullet under [Workflow](#workflow) — *a ref can't be captured that way* — and this sequence was simply left behind when that case was fixed; keep the `&&` for the same reason that bullet does, so a failed fetch can't be followed by a rebase against a stale ref. Read the session-completion block above the same way: it is tool-generated — and so is the copy of it in `AGENTS.md`, which sits inside a `BEADS INTEGRATION` marker carrying the same block hash — so if a regeneration restores the pull form in **either**, correct it in both rather than following it. The generator is `bd` itself, not anything in this repository, so there is no template here to fix; the two copies have to be kept in step by hand.

  Naming remote and branch is still worth doing on the fetch, which is the half it does reach: the earlier instance recorded here was of the **bare** form, whose own fetch is unconstrained too (measured 2026-08-29 22:31 AUSEST, mid-checkpoint, one line after a `git fetch origin worker/<branch>`). The contaminating process is a concurrent one in the same checkout rather than a peer worktree — `FETCH_HEAD` is per-worktree, as `git rev-parse --git-path FETCH_HEAD` resolves inside a linked worktree's own git directory — and the mayor checkout, where several git processes run at once, is where that bites.

  **Do not pipe any step of this sequence, and do not chain past one with `&&` through a filter.** A pipeline's exit status is its *last* command's, so a step written as `… 2>&1 | tail -3 && bd dolt push && git push` reports `tail`'s success and walks straight past a fatal abort with the rebase never performed. That is how the 2026-09-01 abort above went unseen, and why it was inert only in the sense that the push behind it still landed. It is the same hazard as piping a gate through a filter, reached through git instead of a gate runner.

  `sh scripts/beads-checkpoint.sh --pre-pull` (or `-PrePull` on the `.ps1`) answers "would clearing `.beads` throw tracker state away?" — exit 0 means the checkout is safe. **Do not `git stash`**: stashes are repo-global and contaminate every other worktree in flight.

  **This sequence answers one abort message and only that one.** The other cause — the checkpoint you just made having diverged from a racing push — surfaces as `Not possible to fast-forward`, and that is the fast-forward bullet's `git merge --ff-only origin/main` speaking, not the rebase step here, which rebases your checkpoint on top and exits 0. Clearing an already-clean `.beads` is inert against it either way. Branch on the message; both branches are set out under *After each merge* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#after-each-merge).
- **A checkpoint re-exports; it never trusts the working file.** `scripts/beads-checkpoint.sh` (POSIX; `.ps1` sibling for Windows) runs `bd export`, refuses an empty or badly shrunken result, and commits only `.beads/issues.jsonl`. That ordering is what makes a reverted file unreachable: the export is regenerated from Dolt before anything reads it. A hand-rolled `git add .beads/issues.jsonl && git commit` cannot make that guarantee — it commits whatever the last checkout left behind.
- **The same floor is in the pre-commit hook, so a plain `git add` cannot route around it (rf2-or8te).** The checkpoint's guard only protects commits that go through the checkpoint, and twice an empty export reached main by a path that did not: `7aea52459` (2026-06-10, 7172 rows) and `4d8042d80d` (2026-07-26, 2573 rows), both plain `git add` from the mayor checkout, both leaving `git status` clean afterwards. The hook now refuses any staged `.beads/issues.jsonl` below 90% of HEAD, from every worktree. **An empty export is a REGENERATION event, not a data-loss one** — the Dolt database is the source of truth, `sh scripts/beads-checkpoint.sh` rebuilds it, and restoring an older export from git history would time-travel the tracker instead. For a genuine mass delete the message names the escape: inspect with `bd status`, then `git commit --no-verify`.
- **Do not set `git update-index --skip-worktree` on it.** It hides the local edit from `git status` but still blocks the update — the same frozen HEAD, now with nothing on screen to explain it. Stage explicit paths instead of `git add -A`.
- **`bd update --notes` REPLACES the notes field; `--append-notes` is the flag that adds to it.** The loss path here is the bead's own content rather than the export, and it is silent in the same way: `--notes`' help text reads *"Additional notes"*, which is how a reader takes it, nothing errors, `bd` prints its normal success line, and the damage stays invisible until somebody re-reads the bead — on a held bead, possibly never. Measured across five beads in one session (~72,800 characters, `rf2-9wmqd` 46569→3294 the worst), and it had happened before: `rf2-y1jkm` carries an earlier account of the same mistake, surviving only because its author restored it by hand. **Recovery is complete and cheap, so this is not an occasion to panic** — `.beads/issues.jsonl` in git history is a full database export, so the pre-damage notes sit in any checkpoint commit predating the update: `git show <rev>:.beads/issues.jsonl`, rebuild as old + newline + current, write back. One trap in that recovery is worth knowing, because it fails silently where the rest of this is merely quiet: a value past roughly 27,000 characters is rejected by the shell with a non-zero exit and **no message at all**, so split at line boundaries into ~18,000-character chunks — `--notes` for the first, `--append-notes` for the rest — and confirm by probing for known content from the start, middle and end rather than by comparing lengths, which chunking shifts by a byte or two. **A second trap in the same act, and this one DAMAGES the note rather than rejecting it: BACKTICKS inside a DOUBLE-QUOTED shell string are command substitution**, so the backticked words are deleted and whatever they print is spliced in where they stood. `bd` prints its normal success line either way, so the note lands looking healthy while the passage carrying the evidence is gone — and a note about this repo is exactly where backticks cluster, since every path, var and flag in it wants a code span. It damaged a note on `rf2-fmst` in precisely the places quoting the measurements. Measured both ways: ``"epoch anchor `echo REMOVED-BY-SUBSTITUTION` restored"`` arrives as `epoch anchor REMOVED-BY-SUBSTITUTION restored`, while the identical line through a QUOTED heredoc (`<<'EOF'`) arrives verbatim with its backticks intact. **The guard: write the note with a quoted heredoc and pass it as `"$(cat <file>)"`** — the same move the chunking above already needs, so both traps in this bullet share one remedy. If the heredoc will not parse, build the file by any other means and still pass it as `"$(cat <file>)"`: what protects the note is that the content reaches `bd` from a FILE rather than through a double-quoted shell string, and the heredoc is one way to build that file rather than the thing doing the protecting.
- **Reopening a bead ERASES its `close_reason` and its `closed_at`, and the text is not copied into `notes` or anywhere else.** Same class as the `--notes` trap above — a silent field-level loss with a cheap git-history recovery — so read that bullet for the recovery pattern and for the chunking and backtick traps rather than looking for them restated here. Measured 2026-09-09 on a throwaway bead created and disposed of for the purpose (`rf2-i834`): closed with a 419-character reason, it read `close_reason` 419 and `closed_at` a timestamp; one `bd update <id> --status open` later it read `close_reason` **0** and `closed_at` **null**, and a probe for the reason's sentinel token across the WHOLE stringified record — not merely `notes` — read **0**. `bd` prints its ordinary success line either way, so nothing on screen says a field was emptied. The same was measured that day on `rf2-dokz` and `rf2-z5lv`, both closed by the mayor and reopened by the merged-PR audit within the hour. **It bites HERE specifically because this project treats close reasons as NORMATIVE RECORDS** — a ruling is often the close reason of a closed dependency, which is why `bd gc`'s decay phase is banned and why the backlog-reread loop sends you to read them — and because an audit reopening is the system WORKING, so the loss lands precisely on the beads being worked twice, whose account of what the first pass actually did is the one most wanted. **The obvious detection probe cannot work, and that is worth stating because it is the first one a careful reader reaches for**: you cannot find reopened closures by listing non-terminal beads that still carry a `close_reason`, because the reopen removes its own evidence. Measured over the export at HEAD: **0** of the 33 non-terminal beads carry one, against a control of **1084 of 1085** closed beads that do — the probe is live, it simply cannot see this. **Recovery is complete and cheap by two independent routes, and neither needs the tool's cooperation.** (1) `.beads/issues.jsonl` in git history is a full database export, so any checkpoint commit made while the bead was closed carries the text: `git show <commit>:.beads/issues.jsonl | jq -r --arg i <id> 'select(._type=="issue" and .id==$i) | (.close_reason // "" | length)'`. **Select on the IDENTITY field — a bare grep for the id is instrument item (f) and here it fails in the reassuring direction**: bead ids cross-reference each other in dependency lists and close-reason prose, so on checkpoint `4cbaba034c` five records MENTION `rf2-dokz` and exactly one IS it, and `grep '"rf2-dokz"' | head -1 | jq` duly reported a `close_reason` length of 0 on the very checkpoint carrying 5181 characters of it. **And the window is NARROW** — exactly one of the last fourteen checkpoints carried that text — so walk a range and never conclude from the newest. (2) `bd history <id> --json --limit N`, whose per-commit snapshots nest the fields under `.Issue`: on the throwaway bead the lengths read `[0,419,0]` newest-first with exactly one snapshot carrying the sentinel, and four carried it for `rf2-dokz`. **Take the `--limit`, and size the output before anything reads it — the unbounded form on a large bead is GIGABYTES, and it does not fail, it SUCCEEDS.** A bead keeps a full record copy per commit, so history size is record size times snapshot count: measured 2026-09-16 on `rf2-uelji`, the unbounded form returned **1,591,359,019 bytes (1.59 GB)** at exit 0 in 14 seconds with nothing on stderr, against **200,683** at `--limit 1` and **602,043** at `--limit 3` — about 200 KB per snapshot across some 7,900 of them. So the idiom this bullet used to invite, piping it straight into `jq`, is not a slow command but a dead session, and the bead most likely to need recovering is the one that takes the damage, because a record grows large by being argued over. **Redirect to a FILE and `wc -c` it first**, and raise `N` only as far as the walk needs. **The snapshot is NOT truncated**: the same `notes` came back byte-identical from `bd show` and from `--limit 1`, 193,646 bytes, 2.95x the 65,535-byte `TEXT` ceiling — so a short answer here means the field was genuinely empty at that commit, never that it was clipped. **For a large bead route (1) is simply the better route** — a checkpoint export is complete and one `git show` away, where route (2) has to be bounded and sized before it can be read at all. Restore with `bd update <id> --append-notes` (never `--notes`), under a heading naming it a RESTORED CLOSE REASON and citing the commit it came from, so nobody reads it as newer than the audit note below it. **AND A DISPATCH CLAUSE, because this one cost a real cycle**: a brief telling a worker to "read the bead's close reason" is UNSATISFIABLE on a reopened bead, and the worker reads the absence as its own failure rather than as the tool's — two live workers were briefed that way on 2026-09-09 and had to be messaged mid-flight. So either restore the reason into the notes BEFORE dispatching, or do not cite it. Record the behaviour and stop there: no wrapper around `bd`, no gate, nothing to keep in sync.
- **Per-PR and per-run bookkeeping goes on the bead and in the commit, never into a memory — `bd remember` is for findings that GENERALISE** (ruled under rf2-ornb). An audit of one merged PR is already recorded three times — in its `chore(beads): audit merged PR` commit, in the bead's own notes, and on the PR itself — so a memory copy adds nothing. **The rule lives here because its violator does not**: the writer is a generated `.git/codex-pr-audit-<PR>/checkpoint.py`, re-emitted per PR by an out-of-repo merge-audit harness, so no tracked file can enforce it and this bullet is the only durable artefact a future harness author reads. The legacy per-PR receipts are deleted and survive in git history — `MSYS_NO_PATHCONV=1 git show 4520025651:.beads/issues.jsonl | jq -r --arg k merged-pr-audit-pr-9664 'select(._type=="memory" and .key==$k)|.value'` recovers one — and "was PR N audited?" is `git log --oneline --grep='audit merged PR #N'`. **Nine `merged-pr-audit-*` keys stay; leave all nine**: the rolling `merged-pr-audit-cursor`, which is the key the harness's resume logic recalls, and eight method memories — `merged-pr-audit-cursor-correction-pr-7568-timezone-comparison` among them, a correction record that shares the cursor's prefix rather than a second cursor.

## Git Conventions

- **No AI attribution in commits or PRs.** Do not add `Co-Authored-By: Claude ...`, `🤖 Generated with [Claude Code]`, or any similar trailer to commit messages or PR descriptions. Commit and PR text should read as the user's own work. **Your harness says the opposite — a session-level reminder tells you to end every commit message with those exact trailers — and THIS FILE WINS.** Say so in the report when you decline them. A `commit-msg` hook (block `commit-attribution`, installed by `sh scripts/install-git-hooks.sh`) refuses the message locally, and `scripts/check-commit-attribution.sh` grades both the commits a PR introduces and the PR body, as a step of `test.yml`'s `beads-pr-boundary` job — **the check to read is `PR guards (no tracker database, no AI attribution)`**, so a red there on a PR touching no `.beads` path is this guard, and the step name in its log says which surface fired. What is refused is a line that IS the attribution — a whole-line `Co-Authored-By:` naming the assistant, a whole-line `Claude-Session:`, a generated-by marker line, or a bare session URL on its own line — never prose that mentions one; to quote a trailer on purpose, indent it one space. The PR body is read from the frozen event payload, so after correcting a body a re-run re-reads the old text; only a new event clears it. **The commit's identity is graded too**: a commit whose author or committer email is `noreply@anthropic.com` is refused, so set `git config user.name` / `user.email` in a session with no git identity of its own, and rebuild a branch already carrying one with `git rebase --exec 'git commit --amend --no-edit --reset-author' <base>`. The three trailer-carrying commits already on trunk are accepted and history is not rewritten (rf2-2e8f); do not reopen that.

Per `docs/the-mayor-method/`, the `ai/` directory at repo root holds all AI working artefacts. **The tree is local-only** (`/ai/` is in `.gitignore`) — don't `git add` under it. `git ls-files ai/` returns nothing, and `scripts/check-ai-tracking-ratchet.sh` fails any PR that puts a path back under `ai/`.

Per-decision dossiers, when Mike asks for them, go in `ai/decisions/` as one file per decision.

Don't hunt or "fix" existing dangling citations, and this is deliberately not a gate.
- **Timestamp format**: full datetime with timezone, not just date. e.g. `2026-05-09 13:30:57 AUSEST`. Use `date "+%Y-%m-%d %H:%M:%S %Z"` to fetch.

## Workflow

- **Always dispatch beads to a background agent when sensible.** Don't ask permission for clear-cut implementation work, mechanical fixes, or follow-on tasks where the direction is set. Keep the work flowing. Only pause for genuine decisions Mike hasn't made.
- **Minimise merge conflicts when dispatching.** Hot-zone files (`spec/Conventions.md`, `migration/from-re-frame-v1/README.md`, `spec/API.md` together with its two `spec/api-manifest*.edn` sidecars, `spec/Tool-Pair.md`, `spec/Spec-Schemas.md`, `spec/009-Instrumentation.md`, `spec/006-ReactiveSubstrate.md`, `spec/005-StateMachines.md`, `spec/002-Frames.md`, top-level `implementation/deps.edn`, `implementation/shadow-cljs.edn`, `.github/workflows/*`, `.github/scripts/report-changed-surfaces.sh` and its mirror `implementation/scripts/_changed-surfaces.test.cjs`) are sequential, never parallel — two beads touching the same hot file = sequence them, second waits for the first's PR to merge. Isolated surfaces (single-artefact `implementation/<feature>/src/`, new-file additions, test-only dirs `implementation/<feature>/test/`, `examples/<substrate>/<example>/`) are safe to parallel.
  - **`spec/API.md` and the two manifest sidecars are ONE holding** — `lint.yml`'s `api-manifest` job grades all three together, so a public-name change moves all three. - **The dispatch ledger is `ai/worktree-agent-ids.tsv`, and THIS BULLET is its contract** — the file is local-only and its own header has drifted from its rows, so don't read the header. One tab-separated line per dispatch, five fields, in this order: **`worktree`** (the absolute path, never the bare directory name), **`agentId`**, **`dispatched`** (timestamp), **`branch`**, **`beads`**. - **Fast-forward `main` onto `origin` immediately after every PR merge.** Run `git fetch origin main && git merge --ff-only origin/main` as the very next step after `gh pr merge --rebase` — no exceptions, no batching several merges first. **Never the `git pull` form**: a pull takes its target from `FETCH_HEAD`, a scratch file any concurrent git process in the same checkout rewrites, so it can abort on a clean, undiverged tree or silently fast-forward the trunk onto a feature branch — a ref can't be captured that way. Keep the `&&` so a failed fetch can't be followed by a merge against a stale ref. **When the merge aborts, the message names the cause, and the remedies are not interchangeable**: `local changes would be overwritten` is an uncommitted `.beads/issues.jsonl` (checkpoint, `git checkout HEAD -- .beads`, retry — see [Beads durability](#beads-durability)); `Not possible to fast-forward` is your own committed checkpoint diverging from the racing post-merge audit push (`git fetch origin main && git rebase origin/main`). Then verify the tree rather than the line git printed: `git rev-parse HEAD` must equal `git rev-parse origin/main`, and read both again before believing a mismatch, because the audit push can land between the two reads. The full drill is *After each merge* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#after-each-merge). Mike glances at his local working tree to track progress, and dispatches worktree off `origin/main`, so staleness misleads both.
- **Mayor only — the merge criterion's repo-specific traps.** The criterion itself is [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#1-merge) §1, clauses 1–5; these concretions are specific to this repository's workflows and `gh`, so they live here. The first three fail OPEN — each ADMITS a merge that should have been blocked. Full measured accounts: `bd recall claude-md-merge-criterion-traps` and `bd recall claude-md-check-band-clock`.
  - **(a) The job-key discriminator needs TWO LEADING SPACES**: `git diff <merge-base> origin/main -- .github/workflows/ | grep -cE '^\+  [a-z][a-z0-9_-]*:[[:space:]]*$'`. Job keys nest under `jobs:`, so the unindented form always reads 0. **A non-zero count is a question, not an answer**: count removals with the mirrored `^-  …` pattern (added == removed with pairwise-corresponding names is a RENAME, moving the band by zero); confirm each matched key sits under `jobs:` — its block carries `runs-on:`, or `uses:` for a reusable-workflow call — rather than being an `on:`-block trigger key at the same indent; and count only keys in files whose `on:` carries `pull_request`. **A trigger-only change is still a matrix change**: zero job definitions added is compatible with existing jobs newly scheduled on PRs (a job gated off by `if:` still contributes a skipped row), so when a match turns out to be a trigger, ask what the new block schedules. The confirmation is the rollup TOTAL of a PR merged after the suspect commit — one whose files match that workflow's `paths:` filter, if it has one, or it hands back the pre-change number.
  - **(b) Pass the full 40-character head oid to `gh run list --commit`**, taken from `gh pr view --json headRefOid` — never extended by hand from an abbreviated sha. An abbreviated or fabricated sha returns `[]` and clears the live-runs check vacuously; a full rollup beside an empty run list is the tell.
  - **(c) Aggregator rows are REAL JOBS — never subtract one from the band, and never merge on one alone.** `All required checks passed` is `test.yml`'s `all-required-passed`, and other workflows carry their own: an aggregator is a job whose block carries `if: ${{ always() }}` and whose `needs:` lists other jobs in its own file. Enumerate them from the workflow YAML, never from rollup display names. `needs:` cannot span files, so each covers its own workflow alone, and a green aggregator is not a green rollup.
  - **Band timing: compare in one zone, or by ancestry.** `git log --date=iso` prints local time and `gh`'s `mergedAt` prints UTC. Use the COMMITTED clock (`TZ=UTC git log -1 --date=iso-local --format=%cd <sha>`) — or skip clocks and ask `git merge-base --is-ancestor <matrix-commit> <pr-merge-commit>`. To confirm the matrix has not moved, take the control from the target: with `LAST=$(git log -1 --format=%H -- .github/workflows/)`, `git diff --name-only "$LAST^" origin/main -- .github/workflows/` must list at least one file and `git diff --name-only "$LAST" origin/main -- .github/workflows/` none. A fixed offset such as `origin/main~40` expires silently as the trunk advances.

- **Mayor only — granting the shadow-cljs build lane** (the worker half is in `AGENTS.md`). Announce-and-take is not a lock: an announcement NOTIFIES and does not ASK, so two correct announcements compose into a collision. The coordinator is the arbiter. **First acquirer holds**; **never grant on a release message alone** — a release is evidence about the past, so check nobody has announced a take since; **grant explicitly to ONE worker and keep a queue**, telling the next worker its place is held so it does not have to ask. The pre-grant census counts `node.exe`/`java.exe` machine-wide with no path filter — it fails closed, so never narrow it. When a worker has to yield because of a coordination failure, tell it plainly that the fault was not its own. Full account: `bd recall claude-md-shadow-cljs-build-lane`.
- **Instrument hazards — ways the tools on this machine misreport.** Each hands back a clean-looking answer, and every one was reached by a worker taking the obvious route. Each entry below is the symptom and the guard; `bd recall claude-md-instrument-<letter>` holds its full measured account, and `bd memories <topic>` finds related ones — search before any non-trivial census, sweep or worktree operation. Two habits cover most of them: **take the control from the target** (run the probe once against something it must find, so a zero means absence rather than a broken instrument), and **read the runner's own exit code and stderr, never a pipeline's**. The letters are labels, not a census: a new item takes the next label — (aa), (ab), (ac) … — and existing letters are never renumbered, because code comments cite them.
  - **(a)** Bash `grep -iF` aborts here (exit 134, empty stdout — an honest-looking zero; the `Aborted` line goes to the shell's stderr, not grep's), and an `|| grep -cF` fallback answers a different, case-sensitive question. Use the ripgrep-backed search tool, or `grep -F -f <patternfile>`.
  - **(b)** Never pipe a census through `head` when the count is the deliverable — the cap reads as the population. Take the count separately; write "first N of M".
  - **(c)** A census needs two TOKEN axes, not merely two instruments: the same mechanism is spelled differently in different files, and each spelling finds files the other misses.
  - **(d)** From Git Bash, `git show <ref>:<path>` mangles when the ref contains a slash and the path begins with a dot (`origin/main:.gitignore` becomes `origin\main;.gitignore`, exit 128). Tell it from an honest not-found by the error text, never the exit code; prefix `MSYS_NO_PATHCONV=1`, or use `git grep -F <needle> <ref> -- <file>`.
  - **(e)** `jq` writes CRLF here. Joined into an alternation, only the last alternative matches; handed back as an argument (`jq -r … | while read -r id`), the trailing `\r` makes `bd show` return an error OBJECT on stdout instead of the array — check the document is an array before indexing it. Wherever one side of a comparison travelled a `jq` pipeline and the other did not, check that seam: `tr -d '\r'` both sides of a literal comparison; adapt a regex to its data rather than normalising both. Multi-needle search is `grep -F -f <file>`, with a control needle that travelled the same pipeline as the data. **After editing any `w/crlf` file, take three numbers with Python reading the bytes** — total CR, CRLF pairs, and bare LF (line feeds minus CRLF pairs) — and require CR == CRLF **and** bare LF == 0.
  - **(f)** A pathspec with a wildcard must match the WHOLE path: `implementation/*/src` matches nothing (git exits 1, and `| wc -l` turns that into 0), while `implementation/*/src/*` works. The same class reaches the tracker: select a `.beads/issues.jsonl` record on its identity field (`jq -r --arg i <id> 'select(.id==$i)'`), never with `grep '"<id>"'`, which also finds the records that merely mention the id.
  - **(g)** A census that treats prose as evidence fails both ways: a synonym list misses the best-documented code, and `\b` matches across a hyphen (`\btransient\b` hits `host-transient`). Match the spelling you mean (`(transient `, `assoc!`), and read a ranked file before believing its rank.
  - **(h)** From Git Bash, a leading-slash Windows flag is rewritten into a path (`schtasks /query` runs as `schtasks 'C:/Program Files/Git/query'`), exit 1 with nothing on stdout — silent behind `2>/dev/null |`. Prefix `MSYS_NO_PATHCONV=1`, or ask PowerShell.
  - **(i)** `ls <dir> | wc -l` omits dotfiles — including `node_modules/.bin`, whose loss breaks every build. Count with `ls -A` or `find <dir> -mindepth 1 -maxdepth 1`, or read `remove-worker-worktree.sh`'s `CANARY_BEFORE=`/`CANARY_AFTER=` lines.
  - **(j)** Inside an ERE bracket expression, `\]` is a literal backslash and the class closes at that `]`, so `[ )\]]` means one of space, `)` or backslash FOLLOWED BY a literal `]`. Put `]` first (`[])(]`), or use a named class.
  - **(k)** `bd show` renders rather than prints: it hard-wraps and deletes backticks and `<placeholders>`, so a probe of its output reads 0 on text that is there. Probe the field: `bd show <id> --json > <file>.json`, then `json.load(open(path, encoding='utf-8'))[0]['notes']` (a `jq -r` extraction brings CRLF, per (e)). Hard-wrapped plain files have the same wrap problem, so keep a probe short enough to sit inside one line.
  - **(l)** A repeated `--status` on `bd list` keeps only the LAST one, silently. Use the comma form (`--status open,deferred`), or filter an unfiltered `bd list --limit 0 --json` with `jq`.
  - **(m)** `git ls-files A B -- C` UNIONS every pathspec — it has no revision slot, so the `--` is inert. Scope every pathspec to the subtree (`-- 'bench/**/*.clj' 'bench/**/*.cljc'`), or filter the output.
  - **(n)** Native Windows Python reads `/tmp` as `C:/tmp` while Git Bash maps it to the user's Temp directory — the same string names two files and every write "succeeds". Hand off between a Python step and a shell step only through one absolute Windows path (the session scratchpad), and verify by reading back a sentinel.
  - **(o)** The Bash tool halves runs of backslashes anywhere in its command text — quoted heredocs and plain single-quoted arguments alike (`\\` arrives as `\`) — while a lone backslash survives, which is what hides it. Write anything carrying backslashes with the Write tool, and verify by reading a backslash-bearing line back out of the file.
  - **(p)** `gh pr view --json statusCheckRollup` gives a still-running check `conclusion: ""` — a string, not null — so a null guard counts pending as failed. Gate on `.status` first: `select(.status=="COMPLETED" and (.conclusion|IN("SUCCESS","SKIPPED","NEUTRAL")|not))`.
  - **(q)** The rollup reports `status`/`conclusion` in UPPERCASE and `gh run list --json` in lowercase; a lowercase filter over the rollup matches nothing and reads a red PR clean. Case-fold both sides: `(.status|ascii_downcase)`, `(.conclusion // "" | ascii_downcase)`.
  - **(r)** Which `git hash-object` form reproduces a committed blob depends on the file's INDEX eol (`i/lf` wants the default form, `i/crlf` wants `--no-filters`). Compare both forms against `git rev-parse "HEAD:<path>"` and accept a match by either; `git diff --quiet HEAD -- <path>` is an independent check. Never conclude "restore failed" from one form.
  - **(s)** A bare `grep -c $'\r' <file>` intermittently reads 0 on a file full of carriage returns, and `grep -c` counts matching lines rather than bytes anyway. Count carriage returns with Python: `open(p,'rb').read().count(b'\r')`.
  - **(t)** `\b` after `!` or `?` never matches before a space, `)` or newline, so `\(skip!\b` misses every real call site — and this tree's symbols end in punctuation constantly. Make the delimiter explicit (`\(skip![\s)]`), or drop the assertion where the open paren already anchors.
  - **(u)** `sed -i` on a `w/crlf` file rewrites every line ending to LF, even when nothing matched. `git diff` stays silent (except on the one `i/crlf` file, `spec/011-SSR.md`) while `git status` reads ` M`. Ask `git ls-files --eol <path>` first, and edit with the Write/Edit tools or Python bytes.
  - **(v)** `.github/scripts/report-changed-surfaces.sh` takes PATHS: handed revisions it reports every surface false at exit 0. Call it as `report-changed-surfaces.sh $(git diff --no-renames --name-only <base>...HEAD)`, with a control path known to arm surfaces. It never checks existence, by design, so a deleted path still classifies.
  - **(w)** `clj-kondo --fail-level error` exits 0 on findings graded below error — and this repo sets `:unresolved-symbol` to `:warning`, so a reference left dangling by a deletion passes. Run without the flag (a warning exits 2, an error 3), or read the finding lines and the warning count; for a deletion, census the deleted names instead. Don't change the gate's flags.
  - **(x)** An incremental shadow-cljs compile does not re-expand a macro whose input is a non-source file. A red that turns green on a cold rebuild with no edit was never about your tree. A macro that reads a data file does it through `implementation/spec-resource/` (`re-frame.build.spec-resource`), which records the dependency so a data-only edit recompiles the consumer.
  - **(y)** `gh run view --log --job <id>` refuses while any OTHER job in the run is unfinished, even though the named job has completed. Fetch a completed job's log with `gh api repos/<owner>/<repo>/actions/jobs/<id>/logs`; `gh run view --job <id>` reports that job's state while the run is open.
  - **(z)** This repo's quiet test reporter prints `Testing <ns>` only on a namespace's first failure, so grepping a green log for your namespace reads 0 whether it ran or not — and the names a green log does carry are the per-namespace isolation roster. Predict the test and assertion count delta from the diff and compare it against a baseline taken at your merge base.

## Architecture Overview

**The spec is the artefact; the code is downstream.** The normative description of re-frame2 lives in [`spec/`](spec/) (~46K lines across 50+ documents); [`implementation/`](implementation/) is a CLJS reference that validates the spec end-to-end. See the repo-root [`README.md`](README.md) for the marketing-voice introduction and the project-layout map, and [`spec/README.md`](spec/README.md) for the spec index.

`implementation/ui/` (re-frame.ui) and `implementation/freehand/` (re-frame.freehand) are **removed permanently** — not a tree mid-surgery, and never a surface to build on. The **reserved-kind contract** stays: `:rf.adapter/ui`, `:rf.adapter/freehand` and `:rf.adapter/helix` are reserved and never recycled, per the `:rf.adapter/*` row of `spec/Conventions.md`'s reserved namespaces. Other retirement narration that survives in prose is history, and goes under the present-tense rule in [Conventions & Patterns](#conventions--patterns). The `adapters/` (Reagent, reagent-slim, UIx) are **first-class and actively supported**, and `fresco/` (re-frame.fresco) is the re-frame-native view layer.

`tools/` holds dev/inspection tools consuming the Spec 009 instrumentation API and Tool-Pair contract. They are bundle-isolated from production builds: **nothing in `implementation/` may `:require` from `tools/`.**

## Conventions & Patterns

Normative conventions are catalogued in [`spec/Conventions.md`](spec/Conventions.md) — reserved namespaces (the `:rf/*` single-root scheme), reserved fx-ids, reserved app-db keys, the feature-modularity id-prefix convention, and packaging conventions. [`spec/Principles.md`](spec/Principles.md) carries the nine AI-first practical principles. [`spec/Ownership.md`](spec/Ownership.md) maps every contract surface to its owning spec — the "where does X live?" reference.

**Comments, docstrings, human-readable test prose and `spec/` prose describe the code and the contract as they are now, and why — never how they got here; git history, PRs and beads hold that story.** Test each sentence: would it still be true and worth saying had the code been written this way on day one? If it is true only because of history, rewrite it as a present-tense reason ("Z, because X breaks Y"), or delete it when no reason survives; provenance goes outright — bead ids, PR numbers, dates, review waves, audit and ruling narrative. What stays: present-tense contract that merely uses a history word ("`:rf.adapter/ui` is reserved and never recycled"), pointers a reader can open (spec section references, `docs/EP/` references used as pointers), identifiers of every kind, and strings the program emits or a test asserts on (the epic's calibration says when a user-facing message's provenance goes). The detail is on epic `rf2-tv5ac` — read its description with its newest `== CALIBRATION` note, which wins where the two differ.
