# Project Instructions for AI Agents

This file provides instructions and context for AI coding agents working on this project.

## Project stance

> Posture is that we are pre-alpha and focused on elegance, power and a masterpiece.
> But we are not over-engineering or gold plating. Also, we trust the programmer.
> We're trying to facilitate high productivity for them (and the AI they use) via a
> library with excellent ergonomics and low friction. We don't need to litigate every
> last fine detail and drown in the minutiae.

**That quoted block is the stance, and it is pasted VERBATIM into every dispatch preamble — never summarised, never trimmed to fit.** The reason is in its shape: the lenses say what good looks like, and everything after them says when to STOP. A paraphrase keeps the memorable half and drops the restraining one, and what survives does not read as incomplete — it reads as a stance that wants MORE of everything, which is precisely the failure the second half exists to prevent. Two clauses do the most work and are the first to be lost: *trust the programmer* rejects a nagging diagnostic, and *don't litigate the minutiae* lets an item die with its reasoning recorded instead of consuming a worker.

**This file is the stance's home, and that is deliberate rather than incidental.** [`docs/the-mayor-method/dispatch-prompt-template.md`](docs/the-mayor-method/dispatch-prompt-template.md) does NOT carry it and must not: that page is the reusable, OS-neutral method, and it says in terms that the stance is project-specific, that it is "PASTED rather than pulled", that it "lives in its own file", and — the sentence that matters here — **"Do not send the worker to a file that does not carry a stance."** So do not go looking for it there, and do not add it there.

**It is written down HERE because it was measured to have no tracked home at all (2026-09-09).** The full text appeared in exactly ZERO git-tracked files as a stance block — the only hit anywhere was inside `.beads/issues.jsonl`, i.e. quoted in bead prose, against a live control of 70 tracked files carrying `hot-zone`. Its one working copy was `ai/dispatch-blocks.md`, which is **gitignored** (`/ai/`), and whose own header names `dispatch-prompt-template.md` as the source it was regenerated from — a file that, by the design above, does not contain the stance. Regenerate the other three from the template; take the stance from here.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

## Session Completion

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   ```bash
   git fetch origin main && git rebase origin/main
   bd dolt push
   git push
   git status  # MUST show "up to date with origin"
   ```
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**
- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds

## Beads durability

`.beads/issues.jsonl` is a full-database export, not an ordinary source file. `bd` rewrites it in **every** checkout, so each worker worktree carries a snapshot of the tracker as it stood when that worktree was created. Committing that snapshot **time-travels the tracker**: beads closed since it reopen, beads filed since it vanish. PR #6677 landed exactly that — 135 insertions / 136 deletions of pure collateral.

- **The tracker database is the mayor's to commit.** Worker branches carry code, spec, docs and tests — never `.beads/issues.jsonl`, `.beads/metadata.json`, or any other database-derived path. The human-authored config (`.beads/README.md`, `.beads/config.yaml`, `.beads/.gitignore`, `.beads/hooks/**`, `.beads/PRIME.md`) is fair game from anywhere. **`.beads/PRIME.md` is hand-written prose, not an export**: `bd prime` reads it and emits it INSTEAD of its own ~1.8 MB default at SessionStart and PreCompact, so it is the file that decides what rides in every session's opening context — edit it like any other doc, and re-sync it by hand against `bd prime --export` after a `bd` upgrade, since the override suppresses upstream changes to that default. It is advice from a tool and **this file outranks it**; never cite it as "CLAUDE.md says". A pre-commit hook enforces this in linked worktrees **once installed** — run `sh scripts/install-git-hooks.sh` (or `scripts/install-git-hooks.ps1`) once per clone; worktrees share the primary checkout's hooks directory, so one run arms them all, and `--check` answers whether a checkout is currently guarded **through its EXIT CODE ALONE — on success it prints nothing at all** (0 installed and current, 1 otherwise; it writes only when it fails, as its own usage line says). **So never read it through a pipe.** `… --check | tail` hands back `tail`'s status, and empty output beside a 0 looks identical whether the hooks are armed or missing — which is the pipeline-status hazard this file catalogues elsewhere, arriving through a guard everyone is told to run. Measured 2026-09-08 on a checkout whose four hooks WERE installed: piped through `tail` it printed nothing and the pipeline exited 0; re-run bare it printed nothing on stdout, nothing on stderr, and exited 0 — so the piped form cannot separate that case from an unguarded one. Run it bare and read `$?`; to SEE the answer rather than infer it from silence, list the hooks directory and expect `commit-msg`, `post-merge`, `post-rewrite` and `pre-commit` (`core.hooksPath` unset means `.git/hooks`). `scripts/check-beads-pr-boundary.sh` is the CI arm. See `scripts/git-hooks/README.md`.
- **Never resolve a `.beads` conflict with `--theirs` or `--ours`.** Both sides are whole-database exports, so picking one wholesale discards every bead the other side recorded. Resolve then **regenerate**: take the incoming file (`git checkout --theirs .beads/issues.jsonl`), re-import it, and let `bd` re-export from the merged database.
- **Checkpoint first, then clear `.beads`, then update — and never stash.** An uncommitted `.beads/issues.jsonl` makes the rebase step below abort (`cannot rebase: You have unstaged changes`), freezing HEAD at a stale base, so the file does have to be cleared. Rebase refuses on *any* unstaged change, not only one the incoming commits would overwrite, so this bites even when nothing upstream touches the file. But clearing it *after* a `bd close` or `bd create` reverts the export to its pre-close state, and the next checkpoint writes that revert back over the database — the close evaporates (rf2-51uz1: rf2-5e8zv was reopened exactly this way, and commit `e80786e007` records three more re-closed by hand). The order is therefore fixed, and a checkout of `.beads` must never follow a tracker mutation within a tick:

  ```bash
  sh scripts/beads-checkpoint.sh                   # export from the database, verify, commit
  git checkout HEAD -- .beads                      # now safe: HEAD carries the tracker
  git fetch origin main && git rebase origin/main  # explicit ref, not a pull — see below
  ```

  **Take that third step's target from `origin/main`, and don't restore the `git pull --rebase origin main` it replaced — naming the remote and branch does not make a pull equivalent.** A pull is two steps: it fetches into `FETCH_HEAD`, then rebases onto whatever `FETCH_HEAD` says by the time the rebase reads it. Naming remote and branch constrains only the fetch half, so the rebase half still takes its target from a scratch file that any concurrent git process **in the same checkout** rewrites — which is why the named form was measured aborting with `Cannot rebase onto multiple branches` on a clean, undiverged tree, exactly as the bare form had (2026-09-01 22:4x AUSEST, mayor checkout, six worker worktrees live). The reasoning is the one already written out for the merge case in the fast-forward bullet under [Workflow](#workflow) — *a ref can't be captured that way* — and this sequence was simply left behind when that case was fixed; keep the `&&` for the same reason that bullet does, so a failed fetch can't be followed by a rebase against a stale ref. Read the session-completion block above the same way: it is tool-generated — and so is the copy of it in `AGENTS.md`, which sits inside a `BEADS INTEGRATION` marker carrying the same block hash — so if a regeneration restores the pull form in **either**, correct it in both rather than following it. The generator is `bd` itself, not anything in this repository, so there is no template here to fix; the two copies have to be kept in step by hand.

  Naming remote and branch is still worth doing on the fetch, which is the half it does reach: the earlier instance recorded here was of the **bare** form, whose own fetch is unconstrained too (measured 2026-08-29 22:31 AUSEST, mid-checkpoint, one line after a `git fetch origin worker/<branch>`). The contaminating process is a concurrent one in the same checkout rather than a peer worktree — `FETCH_HEAD` is per-worktree, as `git rev-parse --git-path FETCH_HEAD` resolves inside a linked worktree's own git directory — and the mayor checkout, where several git processes run at once, is where that bites.

  **Do not pipe any step of this sequence, and do not chain past one with `&&` through a filter.** A pipeline's exit status is its *last* command's, so a step written as `… 2>&1 | tail -3 && bd dolt push && git push` reports `tail`'s success and walks straight past a fatal abort with the rebase never performed. That is how the 2026-09-01 abort above went unseen, and why it was inert only in the sense that the push behind it still landed. It is the same hazard as piping a gate through a filter, reached through git instead of a gate runner.

  `sh scripts/beads-checkpoint.sh --pre-pull` (or `-PrePull` on the `.ps1`) answers "would clearing `.beads` throw tracker state away?" — exit 0 means the checkout is safe. **Do not `git stash`**: stashes are repo-global and contaminate every other worktree in flight.

  **This sequence answers one abort message and only that one.** The other cause — the checkpoint you just made having diverged from a racing push — surfaces as `Not possible to fast-forward`, and that is the fast-forward bullet's `git merge --ff-only origin/main` speaking, not the rebase step here, which rebases your checkpoint on top and exits 0. Clearing an already-clean `.beads` is inert against it either way. Branch on the message; both branches are set out under *After each merge* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#after-each-merge).
- **A checkpoint re-exports; it never trusts the working file.** `scripts/beads-checkpoint.sh` (POSIX; `.ps1` sibling for Windows) runs `bd export`, refuses an empty or badly shrunken result, and commits only `.beads/issues.jsonl`. That ordering is what makes a reverted file unreachable: the export is regenerated from Dolt before anything reads it. A hand-rolled `git add .beads/issues.jsonl && git commit` cannot make that guarantee — it commits whatever the last checkout left behind.
- **The same floor is in the pre-commit hook, so a plain `git add` cannot route around it (rf2-or8te).** The checkpoint's guard only protects commits that go through the checkpoint, and twice an empty export reached main by a path that did not: `7aea52459` (2026-06-10, 7172 rows) and `4d8042d80d` (2026-07-26, 2573 rows), both plain `git add` from the mayor checkout, both leaving `git status` clean afterwards. The hook now refuses any staged `.beads/issues.jsonl` below 90% of HEAD, from every worktree. **An empty export is a REGENERATION event, not a data-loss one** — the Dolt database is the source of truth, `sh scripts/beads-checkpoint.sh` rebuilds it, and restoring an older export from git history would time-travel the tracker instead. For a genuine mass delete the message names the escape: inspect with `bd status`, then `git commit --no-verify`.
- **Do not set `git update-index --skip-worktree` on it.** It hides the local edit from `git status` but still blocks the update — the same frozen HEAD, now with nothing on screen to explain it. Stage explicit paths instead of `git add -A`.
- **`bd update --notes` REPLACES the notes field; `--append-notes` is the flag that adds to it.** The loss path here is the bead's own content rather than the export, and it is silent in the same way: `--notes`' help text reads *"Additional notes"*, which is how a reader takes it, nothing errors, `bd` prints its normal success line, and the damage stays invisible until somebody re-reads the bead — on a held bead, possibly never. Measured across five beads in one session (~72,800 characters, `rf2-9wmqd` 46569→3294 the worst), and it had happened before: `rf2-y1jkm` carries an earlier account of the same mistake, surviving only because its author restored it by hand. **Recovery is complete and cheap, so this is not an occasion to panic** — `.beads/issues.jsonl` in git history is a full database export, so the pre-damage notes sit in any checkpoint commit predating the update: `git show <rev>:.beads/issues.jsonl`, rebuild as old + newline + current, write back. One trap in that recovery is worth knowing, because it fails silently where the rest of this is merely quiet: a value past roughly 27,000 characters is rejected by the shell with a non-zero exit and **no message at all**, so split at line boundaries into ~18,000-character chunks — `--notes` for the first, `--append-notes` for the rest — and confirm by probing for known content from the start, middle and end rather than by comparing lengths, which chunking shifts by a byte or two. **A second trap in the same act, and this one DAMAGES the note rather than rejecting it: BACKTICKS inside a DOUBLE-QUOTED shell string are command substitution**, so the backticked words are deleted and whatever they print is spliced in where they stood. `bd` prints its normal success line either way, so the note lands looking healthy while the passage carrying the evidence is gone — and a note about this repo is exactly where backticks cluster, since every path, var and flag in it wants a code span. It damaged a note on `rf2-fmst` in precisely the places quoting the measurements. Measured both ways: ``"epoch anchor `echo REMOVED-BY-SUBSTITUTION` restored"`` arrives as `epoch anchor REMOVED-BY-SUBSTITUTION restored`, while the identical line through a QUOTED heredoc (`<<'EOF'`) arrives verbatim with its backticks intact. **The guard: write the note with a quoted heredoc and pass it as `"$(cat <file>)"`** — the same move the chunking above already needs, so both traps in this bullet share one remedy. If the heredoc will not parse, build the file by any other means and still pass it as `"$(cat <file>)"`: what protects the note is that the content reaches `bd` from a FILE rather than through a double-quoted shell string, and the heredoc is one way to build that file rather than the thing doing the protecting.
- **Reopening a bead ERASES its `close_reason` and its `closed_at`, and the text is not copied into `notes` or anywhere else.** Same class as the `--notes` trap above — a silent field-level loss with a cheap git-history recovery — so read that bullet for the recovery pattern and for the chunking and backtick traps rather than looking for them restated here. Measured 2026-09-09 on a throwaway bead created and disposed of for the purpose (`rf2-i834`): closed with a 419-character reason, it read `close_reason` 419 and `closed_at` a timestamp; one `bd update <id> --status open` later it read `close_reason` **0** and `closed_at` **null**, and a probe for the reason's sentinel token across the WHOLE stringified record — not merely `notes` — read **0**. `bd` prints its ordinary success line either way, so nothing on screen says a field was emptied. The same was measured that day on `rf2-dokz` and `rf2-z5lv`, both closed by the mayor and reopened by the merged-PR audit within the hour. **It bites HERE specifically because this project treats close reasons as NORMATIVE RECORDS** — a ruling is often the close reason of a closed dependency, which is why `bd gc`'s decay phase is banned and why the backlog-reread loop sends you to read them — and because an audit reopening is the system WORKING, so the loss lands precisely on the beads being worked twice, whose account of what the first pass actually did is the one most wanted. **The obvious detection probe cannot work, and that is worth stating because it is the first one a careful reader reaches for**: you cannot find reopened closures by listing non-terminal beads that still carry a `close_reason`, because the reopen removes its own evidence. Measured over the export at HEAD: **0** of the 33 non-terminal beads carry one, against a control of **1084 of 1085** closed beads that do — the probe is live, it simply cannot see this. **Recovery is complete and cheap by two independent routes, and neither needs the tool's cooperation.** (1) `.beads/issues.jsonl` in git history is a full database export, so any checkpoint commit made while the bead was closed carries the text: `git show <commit>:.beads/issues.jsonl | jq -r --arg i <id> 'select(._type=="issue" and .id==$i) | (.close_reason // "" | length)'`. **Select on the IDENTITY field — a bare grep for the id is instrument item (f) and here it fails in the reassuring direction**: bead ids cross-reference each other in dependency lists and close-reason prose, so on checkpoint `4cbaba034c` five records MENTION `rf2-dokz` and exactly one IS it, and `grep '"rf2-dokz"' | head -1 | jq` duly reported a `close_reason` length of 0 on the very checkpoint carrying 5181 characters of it. **And the window is NARROW** — exactly one of the last fourteen checkpoints carried that text — so walk a range and never conclude from the newest. (2) `bd history <id> --json`, whose per-commit snapshots nest the fields under `.Issue`: on the throwaway bead the lengths read `[0,419,0]` newest-first with exactly one snapshot carrying the sentinel, and four carried it for `rf2-dokz`. Restore with `bd update <id> --append-notes` (never `--notes`), under a heading naming it a RESTORED CLOSE REASON and citing the commit it came from, so nobody reads it as newer than the audit note below it. **AND A DISPATCH CLAUSE, because this one cost a real cycle**: a brief telling a worker to "read the bead's close reason" is UNSATISFIABLE on a reopened bead, and the worker reads the absence as its own failure rather than as the tool's — two live workers were briefed that way on 2026-09-09 and had to be messaged mid-flight. So either restore the reason into the notes BEFORE dispatching, or do not cite it. Record the behaviour and stop there: no wrapper around `bd`, no gate, nothing to keep in sync.
- **Per-PR and per-run bookkeeping goes on the bead and in the commit, never into a memory — `bd remember` is for findings that GENERALISE** (ruled under rf2-ornb, 2026-09-08). ## Workflow

- **Always dispatch beads to a background agent when sensible.** Don't ask permission for clear-cut implementation work, mechanical fixes, or follow-on tasks where the direction is set. Keep the work flowing. Only pause for genuine decisions Mike hasn't made.
- **The dispatch ledger is `ai/worktree-agent-ids.tsv`, and THIS BULLET is its contract — the file is local-only and untracked, so its own header is not an authority and has already drifted from its rows.** One tab-separated line per dispatch, five fields, in this order: **`worktree`** (the absolute path, never the bare directory name), **`agentId`**, **`dispatched`** (timestamp), **`branch`**, **`beads`**. Per *Reaping* in [`docs/the-mayor-method/loops.md`](docs/the-mayor-method/loops.md#reaping) the reap test reads the **report**, never a field of this line; `agentId` is the route to it, and **there is no done-sentence field**, because whether to hold report text locally at all is still an unmade operator call. Both recorded drifts came from reading the header instead of this contract: taking the last field for a done-sentence returns a bead id — well-formed, reassuring, wrong, and it would have authorised reaping 17 of 30 worktrees on no report at all — and keying column 1 by bare name made a name-keyed grep return 0 rows for 28 worktrees that had rows (rf2-83z0). The header also cites `.claude/commands/mayor-hygiene.md`, under a directory that no longer exists. **The contract binds the NEXT line, and does not describe the file — when this was written, 34 of 261 rows matched it, 13%.** Measured at that same point: 44 rows did not carry five fields at all and 127 began with something other than an absolute path, because this shape only settled on 2026-08-21 and every conforming row postdates that. **Every figure here is a snapshot of a file that grows each tick, so re-measure rather than quoting them.** And binding the next line is not automatic: of the first TEN rows written after this contract merged, four conformed and **six did not, all six by the author of the contract** — because the shape has no spelling for a worktree the MAYOR occupies, which has neither an agent id nor beads, so the writer improvises, and that improvisation put the record's own timestamp in field 1 and shifted every field by one, which is the positional failure this bullet exists to stop. **A mayor-occupied row uses the same five fields**: the absolute path, `(mayor)`, the timestamp, the branch, `--`. **And a dispatch with NO worktree — a zero-edit research or verification bead — uses them too**: `(none)`, the agentId, the timestamp, `(none)`, the beads, so a path-keyed sweep skips it on an exact match rather than trying to parse prose (the same improvisation recurred in this new position on 2026-09-09, one row in eight reading `(no-worktree: zero-edit research bead)` in field 1 while already carrying `(none)` in field 4). **So read a row's fields; never address them by index.** A positional parse is right about one row in eight and wrong with a well-formed answer on the rest, which is the failure this bullet exists to stop, one level up. Normalising the history is explicitly NOT wanted: the contract is here so the next line is right, not so the old ones are.

(That abort only — a `Not possible to fast-forward` abort is the other cause named in the bullet above, and this remedy does nothing for it.) Run `sh scripts/beads-checkpoint.sh` (it re-exports from the Dolt database rather than trusting the working file), *then* `git checkout HEAD -- .beads`, *then* `git fetch origin main && git rebase origin/main` — never `git pull`, and never piped. Stashes are repo-global and contaminate every worktree in flight — see [Beads durability](#beads-durability) for the full sequence and the `--pre-pull` pre-flight. (The `ai/` tree is local-only and won't show up in `git status`.)

Real-regression coverage lives in substrate contract tests (`npm run test:cljs`), the Xray feature-matrix gate (`npm run test:xray-feature-gate`), bundle-isolation, the perf-bundle gate, and mcp-conformance. **Framework testbeds (`tools/xray/testbeds/`, top-level `testbeds/`) are gated by a DERIVED compile sweep, and it names no build — so a grep for a build id returns an honest-looking zero (rf2-dttg).** `implementation/scripts/check-examples-compile.cjs` reads its roster out of `implementation/shadow-cljs.edn` (every `:examples/*` and `:testbeds/*` build id), so **ask the tool to enumerate its own coverage — `node implementation/scripts/check-examples-compile.cjs --list`, 58 builds when this was written, re-measure — rather than searching for a name.** It runs as `test.yml`'s `cljs-examples-compile` job on the classifier's `examples_compile` surface (armed by `tools/xray/testbeds/*`, `testbeds/*.cljs|.cljc`, `examples/*`, the adapters, the feature artefacts and `shadow-cljs.edn`, but deliberately NOT `implementation/core/*` — a core-only PR is covered by the nightly, where the same sweep runs unconditionally); Docs build from repo root with `mkdocs build --strict` (config in `mkdocs.yml`). **Where the bare `mkdocs` console script is not on PATH — measured here exiting 127, which a pipeline reads as a failed build rather than a missing tool — invoke it as `python -m mkdocs build --strict` (mkdocs 1.6.1 answers that form on this box). Every nomination of `mkdocs build --strict` in this file means EITHER form; do not read a 127 as the docs being broken, and check the entry point before spending a run on it.**

**`mkdocs build --strict` does not cover `docs/design/**`** — `mkdocs.yml`'s `exclude_docs` block deliberately keeps the design trees out of the site (they are working design records, not user-facing documentation), so never nominate it as the gate for an edit confined to that tree. **That block is the authority on what the build cannot see from WITHIN `docs_dir`, and it holds more than the design trees; read `exclude_docs` in `mkdocs.yml` before nominating `mkdocs build` for any path under `docs/`, rather than trusting a list in prose — a prose list drifts, and this one already had, naming two of the six trees the block excluded (rf2-yxuta).** But `exclude_docs` is only one of **two doors**, and the other is the one that catches people: `docs_dir` is `docs`, so anything outside it — `implementation/**`, `examples/**`, `tools/**`, `.github/**`, repo-root markdown — was never a candidate for exclusion and will never appear in that block (`mkdocs_hooks.py` classes `implementation/` as "CLJS source; not docs" and rewrites such references to GitHub URLs). **Absence from `exclude_docs` is therefore not evidence that the build covers a path**; check `docs_dir` first, or the wrong-gate nomination below simply recurs through the other door (rf2-8pb5k).

**But `docs_dir` does not bound the build's reach either, and the third door runs the OTHER way — INTO the build: `spec/` and `migration/` ARE covered by the strict build, because `mkdocs_hooks.py`'s `on_pre_build` hook stages them into `docs_dir` before MkDocs scans a single file** (its `_STAGE` table maps `spec` → `docs/spec` and `migration` → `docs/migration`; the staged copies are gitignored as `/docs/spec/` and `/docs/migration/`, so they never dirty a tree). **So `docs_dir: docs` is true but NOT dispositive, and reading it as "the strict build cannot see `spec/`" is the misreading that put a wrong gate nomination in roughly a dozen briefs (rf2-3r2t).** **The staging lives in the HOOK, not only in CI, so it runs on ANY invocation — `build`, `serve`, `--strict`, local or CI — and a BARE local `mkdocs build --strict` covers `spec/` with no manual staging step of your own.** That hook landed 2026-05-19 (`b2e622c316`, rf2-qw5mh) and its own comment says it exists so that any local or CI invocation auto-stages; `.github/workflows/docs.yml` keeps an explicit `rm -rf docs/spec && cp -r spec docs/spec` step that the file itself calls redundant belt-and-braces. **Do not tell a worker to replicate the staging by hand, and do not discount a local strict run as not covering `spec/` — both were measured wrong.** Measured on one tree by deleting `docs/spec` and `docs/migration` outright and running a bare `mkdocs build --strict`: both directories were recreated by the hook and 52 `spec/` pages were built, `spec/conformance/README.md` among them.

**Link validation is split across two gates, and the split does not follow the job name.** `scripts/check_doc_slugs.py` validates markdown link targets and heading anchors under `docs/`, `spec/`, `skills/`, `migration/` and `tools/*/spec` — and **nothing else**: repo-root markdown (`README.md`, `CLAUDE.md`, `TESTING.md`, `AGENTS.md`, `CHANGELOG.md`, `SKILL-REDIRECT.md`) and every `README.md` beside source code, `implementation/**` included, are outside its roots, where it **exits 0 on a broken link**. Those are `scripts/check_readme_links.py --ci`'s surface, which models GitHub's `-N` duplicate-heading suffix where the docs gate models MkDocs' `_N`. Since rf2-i4nb2 that surface is **three** rosters rather than two — git-tracked non-`README.md` markdown beside source is the third (`implementation/SECURITY.md`, `examples/TESTING.md` and a handful more that no gate reached before), narrow by design, with `scripts/_test_fixtures/`, the docs-gate roots and `tools/*/spec/` all still excluded. **Both run in `test.yml`'s `verify-readme-links` job on every PR** — that job carries no surface guard, which is what rf2-v7fui secured for the docs gate — so the surface is gated, and the repair for a wrong nomination is to name the right gate, never to add one. Both also run in the fast-PR spine, but there they sit inside its **documentation tier, which is classifier-gated**: a green spine on a diff the classifier did not call documentation ran neither of them, so cite CI for these two rather than a local spine pass. But **that job's NAME reads as though it checks READMEs while the gate that actually does is the other one**, so nominate by PATH, never by job name: a broken target planted in `implementation/adapters/reagent/README.md` returns `check_doc_slugs.py` green and `check_readme_links.py --ci` red (rf2-8pb5k, measured twice). **And `mkdocs build --strict` does not validate heading ANCHORS at all — not even on a page it builds and publishes, so `exclude_docs` and `docs_dir` do not exhaust its non-coverage**: MkDocs grades a missing anchor, in-page or cross-file, at INFO (`validation.anchors` defaults to `info`, and `mkdocs.yml` sets no `anchors` key — only `links.unrecognized_links`), and `--strict` promotes WARNING but not INFO, so the strict build names the broken anchor on stdout and still exits 0. That leaves `check_doc_slugs.py` the only anchor gate for pages under `docs/` — **redundancy missing rather than coverage missing**, since it runs unguarded on every PR (rf2-zk50, measured on one planted anchor: docs gate exit 1 naming file, line and anchor; strict build exit 0). **So for the staged trees the two gates are COMPLEMENTARY rather than redundant, and neither substitutes for the other: `check_doc_slugs.py` validates ANCHORS and REPO-RELATIVE targets — what GitHub browsing needs — while `mkdocs build --strict` validates LINK RESOLUTION INSIDE THE BUILT SITE, which the slug gate cannot see at all.** A link can be correct on one and broken on the other, and a page under `spec/` is where that bites, because staging moves it: `mkdocs_hooks.py` rewrites the depth-1 form `](../docs/` to `](../` (`_SPEC_TO_DOCSROOT`), but there is **no depth-2 analogue, no `docs/` entry in the `_REWRITES` GitHub-URL fallback table, and no depth dispatch in the `spec/` branch** the way the guide branch dispatches on source depth — so a page in a `spec/` SUBDIRECTORY cannot reach `docs/` by a relative path at all, while a page at the top of `spec/` reaches it fine (453 such `](../docs/` links across 28 files are live and resolve in the built site). Measured on one tree with a single planted link in `spec/conformance/README.md`: `mkdocs build --strict` exit 1 naming the file and the unresolvable target, `check_doc_slugs.py` exit 0 and silent on the same tree (rf2-3r2t). `scripts/check_provenance_pins.py` validates changed pages under `docs/design/fresco/` as its own `docs.yml` job. **And neither gate looks inside a fenced code block at all**, which bounds every green above a second time and along a different axis than the rosters: both share one extractor, and it strips fences before it reads a single link, so a broken target or anchor written inside a fence is invisible and the exit 0 is silent about it (rf2-sodfq, measured in both directions — the identical broken anchor returns exit 0 inside a fence and exit 1 four lines above it in prose). The skip is deliberate and stays: well over a hundred in-repo doc links live inside fences, most of them in `spec/Spec-Schemas.md` as `;;` commentary inside schema samples, and a fence is code — this repo's own write-ups quote broken links on purpose. Only `docs/design/fresco/` and `docs/the-mayor-method/` are held to more, and there the rule is the opposite one: a doc link inside a fence is itself reported, because those trees' fences are pasteable deliverables. **So for an edit CONFINED to a fenced block — and whole pages qualify, `spec/Spec-Schemas.md`'s schemas among them — neither gate is the gate**: nominating one returns a green that inspected nothing you changed, so check the links by hand and say so. Nothing validates any of this markdown's PROSE, tables, rendering or nav — link targets and anchors are the whole of what these gates check — so **the worker verifies anchors and table column counts by hand and says so in the PR body**.

## Architecture Overview

**The spec is the artefact; the code is downstream.** The normative description of re-frame2 lives in [`spec/`](spec/) (~46K lines across 50+ documents); [`implementation/`](implementation/) is a CLJS reference that validates the spec end-to-end. See the repo-root [`README.md`](README.md) for the marketing-voice introduction and the project-layout map, and [`spec/README.md`](spec/README.md) for the spec index.

Status that the directory tree does not tell you: `implementation/ui/` (re-frame.ui) and `implementation/freehand/` (re-frame.freehand) are **RETIRED and REMOVED** — Mike's 2026-08-14 disposition (rf2-0yp7w), executed by PR #8322 on 2026-08-16, and `git ls-files` now returns nothing under either path. The absence is permanent, not a tree mid-surgery. The code is gone, and the donor references that survive in prose are deliberate rather than residue awaiting deletion (measured 2026-08-21, rf2-wppza): every one of `spec/`'s is either retirement bookkeeping (a dated statement naming rf2-0yp7w, or one of the struck-through `spec/009-Instrumentation.md` catalogue rows recording their own retirement under rf2-d89rs instead) or the **reserved-kind contract** — `:rf.adapter/ui` and `:rf.adapter/freehand` stay rostered in `spec/006-ReactiveSubstrate.md`, `spec/Conventions.md` and `spec/API.md` precisely BECAUSE tooling still refuses those values defensively against a stale co-loaded build — and the teaching corpus (`docs/core/`, `testbeds/`) carries none at all. So read a donor reference as history or as a reserved value to keep: never a surface to build on, and never something to delete on sight. The `adapters/` (Reagent, reagent-slim, UIx) are **first-class and actively supported**, and `fresco/` (re-frame.fresco) is the re-frame-native view layer.

`tools/` holds dev/inspection tools consuming the Spec 009 instrumentation API and Tool-Pair contract. They are bundle-isolated from production builds: **nothing in `implementation/` may `:require` from `tools/`.**
