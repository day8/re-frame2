## Portraits to check

**(a) Does TanStack require fetching from render?** No. The default `useQuery` model is fetch-on-render (suspense guide: "React Query's suspense mode defaults to 'Fetch-on-render'"), but the documented alternatives start the fetch before any component renders: the prefetching guide's router-loader section ("declare needed data per route … block rendering until critical data loads or start prefetching secondary data"), the SSR guide ("In the loader function, do `await queryClient.query(...)` for each query you want to prefetch"), and the TanStack Router page (`queryClient.ensureQueryData` in `loader`, `useSuspenseQuery` in the component; "No waterfall data fetching, caused by component based fetching"). Since 5.102.0 the imperative entry point is `queryClient.query`; `prefetchQuery`/`ensureQueryData` are deprecated and slated for removal in the next major. Sources: rows "Prefetching", "SSR", "TanStack Router loader integration", "Suspense hooks", RFC #9135.

**(b) Per-request QueryClient in SSR — is it the documented shape?** Yes, and it is the *only* documented shape. SSR guide: "Creating the queryClient at the file root level makes the cache shared between all requests and means _all_ data gets passed to _all_ users."; create it "inside of your app, in React state (an instance ref works fine too). **This ensures that data is not shared between different users and requests**". Advanced SSR (RSC): `getQueryClient` wrapped in React `cache()` — "cache() is scoped per request, so we don't leak data between requests". A module-global client is named only as the anti-pattern. Sources: SSR and Advanced SSR rows.

**(c) Is context-rollback clobbering a newer concurrent write the library's behaviour or a recipe, and does the variables pattern avoid it?** It is a **recipe**: the "via the cache" pattern is user code (`onMutate` snapshot → `setQueryData` → `onError` restores the snapshot), and the library provides no conflict detection around it. The TanStack page does not discuss the clobber at all — the words "race", "clobber", "in flight" are absent; its only concurrency remark on the cache side is `cancelQueries` "so they don't overwrite our optimistic update" (refetches, not other mutations), plus `onSettled` "Always refetch after error or success". **RTK Query's docs name the hazard explicitly** for the same recipe: "Where many mutations are potentially triggered in short succession causing overlapping requests, you may encounter race conditions if attempting to roll back patches using the `.undo` property on failures" and recommend tag invalidation instead. On the variables pattern, TanStack's docs describe it as writing nothing to the cache (UI reads `variables` from `useMutation`/`useMutationState`), explicitly handle multiple in-flight mutations ("`variables` will be an `Array`, because there might be multiple mutations running at the same time"; `submittedAt` makes "displaying concurrent optimistic updates a breeze"), and prefer it when the result is shown in one place. That the variables pattern therefore cannot clobber a concurrent cache write is my inference from those sentences, not a sentence on the page.

**(d) Does RTK's tag system give declarative invalidation?** Yes. `providesTags` on queries and `invalidatesTags` on mutations are declared on the endpoint definitions; matching is by tag type (general) or type+id (specific), with the `'LIST'` id convention; "If cache data is being invalidated, it will either refetch the providing query (if components are still using that data) or remove the data from the cache." `invalidationBehavior` defaults to `'delayed'`. The OpenAPI codegen can emit tags (`tag` option). TanStack Query has no equivalent: invalidation is imperative `invalidateQueries` in `onSuccess` (row "Invalidation from mutations"). TanStack DB's QueryCollection sits between the two: "after any persistence handler completes successfully, the query will automatically refetch" unless the handler returns `{ refetch: false }`.

**(e) Does mutation `scope` serialise overlapping writes?** Yes, by queueing: "All mutations with the same `scope.id` will run in serial, which means when they are triggered, they will start in `isPaused: true` state if there is already a mutation for that scope in progress." It is opt-in per mutation, keyed by a string you choose; the docs describe ordering only, not merging or conflict resolution (observation, not a quote).

**(f) Can the Devtools show the cause of a fetch?** Not per any page read. The official devtools page lists observing queries and mutations, triggering loading/error states, and `errorTypes`/`buttonPosition`, and says nothing about fetch cause or invalidation provenance. The browser-extension listing (publisher "DeeCode", unverified as TanStack-official) enumerates status, data, metadata, "last updated", cache actions, search/sort — no "why did this fetch" or "which mutation invalidated it" feature. A web search for those terms found nothing in the docs. Treat "Devtools cannot show cause" as *not documented*, not as a measured absence in the UI.

**(g) Data-classification / sensitive-field redaction for logs, devtools or SSR payloads?** No library read has a field-level classification feature. The closest mechanisms, all coarser than field-level: TanStack `dehydrate`'s `shouldRedactErrors` — SSR payload **errors** are redacted by default ("replaced with a generic `Error('redacted')`") — and `shouldDehydrateQuery` / `shouldDehydrateMutation` predicates, which let you exclude whole queries from an SSR/persist payload but carry no classification metadata (query `meta` is free-form). TanStack's `broadcastQueryClient` and persisters serialise whole query state with no redaction hook mentioned. Angular's `resource` guide warns against using the SSR `TransferState` `id` cache "for user-specific data" (advice, not a mechanism). RTK Query, SWR, Apollo, TanStack DB: nothing on the pages read. Store5's docs index lists a "Security and Data Encryption" use-case page (title only, from search results) — **UNVERIFIED**, not read.
