## The objective you are researching, in Mike's words (2026-09-14)

> We want the Resources feature in re-frame2 to have feature parity with TanStack Query and similar JS (and other) alternatives. Except, of course, we want it to leverage re-frame2's strengths, idioms and ethos. See the Conduit RealWorld example.
>

Both questions are the deliverable, and they are co-equal. The first asks for a MEASUREMENT METHOD that can be re-run after a TanStack major or a Resources slice lands, and its first reading. The second asks for IMAGINATION grounded in what re-frame2 actually has. A report that only produces a feature checklist has answered half. Recommendations follow from the two answers; they are not a third question. The answer must be free to conclude that a competitor is better for a particular job, that Resources already suffices, or that the evidence is insufficient.

**Parity, defined so it can be tested:** an experienced TanStack Query (or RTK Query, SWR, Apollo-for-REST, Vue Query, Angular `resource`) user can sit down with Resources — ideally by cloning Conduit's pattern — and accomplish the server-state jobs they came for (read, cache, revalidate, paginate, write, invalidate, roll back, prefetch, hydrate, debug, test) with comparable reliability and at comparable or lower ceremony, without a map of re-frame2 internals. The API may be `reg-resource` and events rather than a hook; the cache may live in a frame's runtime partition rather than a `QueryClient`; the debugger may be Xray rather than the Devtools panel; those are not gaps. Being unable to do the job, or only able to do it through undocumented internals, disproportionate ceremony, or by hand-rolling what `realworld_http` already does, is a gap. Parity does not require reproducing another library's option surface, plugin count, or accumulated complexity, and it does not permit quietly narrowing the comparison to the jobs where Resources already looks strong, or calling an inconvenient omission a deliberate divergence without a recorded reason. A deferred feature stays in the comparison as a gap when the job matters; document the trade-off rather than making it disappear, and do not treat a recorded architectural refusal as automatic satisfaction of Mike's broader objective.

**Better, defined so it can be tested:** some of those jobs are cheaper, more honest, or newly possible because a read is caused by an event, owned by a route or a machine, scoped by a required structural key, traced on the same bus as everything else, replayable from an epoch, classified for egress, and declared as data an agent can read. Better is fewer concepts doing more work, and a stale page that explains itself. It is not more options. A meaningful ergonomic advantage need not be impossible elsewhere; it must be materially cheaper or more reliable for a structural reason you can name and test.

**The ethos the comparison is held to** (from `spec/000-Vision.md`, `spec/Principles.md`, `spec/016-Resources.md` and the stance): data before magic — resource and mutation bodies are data, request fns return request maps, not promises; views are passive — a subscription that fetches is a defect, not a convenience; one obvious way — no second cache, second invalidation style, or hook-shaped wrapper over `ensure`; named, addressable things — keys, owners, causes, mutation instances, tags; trust the programmer — a one-shot uncached GET belongs to managed HTTP and needs no Resources ceremony, and avoiding Resources for that job can be the ergonomic answer; AI-first is a property of the SHAPE (enumerable registry, consequences on the declaration, one reply envelope), not a bolt-on; Resources is an OPTIONAL artefact, and Spec 016 owns the contract, but for "how close are we today" the CODE at trunk wins where spec and code disagree, and Conduit wins where spec and code claim a job the example cannot do. Code establishes present behaviour, the spec establishes the promised contract, and the example establishes only what it exercises — say which artefact every verdict came from.

## What Resources is, and what to read first

Resources is re-frame2's declarative server-state capability: a cached read is a **resource** (`reg-resource`), a write is a **mutation** (`reg-mutation`) whose cache consequences are declared as data, the cache lives in the framework-owned runtime partition of each frame (never app-db), every entry carries a required **scope** as part of its identity, a read is **caused** by a route or an event and only ever **read** by a view (views never fetch), and the transport is managed HTTP. It ships as the optional artefact `day8/re-frame2-resources` (`implementation/resources/`, 26 source files, 60 test files), surfaced through the core facade `implementation/core/src/re_frame/core_resources.cljc` (read it to separate the public facade from the artefact that supplies it), with the Xray Resources panel, six conformance fixtures, a docs chapter, a five-part tutorial, four capability examples and a complete RealWorld app. Read in this order, before you read anything outside the repo, and pull other sections only when a job requires them:

## Question 1 — how do we test how close we are?

Design a re-runnable test, then take its first reading. Requirements:

- **Rows are JOBS a user does, not competitor options.** Start from the jobs Conduit has (the eight reads and their scopes, the mutations and their consequences, login, logout and cold boot with a stored token, offset pagination, tag filter, refresh-error), then the shipped scorecard's twenty-two dimensions, then add or cut on what the comparison set shows. the four visible states (loading, fetching, error, refresh-error) rendered without hand-written flags; stale-while-revalidate, dedupe, fresh-skip and garbage collection as policy, INCLUDING the defaults a migrant expects (stale immediately versus never; retry on reads versus writes; GC window); a write that invalidates exactly what it made stale, across every mounted reader, with nothing remembered at the call site; per-instance pending, result and error for a write, and two instances in flight at once, distinguishing transport success from an accepted domain result; - **Status vocabulary**, used consistently and defined in `rubric.md` so two readers score a row the same way: `WIN` (Resources does the job at lower ceremony, more honestly, or in a way the comparator cannot); `MATCH` (comparable ceremony; a TanStack user would not bounce); `GAP` (cannot be done, or only through undocumented internals or disproportionate ceremony); `SPEC-ONLY` (the contract exists in `016`; code or docs do not honestly ship it); `UNDERMARKETED` (shipped, but a user following `docs/resources/` and the Conduit README would not find it); `DIVERGENT` (refused on purpose and the job is served another way — cite the resolved decision and name the other way); `OUT` (not a Resources job — name where in re-frame2 it lives instead); `TARGET` (the spec's Deferred slices or Open questions already require it and mark it not-yet). **Every `WIN`, `MATCH` and `GAP` names its comparator** (WIN vs TanStack may be MATCH vs RTK Query on the invalidation row), and a comparative status is a separate judgement from whether Resources can do the job at all — the layers below carry the capability, the status carries the comparison. ## Question 2 — how do we imagine being better?

Reason from what re-frame2 HAS rather than from what TanStack lacks. Every bullet below is a HYPOTHESIS the docs already claim; try to disprove each against TanStack's strongest practical workflow with the Devtools, against RTK's tag invalidation, and against the friction you measured in Question 1, before you keep it. For each, separate SUBSTRATE POTENTIAL from SPECIFIED CONTRACT from SHIPPED BEHAVIOUR from DISCOVERABLE BY A CONDUIT-CLONING AUTHOR:

- **Every load has a cause, and causes are traced.** A Resources load carries an event or route cause, an owner, and a `:work/id` on the same trace bus as every other event, and the Xray panel claims to show "which route owns this read, why is it fetching, did the last refresh fail, is this `/me` read accidentally global". Is that lens shipped and does it answer those questions on Conduit today (file:line, and you looked)? What does a TanStack maintainer do instead with the Devtools, and how much slower is it on the same planted fault? Demonstrate faster diagnosis or fewer translations; a larger trace alone is not an advantage.
- **Owners and causes are distinct, and owners can be routes and machines.** Liveness pinned by a route token or a state machine, released on leave or transition, instead of by component mount. What does that make possible (a page's reads released as a unit; a machine's resource lifecycle proven by the machine's states; SSR readiness derived from the branch plan) that observer-counting cannot? Does it also make the first read harder, or create avoidable ownership ceremony? Built, specified, or only possible?
- **Scope is structural identity, fail-closed.** The docs call it "the leak boundary other libraries do not have". Prove it with a deliberate leak on both sides, count what it costs every registration, and say whether the default is the right one for a single-user SPA that has no scope to speak of.
- **Invalidation is data.** `:invalidates`, `:populates`, `:patches`, `:removes` and the scoped descriptors are declared on the mutation, so the consequences of a write are in principle readable by Xray, by a test, and by an agent without executing anything. RTK Query's tags are the nearest thing. What can Resources do with the declaration that RTK cannot (diff two mutations' consequences; lint a mutation that invalidates nothing or invalidates the wrong scope — the scope-mismatch lint near `016` line 1734; generate the Conduit consequence table in the README from the registrations)? Which of those exist? And be exact about the limit: function-valued requests, invalidation targets and patches may need params or runtime context, so a registry that contains data does not make every consequence statically enumerable — say which consequences are.
- **Optimism stays correct under overlap.** The author declares only the forward patch; the runtime records the inverse and, on a contested rollback, invalidates rather than restores (`:on-conflict :invalidate`, EP-0019). Compare against TanStack's context rollback AND its `variables`-based pattern AND its mutation `scope`, on the overlapping-writes experiment you ran; say whether the difference is a spelling or a behaviour, and what it costs in refetches.
- **The cache is not app state.** Runtime-db keeps app-db pure and the cache out of reach of an ordinary handler. What does that buy (undo and time-travel over app-db unpolluted by cache churn; epoch export without server payloads; classification at egress) and what does it cost (a second place to look)?
- **Deterministic replay and epochs.** `replay_determinism_e2e` and `resource_generation_recordable` exist. Can a production epoch that includes resource loads be replayed against canned replies to reproduce a stale-page bug, as a user-facing workflow rather than a substrate test? Shipped, specified, or a test that proves the substrate only?
- **Data classification.** Sensitive server data projected or elided at the egress boundaries (traces, SSR wire, epoch export). Is it a differentiator a Conduit author meets (password, email, token) or a contract only a security reviewer sees, and does any comparator or its ecosystem have an equivalent?
- **Frames.** Per-request SSR frames, parallel frames in tests, several apps on one page. What does a per-provider `QueryClient` cost in SSR and multi-tenant cases, and is Resources' answer actually cheaper — with a Conduit or `resources_ssr` path, not "we have frames, therefore SSR isolation"?
- **A spec separate from the code, with conformance fixtures.** A port or a rewrite can be graded; the JS libraries ARE their code. Portability hygiene or a user-facing advantage? Say so plainly.
- **Views never fetch.** A principle, not an option. Prove where it pays (SSR, tests, Story variants of every server state without a network, cache hits that render identically) and where it is the ceremony a TanStack user feels first.
- **The same case serves human, test and assistant.** Describe the loop an assistant can run today (read the registry, add a resource or a mutation with declared consequences, run the Conduit test with a canned stub, read the trace) with the exact skill leaves and MCP tool names, state the actual host, frame and transport, and say what the loop still cannot do. Then imagine the loop it should run in a year, and say which pieces are cheap.
- **Schemas to identity, and to controls.** `:params-schema` validates and canonicalises the cache key; TanStack relies on TypeScript inference and key factories by convention. Does the schema also drive anything else (Story controls for a resource-backed view; an Xray form to ensure a read by hand; consequence documentation derived from the declarations)? Built, specified, or imagined — and verify what is actually available before proposing it.
- **The limits of a data-shaped cache.** Live I/O, clocks, websockets, GraphQL graphs, offline queues. Say where Resources should stop and hand the job to managed HTTP, a machine, or a different artefact, rather than inventing a second Apollo.

Then write the advantage thesis: which jobs the comparators do poorly BECAUSE OF THEIR SUBSTRATE (component-mount ownership, a process-global client, no trace bus, no spec, cache and app state in one store, the user id as a forgettable key segment) rather than because a plugin has not shipped — dropping any candidate RTK or TanStack already covers idiomatically; which of those Resources has productised (a Conduit author does it without knowing the substrate's name) versus latent (possible if you know re-frame2 well, invisible if you don't); whether the small set of primitives the docs teach (register / cause / project, plus tags on writes) is the right set — if you keep it say why, if you replace it say which job it fails; what "better" looks like in a year as a handful of scenes (an app developer declaring a page's reads; a multi-tenant SaaS maintainer diagnosing a stale page in one lens; a tester rendering every server state as a Story variant with no network; an assistant adding a write with declared consequences and proving it; a security reviewer auditing scope and classification), each materially cheaper or more reliable than in TanStack for a structural reason, or dropped; and what Resources should stop copying, if anything (an option surface that exists because a hook has no other place to put policy; per-component fetch policy; imperative cache writes; restoring contested optimistic context). Also state, honestly, where TanStack is BETTER and is likely to stay better — the one-line colocated read, TypeScript inference, `useQueries` over a dynamic list, Suspense integration, persisters, Devtools polish, the ecosystem, `staleTime: 0` as the default a migrant expects, and whatever TanStack DB has shipped — and say which of those a re-frame2 SPA author actually misses; evaluate the smallest Resources-shaped answer to the one-line read and to offline persistence before recommending continued deferral. For each "better" claim state its tier: BUILT (file:line, and you ran it), SPECIFIED (spec section, not yet in code), or IMAGINED (your proposal, with a before-and-after workflow, the existing primitive it uses, a small idiomatic data sketch where it helps, its costs, a falsification test and a stopping point). These tiers are for advantage claims; the status vocabulary above is for matrix rows; do not invent a third jargon. Select roughly three to five opportunities and decline the rest, preferring a worked example or an existing integration over new machinery. Apply the stance to every proposal: a proposal that adds a concept, a second encoding, an option, or a ceremony the programmer did not ask for must say what it removes, or be killed in one sentence rather than litigated into a recommendation. It is an acceptable outcome that a competitor is more ergonomic on a job, that Resources already has the right capability and only needs better presentation, or that the evidence is insufficient.

## Lessons carried over from the Story research (2026-09-14)

The sibling critique of the Story report is short and applies here unchanged. (1) Assess the CURRENT tree and lead with it; if something was fixed while you worked, re-verify and revise the headline, matrix and recommendation sequence throughout as "historical defect → landed repair → evidence still needed", keeping the original reading as a dated baseline and leaving no old present-tense claim under a new header, and never inferring a whole job done from a merged patch. (2) Arithmetic is not evidence of comparative superiority — a forecast score after hypothetical fixes is not a finding. (3) Do not overstate consensus with anyone; attribute shared experiments, and remember that repeated citations are not independent confirmation and consensus does not settle a disputed empirical claim. (4) A job Mike asked about is a job to evaluate now, even if the project's instinct is to refuse it — offline persistence and the one-line read are the ones here; evaluate the smallest Resources-shaped answer, or an existing supported integration, before recommending continued deferral. (5) Measure the advantage where it matters to the programmer: less re-entry, faster diagnosis, fewer host and context switches on the same realistic task, on a full journey, before calling it an ergonomic win. (6) Finish the consequential corrections, then shorten.
