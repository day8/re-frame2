Both questions are the deliverable. The first asks for a MEASUREMENT METHOD that can be re-run after a TanStack major or a Resources slice lands, and its first reading. The second asks for IMAGINATION grounded in what re-frame2 actually has. A report that only produces a feature checklist has answered half.

**Parity, defined so it can be tested:** an experienced TanStack Query (or RTK Query, SWR, Apollo, Vue Query, Angular `resource`) user can sit down with Resources and accomplish the server-state jobs they came for — read, cache, revalidate, paginate, write, invalidate, roll back, prefetch, hydrate, debug, test — at comparable or lower ceremony, without a map of re-frame2 internals. The API may be `reg-resource` and events rather than a hook; the cache may live in a frame's runtime partition rather than a `QueryClient`; the debugger may be Xray rather than the Devtools panel; those are not gaps. Being unable to do the job, or only able to do it through undocumented internals or disproportionate ceremony, is a gap. Parity does not require reproducing another library's option surface, plugin count, or accumulated complexity, and it does not permit quietly narrowing the comparison to the jobs where Resources already looks strong, or calling an inconvenient omission a deliberate divergence without a recorded reason.

**Better, defined so it can be tested:** some of those jobs are cheaper, more honest, or newly possible because a read is caused by an event, owned by a route or a machine, scoped by a required structural key, traced on the same bus as everything else, replayable from an epoch, classified for egress, and declared as data an agent can read. Better is fewer concepts doing more work, and a stale page that explains itself. It is not more options.

## What Resources is, and what to read first

Resources is re-frame2's declarative server-state capability: a cached read is a **resource** (`reg-resource`), a write is a **mutation** (`reg-mutation`) whose cache consequences are declared as data, the cache lives in the framework-owned runtime partition of each frame (never app-db), every entry carries a required **scope** as part of its identity, a read is **caused** by a route or an event and only ever **read** by a view (views never fetch), and the transport is managed HTTP. It ships as the optional artefact `day8/re-frame2-resources` (`implementation/resources/`, 26 source files, 60 test files), the Xray Resources panel, six conformance fixtures, a docs chapter, a five-part tutorial, three capability examples and a complete RealWorld app. Read in this order, before you read anything outside the repo:

1. `spec/016-Resources.md` — the normative contract (about 2,000 lines). Read §Abstract, §Implementation status (what the first public-beta surface includes; the read-resource MVP, mutations, focus/reconnect), §Resource identity and §Scope resolution (identity is the `[scope resource-id canonical-params]` triple; scope is fail-closed), §Active owners and causes (owners pin liveness, causes explain work — the pair TanStack collapses into "observers"), §Lifecycle is an FSM and §Status semantics (`:loading` vs `:fetching`, `:error` reserved for first-load failure, `:refresh-error` keeps data), §Cache home and write authority (runtime-db, not app-db), §Frame work ledger, §Public API (events take map payloads; subscriptions are passive; `:reply-to` continuations; no `:select`), §Mutations (scoped invalidation descriptors, populate, optimistic apply/settle), §Transport, §Paginated and previous data, §Infinite resources, §SSR and hydration, §Restore and replay, §Xray and AI tooling, §Examples, and — read these three with particular care — §Deferred slices, §What Spec 016 does NOT cover, §Open questions, and §Resolved decisions (a resolved decision is a refusal with a recorded reason; a divergence by design is not a gap, say so where it applies, and say whether the reason still holds).

## Question 1 — how do we test how close we are?

Design a re-runnable test, then take its first reading. Requirements:

- **Rows are JOBS a user does, not competitor options.** Start from the jobs Conduit has (the eight reads and their scopes, the nine mutations and their consequences, login and logout, pagination, tag filter, refresh-error), then the shipped scorecard's twenty-two dimensions, then add or cut on what the comparison set shows. Group by journey: first hour (one read on screen from an empty project, with the loading and error states honest); a keyed, parameterised read; the four visible states (loading, fetching, error, refresh-error) rendered without hand-written flags; stale-while-revalidate, dedupe, fresh-skip and garbage collection as policy; a write that invalidates exactly what it made stale, across every mounted reader, with nothing remembered at the call site; per-instance pending, result and error state for a write; optimistic update and rollback that restores what was actually there; populate, patch and remove from a reply; paginate and load-more with previous data kept on screen; prefetch on intent and route-plan preload; dependent and serial reads (B needs A's result — how does Resources express it, and is `:reply-to` or the route plan the ergonomic path?); parallel reads for one page; polling; focus and reconnect revalidation; cancellation and stale-reply suppression when a read is superseded; auth headers, retry and backoff (the managed-HTTP seam) and domain-failure normalisation; SSR and hydration with freshness rules; offline persistence and cross-tab (Deferred by the scorecard — decide whether a TanStack user bounces); realtime and streaming (subscriptions, `streamedQuery`, `onCacheEntryAdded` — where does re-frame2 put this job, and is it a Resources job at all); the multi-user leak boundary (scope — a candidate WIN, but count what it costs every registration); devtools (Xray panel versus the Devtools); testing (canned stubs, reset fixtures, deterministic replay, conformance fixtures, a Story variant per server state); the agent surface (skills, registry-as-data, MCP); schemas and type safety (`:params-schema` versus TypeScript inference and `queryOptions`); code generation from an API contract; and the honest OUT rows (normalised entity cache, GraphQL). Roughly eighteen to twenty-four rows; more than that almost certainly means you are litigating minutiae. Scoring "is there a `select` option?" undercounts Resources' wins (projections are ordinary subscriptions) and overcounts TanStack's — if a row is an option rather than a job, delete it.
- **Status vocabulary**, used consistently and defined in `rubric.md` so two readers score a row the same way: `WIN` (Resources does the job at lower ceremony, more honestly, or in a way the comparator cannot); `MATCH` (comparable ceremony; a TanStack user would not bounce); `GAP` (cannot be done, or only through undocumented internals or disproportionate ceremony); `SPEC-ONLY` (the contract exists in `016`; code or docs do not honestly ship it); `UNDERMARKETED` (shipped, but a user following `docs/resources/` would not find it); `DIVERGENT` (refused on purpose and the job is served another way — cite the resolved decision); `OUT` (not a Resources job — name where in re-frame2 it lives instead); `TARGET` (the spec's Deferred slices or Open questions already require it and mark it not-yet). A `DIVERGENT` whose "other way" does not actually serve the job is a `GAP`; never record a refusal as a silent absence, and never record a Deferred row as a gap in the competitor's favour without checking whether a bead has since landed it.
- **Four layers per row**, because a single status hides the interesting disagreements: SPEC (is the contract in `016`, `014`, `012` or `015`?), CODE (does `implementation/resources/src` implement it, and do tests in `implementation/resources/test/` or a conformance fixture pin it?), DOCS (can `docs/resources/` plus the Conduit README get a new user there?), ERGONOMICS (is it the path of least resistance, or a power-user back door?). Add an EVIDENCE-STRENGTH column beside the status — exercised (you ran it), source-traced, documented-only, unverified — and where a row's status differs between layers say so in the row; the layer disagreements are the most useful output of the whole matrix.
- **Ceremony count** is part of the test: concepts the author must hold, registrations and declarations they must write, files they must touch, boot requires they must remember, and — specific to this comparison — how many places one job is spread across. TanStack's headline ergonomic is a colocated `useQuery` in one component; Resources deliberately splits that into a registration, a cause and a passive read (the docs say so: "one hook becomes three jobs"). Count that honestly on both sides for a first read AND for the tenth read in a real app, where TanStack's colocation starts to cost (key discipline, invalidation bookkeeping, duplicated fetch logic) and Resources' split starts to pay. A `MATCH` at twice the ceremony is a `GAP` in disguise; a `WIN` on the tenth read that is a `GAP` on the first is a first-hour finding. Trust the programmer: "the programmer might forget a key segment" is a gap in TanStack's favour only if the framework can catch it, which is exactly the scope argument — test whether it actually catches it (there is a `resources_scope_leak_boundary` test; run it and a deliberate leak).

Where a row depends on a test, use a deliberate fault to show the claimed test detects the defect: fault the fake backend in Conduit, or a canned stub, and confirm the assertion that claims to pin the row goes red. A test that stays green under the fault does not pin the row.

## Question 2 — how do we imagine being better?

Reason from what re-frame2 HAS rather than from what TanStack lacks, and try to disprove each advantage before you claim it. Then, for each strength, separate SUBSTRATE POTENTIAL from SPECIFIED CONTRACT from SHIPPED BEHAVIOUR from DISCOVERABLE BY A NEW USER:

- **Every load has a cause, and causes are traced.** A TanStack fetch happens because a component mounted; nothing records why. A Resources load carries an event or route cause, an owner, and a `:work/id` on the same trace bus as every other event, and the Xray panel can show "which route owns this read, why is it fetching, did the last refresh fail, is this `/me` read accidentally global". Is that lens shipped and does it answer those questions on Conduit today (file:line, and you looked)? What would a maintainer in TanStack-land do instead (Devtools plus console plus guesswork)?
- **Owners and causes are distinct, and owners can be routes and machines.** Liveness pinned by a route token or a state machine, released on leave or transition, instead of by component mount. What does that make possible (a page's reads released as a unit; a machine's resource lifecycle proven by the machine's states; SSR readiness derived from the branch plan) that observer-counting cannot? Built, specified, or only possible?
- **Scope is structural identity, fail-closed.** The docs call it "the leak boundary other libraries do not have". Prove it with a deliberate leak on both sides, count what it costs every registration, and say whether the default is the right one for a single-user SPA that has no scope to speak of.
- **Invalidation is data.** `:invalidates`, `:populates`, `:patches`, `:removes` and the scoped descriptors are declared on the mutation, so the consequences of a write are readable by Xray, by a test, and by an agent without executing anything. RTK Query's tags are the nearest thing; what can Resources do with the declaration that RTK cannot (diff two mutations' consequences; lint a mutation that invalidates nothing; generate the Conduit consequence table in the README from the registrations)? Which of those exist?
- **The cache is not app state.** Runtime-db keeps app-db pure and the cache out of reach of an ordinary handler. What does that buy (undo/redo and time-travel over app-db unpolluted by cache churn; epoch export without server payloads; classification at egress) and what does it cost (a second place to look)?
- **Deterministic replay and epochs.** `replay_determinism_e2e` and `resource_generation_recordable` exist. Can a production epoch that includes resource loads be replayed against canned replies to reproduce a stale-page bug? Is that shipped, specified, or a test that proves the substrate only?
- **Data classification.** Sensitive server data projected or elided at every egress boundary (traces, SSR wire, epoch export). No comparator has it. Is it a differentiator a Conduit author meets (password, email, token) or a contract only a security reviewer sees?
- **Frames.** Per-request SSR frames, parallel frames in tests, several apps on one page. TanStack has one `QueryClient` per provider; what does that cost it in SSR and multi-tenant cases, and is Resources' answer actually cheaper?
- **A spec separate from the code, with conformance fixtures.** A port or a rewrite can be graded; the JS libraries ARE their code. Is that a user-facing advantage or a project-hygiene one? Say so plainly.
- **Views never fetch.** A principle, not an option. Prove where it pays (SSR, tests, Story variants of every server state without a network, cache hits that render identically) and where it is the ceremony a TanStack user feels first.
- **The agent loop.** Describe the loop an agent can run today (read the registry, add a resource or a mutation with declared consequences, run the Conduit test with a canned stub, read the trace) with the exact skill leaves and MCP tool names, and what the loop still cannot do. Then imagine the loop it should run in a year, and say which pieces are cheap. AI-first is a property of the shape (a registry that is data, consequences that are data, one reply envelope), not a bolt-on demo.
- **Schemas to identity, and to controls.** `:params-schema` validates and canonicalises the cache key; TanStack relies on TypeScript inference and key factories by convention. Does the schema also drive anything else (Story controls for a resource-backed view; an Xray form to ensure a read by hand; an OpenAPI mapping)? Built, specified, or imagined?

Then write the advantage thesis: which jobs the comparators do poorly BECAUSE OF THEIR SUBSTRATE (component-mount ownership, a process-global client, no trace bus, no spec, cache and app state in one store) rather than because a plugin has not shipped; which of those Resources has productised (a Conduit author does it without knowing the substrate's name) versus latent (possible if you know re-frame2 well, invisible if you don't); what "better" looks like in a year as a handful of scenes (an app developer declaring a page's reads; a maintainer diagnosing a stale page in one lens; a tester rendering every server state as a Story variant with no network; an agent adding a write with declared consequences and proving it; a security reviewer auditing scope and classification), each impossible or humiliating in TanStack for a structural reason; and what Resources should stop copying, if anything (an option surface that exists because a hook has no other place to put policy; per-component fetch policy; imperative cache writes). Also state, honestly, where TanStack is BETTER and is likely to stay better — the one-line colocated read, TypeScript inference, `useQueries` over a dynamic list, Suspense integration, persisters, the ecosystem, and whatever TanStack DB has shipped — and say which of those a re-frame2 SPA author actually misses. For each "better" claim state its tier: BUILT (file:line, and you ran it), SPECIFIED (spec section, not yet in code), or IMAGINED (your proposal, with a before-and-after workflow, a small idiomatic data sketch where it helps, and a falsifiable hypothesis about user benefit). These tiers are for advantage claims; the status vocabulary above is for matrix rows; do not invent a third jargon. Apply the stance to every proposal: a proposal that adds a concept, a second encoding, an option, or a ceremony the programmer did not ask for must say what it removes, or be killed in one sentence rather than litigated into a recommendation. ## Lessons carried over from the Story research (2026-09-14)

The sibling critique of the Story report is short and applies here unchanged; do not repeat its mistakes. (1) Assess the CURRENT tree and lead with it; if something was fixed while you worked, re-verify and say so, keeping the original reading as a dated baseline. (2) Arithmetic is not evidence of comparative superiority — a ratio near 1.0 with a wide sensitivity band is a "roughly at parity, with these named exceptions", and a forecast score after hypothetical fixes is not a finding. (3) Do not overstate consensus with anyone; attribute shared experiments. (4) A job Mike asked about is a job to evaluate now, even if the project's instinct is to refuse it — offline persistence and the one-line read are the ones here; evaluate the smallest Resources-shaped answer before recommending continued deferral. (5) Measure the advantage where it matters to the programmer: less re-entry, faster diagnosis, fewer host and context switches on the same realistic task, on a full journey, before calling it an ergonomic win. (6) Finish the consequential corrections, then shorten.

## What NOT to do

- Do not re-litigate decisions recorded in `016` §Resolved decisions or in a bead's close reason (cache in runtime-db; scope fail-closed; single built-in transport; `:error` reserved for first-load failure; no `:select`; lifecycle as a transition fn) unless you have new evidence that the refusal now costs a JOB rather than an option; if you disagree, say so in one paragraph with the evidence and move on.
- Do not propose a GraphQL or normalised entity cache (a later artefact by ruling), a second transport beside managed HTTP, a hook-style colocated fetch that lets a view cause a load, moving the cache into app-db, or a TanStack-compatible API shim, unless you can show a concrete Conduit-sized author it serves and a cost under a week.
- Do not redo the resources test suite or the spec's conformance; implementation defects are in scope only as honesty constraints on claimed wins. If you find a real defect while exercising a row, record it in `evidence.md` with a reproduction and move on; the mayor files it.
- Do not score a row from a library's marketing page; find the docs page or source that shows the behaviour, and say if you could not. Do not use this repo's version numbers, or any star or download count, as current.
- Do not write a README for Resources, and do not restate the tutorial or the migration page. The reader owns the project.
- Do not exceed what the decision needs. Mike will read this in one sitting; a 4,000–8,000 word report with the matrix, rubric and evidence beside it is the right size.

## Instrument notes for this machine (CLAUDE.md § Workflow catalogues them; read the bullet if you meet a surprising zero)
