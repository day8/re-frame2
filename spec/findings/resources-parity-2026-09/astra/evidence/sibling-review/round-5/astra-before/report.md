# Resources parity and a better SPA authoring experience

Resources already implements most of the server-state machinery an ordinary online SPA needs. The strongest evidence is more substantial than an API inventory: its Resources module passed **872 tests and 7,763 assertions**, and selected Conduit/Xray integration suites passed **79 tests and 724 assertions**. An independently built Conduit browser fixture also preserved a newer optimistic success when an older write failed, kept an old viewer's delayed representation out of the next viewer's read, and detected a deliberately missing invalidation target. These results support a capable foundation, not a claim of complete ecosystem parity. [Execution evidence](evidence.md), [controlled Conduit cases](evidence/conduit-controlled-cases.json).

The best near-term direction is to make that foundation easier to enter, explain and extend. A concrete tutorial dependency omission blocks the advertised transport require. Competitive prose overstates several differences. Durable offline work, cross-tab coordination, push updates and some infinite-feed capabilities remain meaningful gaps. The most promising superiority claim is **less application coordination around identity, write consequences and failure recovery**, combined with an explanation that a programmer or assistant can actually use. Faster development has not yet been established by a comparative user study.

This assessment uses the [recorded repository baseline](evidence/baseline.json), preserved local source, and current primary sources accessed on 14 September 2026. Executed TanStack Query packages are **5.102.8**. Research versions for the other comparators are Redux Toolkit **2.12.0**, SWR **2.5.1**, Apollo Client **4.3.0**, Riverpod **3.4.3**, and TanStack DB **0.9.0**, whose project still describes it as beta. Their documentation was inspected; they were not all executed. [Version receipts](evidence/upstream-versions.json), [Riverpod release](evidence/primary/riverpod-release.json), [TanStack DB status](https://github.com/TanStack/db#status).

The independent findings were preserved before consulting siblings. A subsequent [sibling review](sibling-review.md) added targeted source checks and two new executable probes. Peer observations remain attributed; they do not become additional Astra test passes.

## What parity should mean

Parity means completing a developer's job with dependable behavior and reasonable effort. It does not require borrowing another library's option names, hooks or cache architecture. It does require accounting for a relevant outcome even when the present design deliberately postpones it. An offline queue remains a gap for an offline application; classifying it as deferred explains the gap rather than removing it.

The [comparison matrix](parity-matrix.md) uses sixteen stable jobs, from a first useful read through mutation coordination, identity changes, hydration, debugging and assistant use. It keeps contract, implementation, discoverability and observed behavior separate. A categorical comparison is more useful than a parity percentage: a successful polling test cannot compensate for a broken first session or a cross-view inconsistency.

Conduit is a good anchor because it combines viewer-relative data, filtered lists, pagination, writes and navigation. It is not the ceiling of Resources. Infinite feeds and SSR need their own examples; persistence and streaming remain relevant even though this particular demo does not require them. Equally, an uncached one-shot action can remain a managed-HTTP operation without making Resources less ergonomic.

The migration page's full scorecard contains **22 dimensions: 17 Landed, three Different by design, one Out of scope and one Deferred**. Each Landed dimension has identifiable relevant implementation/test coverage. That is materially different from proving the complete visible workflow, every policy combination or comparative ease of use. The [scorecard crosswalk](scorecard-audit.md) names the tests and their limits rather than replacing the existing scorecard with another undifferentiated checklist.

## What Conduit demonstrates

The example's eight reads deliberately distinguish viewer-relative representations from genuinely shared data. Article lists, details, comments and profiles can be readable anonymously while still containing viewer-relative flags. Their scope resolver separates anonymous, authenticated and unresolved identities; only the tags read is globally invariant. This is a useful design discipline: scope asks which facts determine the response, while backend authorization asks who may obtain it. A programmer can still make an incorrect explicit global-scope declaration. [Resources registrations](evidence/local-source/examples/real-apps/realworld_resources/resources.cljs), [scope resolver](evidence/local-source/examples/real-apps/realworld_resources/scope.cljs).

The tutorial needs to maintain that discipline when it introduces authentication. Parts 2 and 4 retain global article/list keys and populate the global detail from an authenticated favorite reply. Public readability does not make `favorited`, `following` or content visibility viewer-invariant. In a new isolated browser probe, an intentionally global registration retained a synthetic prior-viewer marker after switching to Bob, with one request total. The correctly scoped reference app is not implicated. The appropriate repair is a clear viewer-scope example and session transition, rather than framework heuristics that second-guess explicit programmer intent. [Counterexample](evidence/scope-counterexample.json), [tutorial source checks](sibling-review.md), [RealWorld visibility policy](https://docs.realworld.show/specifications/frontend/api/).

The browser experiment installed two owners of one delayed article read and counted exactly one request. Releasing one owner did not prevent the remaining consumer from receiving the result. A further ensure of a fresh entry added no request. These are useful semantics, but not unique: the TanStack core counterpart also deduplicated two observers and retained the late result for the remaining observer. Cancellation, declining an obsolete result and reversing a server write are three different operations. [Resources receipt](evidence/conduit-controlled-cases.json), [TanStack receipt](evidence/tanstack-core-cases.json).

The favorite workflow is more informative than a boolean toggle. A populated detail, a list that already contains an article and a favorited list that did not previously contain it need different consequences. Conduit patches existing tagged representations optimistically, populates the authoritative detail from the reply, and invalidates collection identities to recover membership and counts. The acting username reaches the favorite mutation because an article's author is not necessarily the person whose favorites list changes. That application information cannot be inferred from the article tag alone. [Mutation declarations](evidence/local-source/examples/real-apps/realworld_resources/mutations.cljs).

Removing the favorite invalidation helper in the isolated browser left a newly favorited article absent from the cached favorites collection even though its detail had accepted the write. Restoring the helper made the same membership expectation pass; reinstating the fault made it fail again. The TanStack React counterpart showed the same fail/pass/fail pattern when its settlement invalidation was removed and restored. Both can serve the job. Resources' declaration puts the consequence beside the named write; the comparator needs application invalidation logic, which can also be centralized. [Resources control](evidence/conduit-controlled-cases.json), [TanStack control](evidence/tanstack-membership-cases.json).

The controlled overlap used distinct mutation instances: an earlier favorite was rejected, a later favorite succeeded, and the rejection was delivered last. The accepted favorite and authoritative count survived. This supports the value of Resources' recorded inverse and revision-aware conflict settlement. It does not establish arbitrary last-click-wins semantics at the server, nor does it prove that every application patch is idempotent. Conduit's ordinary buttons reuse a per-article instance; the independent-instance stress case is separately identified. [Optimistic settlement tests](evidence/local-source/implementation/resources/test/re_frame/resources_optimistic_settle_cljs_test.cljc), [browser observation](evidence/conduit-controlled-cases.json).

The sibling comparison sharpens the next test: inspect the value between rejection and recovery, not just after every refetch finishes. A snapshot can briefly replace a newer server count and still converge correctly. Record that interval and the affected views before assigning an ergonomic or correctness win to either recovery strategy. [Synthesis and revised protocol](sibling-review.md).

A viewer-change experiment withheld a response carrying a synthetic private marker, changed the application identity, replanned route resources, and then released the old response. The new viewer initially saw no data for that key and obtained an ordinary result after its own ensure. The replan is meaningful ceremony: changing a passive read's identity does not itself create a fetch cause. The application already has explicit session-resolution/replan machinery. A probe that called only the state-storage helper omitted that workflow and exposed an idle-view rendering error; that incomplete sequence is not evidence that the normal login/logout path is broken. The suite also exercises fail-closed unresolved scopes, but a complete cold-browser restore walkthrough remains unexecuted here. [Auth workflow](evidence/local-source/examples/real-apps/realworld_resources/auth.cljs), [scope tests](evidence/local-source/implementation/resources/test/re_frame/resources_scope_leak_boundary_cljs_test.cljc).

## Where the evidence supports a match, and where it does not

Cache identity, deduplication, fresh reuse, refresh-with-data, mutation instances, completion continuations, invalidation and optimistic settlement have substantial executable support. Resources' separation of application state from its runtime cache is coherent with re-frame2's model. The managed-HTTP sibling makes the reduction in application plumbing visible: its favorite flow carries explicit snapshot, synchronization and rollback events, while Resources keeps those cache mechanics in the runtime. This is evidence about that pair, not a transitive verdict about TanStack. [Managed-HTTP favorites](evidence/local-source/examples/real-apps/realworld_http/favorites.cljs).

Defaults need special care. Conduit sets a one-minute stale window and five-minute inactive retention. Resources itself defaults to no time-driven staleness; TanStack's browser queries default to immediately stale, finite inactive retention and background revalidation triggers. The TanStack core probe issued two successive requests with its native stale policy and one with the one-minute policy. Comparing request totals without matching freshness would reward a different promise to the user. Resources' no-time-staleness default and focus/reconnect behavior were covered by the module's policy tests; a controlled browser focus/reconnect comparison was not executed. [Conduit policy](evidence/local-source/examples/real-apps/realworld_resources/resources.cljs), [TanStack defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [policy observations](evidence/tanstack-core-cases.json).

Dependent reads need a separate verdict. Route `:after` orders ensure dispatches; it does not wait for one result and derive the next request's params from it. Ordinary event continuations can express that workflow, and Conduit's editor demonstrates joining a read with `:reply-to` to seed a draft. That is not itself a demonstrated two-resource dependency chain. TanStack documents data-dependent `enabled` queries and dynamic parallel queries. Teach and compare one response-to-next-read recipe, including stale continuation suppression, before deciding whether Resources needs a richer planner. [Planner contract](evidence/local-source/implementation/resources/src/re_frame/resources/route.cljc), [editor continuation](evidence/local-source/examples/real-apps/realworld_resources/article_editor.cljs), [TanStack dependent queries](https://tanstack.com/query/latest/docs/framework/react/guides/dependent-queries).

Infinite Resources is implemented, rather than merely planned. Tests cover initial load, terminal cursors, deduped load-more, failed additional pages, superseded replies and sequential refetch sweeps. Its default refresh replaces page zero while preserving the visible tail; opting into `:refetch-all-pages?` refreshes the accumulated pages. Preserving that window is not a guarantee that every retained page is fresh or that shifted page boundaries remain consistent. TanStack documents sequential full refetch, bidirectional loading and bounded retention through `maxPages`; its bounded-page behavior was executed here. Resources should be assessed separately for next-page feeds and for bidirectional, bounded collections. [Resources infinite tests](evidence/local-source/implementation/resources/test/re_frame/resources_infinite_load_more_cljs_test.cljc), [state policy tests](evidence/local-source/implementation/resources/test/re_frame/resources_infinite_state_cljs_test.cljc), [TanStack infinite queries](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries).

SSR has meaningful implementation evidence: request/frame isolation, projected payloads, hydration reconciliation, classification-sensitive keys, stale decisions and blocking timeouts. These tests include more than a helper that returns its input unchanged. Nevertheless, a running streamed application, browser hydration and deployment-specific serialization were not compared end to end. Both stacks have a supported hydration model; calling Resources uniquely safe because its cache is per frame would misdescribe TanStack's documented per-request client setup. [Resources SSR tests](evidence/local-source/implementation/resources/test/re_frame/resources_ssr_cljs_test.cljc), [projected-key tests](evidence/local-source/implementation/resources/test/re_frame/resources_ssr_projected_key_refetch_cljs_test.cljc), [TanStack SSR](https://tanstack.com/query/latest/docs/framework/react/guides/ssr).

Durable persistence and offline write recovery are the clearest broad parity gaps. A cached value surviving navigation is not persistence across a restart, and replaying a response is not a durable queue with conflict handling. TanStack supplies persistence integrations and documented mutation-resumption setup; that setup includes application functions and policy, rather than magically serializing executable code. Its cross-tab broadcast utility remains experimental. Resources explicitly defers persistence/write queues; no supported equivalent was established in this audit. [Resources deferred slices](evidence/local-source/spec/016-Resources.md), [TanStack persistence](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient), [broadcast status](https://tanstack.com/query/latest/docs/framework/react/plugins/broadcastQueryClient).

## What the alternatives teach

**TanStack Query is a stronger comparator than a bare fetch-on-render hook.** It supports client-driven prefetching, reusable typed query options, cancellation, mutation-state inspection and serialized mutation scopes. The installed core passed the serialization and request-isolation experiments. Its optimistic guide offers both cache updates and a UI projection of pending mutation variables; the latter can be shared through `useMutationState`. It avoids some rollback work, but all affected views must participate in that projection. Compare the same visible outcome and count that work. [Query options](https://tanstack.com/query/latest/docs/framework/react/guides/query-options), [optimistic updates](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates), [mutation scopes](https://tanstack.com/query/latest/docs/framework/react/guides/mutations).

**RTK Query is the closest challenge to declaration-based consequences.** Endpoint tags already express which reads a mutation invalidates. Its documentation explicitly discusses overlapping optimistic patches and recommends invalidation when undo would race. Streaming lifecycles and OpenAPI generation are concrete jobs to compare, rather than reasons to copy Redux or manufacture an additional Resources abstraction. [Automated refetching](https://redux-toolkit.js.org/rtk-query/usage/automated-refetching), [manual cache updates](https://redux-toolkit.js.org/rtk-query/usage/manual-cache-updates), [streaming updates](https://redux-toolkit.js.org/rtk-query/usage/streaming-updates), [code generation](https://redux-toolkit.js.org/rtk-query/usage/code-generation).

**SWR challenges claims of uniquely automatic optimistic behavior.** It documents optimistic data, rollback, reply population, query/mutation race handling and subscription integration. Its provider mechanism also makes a universally process-global-cache description inaccurate. These are documented capabilities, not independently executed findings here. The useful question is whether Resources makes equivalent coordination easier to author and inspect. [Official mutation source](https://github.com/vercel/swr-site/blob/main/content/docs/mutation.mdx), [cache provider](https://github.com/vercel/swr-site/blob/main/content/docs/advanced/cache.mdx), [subscriptions](https://github.com/vercel/swr-site/blob/main/content/docs/subscription.mdx).

**Apollo illustrates an alternative coherence mechanism.** Normalization lets multiple queries reference one entity, reducing repeated representation updates. It does not automatically know every filtered list's intended membership after a write. Resources should account for the extra requests and temporary inconsistency of its chosen strategy before deciding that an entity store is necessary. A GraphQL-shaped application can be a real gap without making a new GraphQL client the right pre-alpha investment. [Apollo normalization](https://www.apollographql.com/docs/react/caching/overview), [cache interaction](https://www.apollographql.com/docs/react/caching/cache-interaction).

**Riverpod contributes a useful non-JavaScript comparison.** Its disposal and retention model shows that explicit lifetime control and productivity are compatible outside React. Its persistence and mutation APIs are currently labeled experimental, which limits any maturity comparison. The transferable question is whether ownership policies are taught at the point developers encounter them, with a straightforward retained-result path. [Automatic disposal](https://riverpod.dev/docs/concepts2/auto_dispose), [persistence](https://riverpod.dev/docs/concepts2/offline), [mutations](https://riverpod.dev/docs/concepts2/mutations).

**TanStack DB raises the bar for the future, without becoming a mandatory dependency.** Its Query collection integrates REST-backed queries with collections, live queries and optimistic mutation handling. That makes a blanket “only re-frame2 can combine declarations and automatic coordination” claim untenable. It also introduces collection identity, synchronization and mutation handlers. Test one existing dense-list editing job against that complete cost before proposing a second cache or sync platform in re-frame2. [DB overview](https://tanstack.com/db/latest/docs/overview), [Query collection](https://tanstack.com/db/latest/docs/collections/query-collection).

## Ergonomics and the credible route to being better

The first-read cost is real. Resources asks an author to connect a registration, a cause and a passive projection, alongside dependency loading, scope and parameter schema. A TanStack read normally needs a client/provider and a query declaration consumed by a hook. Later, a shared Resources mutation can remove repeated coordination at its callers. Neither arrangement guarantees that the tenth read will be cheaper; TanStack's typed option factories and RTK's endpoint declarations also centralize knowledge.

The isolated tutorial check found a specific defect: Part 2 says to add managed HTTP, requires `re-frame.http.managed`, but its displayed dependency map omits `day8/re-frame2-http`. The shown dependency set failed to load that namespace; adding the missing artifact succeeded. This is a dependency/namespace probe, not a completed novice study or proof that the repaired full tutorial compiles. It is still an unusually high-value correction because it removes an immediate and reproducible stall. [Literal dependency set](evidence/consumer/literal-deps.edn), [failed probe](evidence/consumer-literal-re-frame2-1.log), [repaired probe](evidence/consumer-repaired-re-frame2-1.log).

Sibling leads exposed a broader continuity problem. Part 5 tests an auth machine that Part 3 does not construct, and says renaming registration files to `.cljc` makes them portable despite their unguarded browser interop. A focused JVM probe reproduced `No such namespace: js`; it also confirmed the public clearing API is `rf/clear`, while `resource-state` and `mutation-state` remain available. Fix the path as a whole, preserving compiler/dev dependencies and showing boot requires. Offer a concrete local demo setup alongside the currently documented `.show` API address. A minimal working route through the tutorial is more valuable than adding another inventory of gotchas. [Facade/portability probe](evidence/facade-portability-re-frame2-1.log), [source verification](sibling-review.md), [current RealWorld API](https://docs.realworld.show/specifications/frontend/api/).

Tools should turn Resources' structure into fewer translation steps. Xray already has resource instances, owners, work, lifecycle, route and invalidation views; relevant helpers passed their tests. Registry inspection exposed the favorite declaration during the repair exercise. The configured Pair connection was unavailable, and the full Xray diagnosis workflow was not exercised. Therefore this report makes no measured faster-diagnosis or completed-MCP-workflow claim. [Xray panel](evidence/local-source/tools/xray/src/day8/re_frame2_xray/panels/resources.cljs), [Pair metadata contract](evidence/local-source/tools/re-frame2-pair-mcp/src/re_frame2_pair_mcp/tools/handler_meta.cljs), [tooling limits](evidence.md).

Three opportunities deserve a small worked example before new machinery. First, show **“this write changed these reads”** using existing mutation consequences, actual params, scopes and trace evidence; function-valued declarations cannot all be enumerated statically. In particular, settlement `:affected-keys` is not a history of every optimistic touch. The existing reconciliation trace separately records optimistic keys, authoritative commits and refetch targets; use those fields to explain a guessed value that never received reconciliation, while allowing an intentionally committed optimistic value. Second, turn the empty-favorites-list regression into a reusable failure scenario that can also appear as a Story variant. Third, preserve a compact reproduction with enough classification-aware evidence for an assistant to identify and verify the repair. These are hypotheses about productivity. Their stopping rule is a demonstrably shorter, trustworthy task—not a larger graph, another registry or more diagnostics. [Settlement/trace implementation](evidence/local-source/implementation/resources/src/re_frame/resources/mutation_events.cljc).

## Recommendations

1. **Repair and exercise the public entry path first.** Make setup, namespace loading, authenticated cache scope and Part 5's tests describe the same application; correct the transport dependency, API address and stale facade names. Keep the artifact boundary; do not hide it with a second query API. Acceptance: a clean consumer follows one read, one failure, a viewer change and one mutation, then runs the tests taught for that code. This is a bounded documentation/example repair; the complete walkthrough remains necessary. An optional minimal route through the chapters may reduce first-hour load, but its benefit should be observed rather than presumed from concept counts.

2. **Teach one complete consequence and recovery story.** Use the existing Conduit favorite flow, including an initially absent collection member, an older rejected write, and identity change plus replan. Retain the library's existing tests and add only the missing application-level assertion to the appropriate existing suite if inspection shows it is absent. Acceptance: the specific application fault fails, the repair passes, and reinstatement fails without weakening the membership expectation. This is a small example/test/tooling integration, not a new conformance platform.

3. **Make one diagnosis task excellent in the existing tools.** Give the flagship a documented development launch with Xray/Pair attached: its standard build does not declare those preloads. Connect the affected entry to its write, consequence descriptors and relevant source; demonstrate the same repair through available assistant inspection. Prefer an existing view or concise recipe. Acceptance: the author can identify why a previously empty collection did not refresh and verify its repair, including missing params/scope context. Relative diagnosis time remains to be measured. This is a bounded integration experiment, likely more valuable than additional panel inventory.

4. **Treat persistence and live-data needs as explicit product decisions.** Keep them visible in the parity matrix. For a concrete consumer, first test a narrow persisted-read seam with versioning, identity and projection rules; add durable writes only when the product needs restart survival and can specify server idempotency/conflicts. Compare the integration cost with TanStack's supported plugins and DB collection options. These are medium-to-large capabilities, not prerequisites for an excellent online Conduit experience.

5. **Explain infinite-feed tradeoffs before enlarging the API.** Demonstrate the default retained tail versus full sequential refresh on a feed whose membership changes. If the target app requires backward loading or bounded retention, assess that as a specific gap and design the smallest coherent addition. Acceptance must cover missing/duplicate items, memory bounds and visible continuity, not just a longer page vector. Do not infer improved freshness from a preserved scroll window.

Do not build a normalized store, general sync engine, static consequence analyzer or permanent competitive benchmark merely to lengthen the feature list. Revisit one when an observed job exceeds the current model at an unacceptable application cost. Pre-alpha permits simplifying an awkward surface directly; it does not require preserving every spelling through another wrapper.

The decisive next evidence is a complete fresh-consumer walkthrough and a real Xray/assistant diagnosis of the already reproducible membership case. Resources has enough implemented capability to make those productivity demonstrations worthwhile now.
