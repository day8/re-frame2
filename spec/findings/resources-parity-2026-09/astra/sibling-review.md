## Claims deliberately not imported

Internal `re-frame.core-resources/clear-resource` is not an export of `re-frame.core`. Fable's first audit/matrix blurred those namespaces; its second pass withdrew that claim. The independent runtime probe establishes the distinction: use `rf/clear`; keep `resource-state` and `mutation-state`; use `handler-meta` for registration metadata. The API reference is correct; a stale `clear-*` phrase survives in the migration summary.

Fable's original two-argument `handler-meta` attempt did not justify a new arity: Astra's existing browser experiment successfully used `(rf/handler-meta {:source :store :kind :mutation :id :realworld/favorite})`. Fable's latest P2c probe uses that map form successfully and withdraws the proposal. The returned metadata and function-valued consequences still need interpretation; fixing that call alone cannot establish an assistant productivity win.

Neither “the whole scoped cache is retained” nor a demo's shared favorite flags prove that Bob can read Alice's private projection. Conversely, a required policy declaration cannot make every erroneous global claim impossible. The two controlled scope cases now demonstrate both sides of this boundary.

The siblings' stronger WIN/AHEAD labels are not adopted wholesale. A shorter comparison with managed HTTP does not establish a win over TanStack, whose query factories and centralized mutation helpers can also remove repetition. Two versus three refetches in particular recipes do not establish an unavoidable competitor cost. Compare equivalent freshness, populated detail, list membership and recovery policy first. A source-level causal model is promising; it is not a measured faster Xray or assistant task.

Fable's final revision accepts that correctly scoped keys, providers and per-request clients are real boundaries, qualifies the refetch-count comparison as recipe-dependent, and withdraws the blanket ban on read-API changes. Resources makes scope declaration more explicit; that is a concrete distinction whose authoring benefit remains to be measured. The current agreement is to preserve a coherent model while simplifying awkward authoring where a real task earns the change. [Final reviewed sibling revisions](evidence/sibling-review/round-6/receipt.json).

Likewise, lack of a Conduit demonstration does not demote implemented SSR or infinite features to specification-only. “Out of scope” explains an architecture decision but does not remove a relevant user job from the parity comparison. Apollo normalization reduces shared-entity duplication; it does not infer every filtered collection's membership without application input.

## Stronger analysis after the comparison

The reports converge on a capable online-SPA foundation, the value of the now-landed tutorial repair, better exposure of existing tools, and explicit durability/live-data gaps. They do not yet establish consensus on the magnitude of ergonomic superiority. The useful disagreement is about evidence: mechanism-level advantages are credible, while whole-task productivity remains to be demonstrated.

The next measurement should follow one feature change across all affected views, including the first useful result, an intervening failure, and recovery. That exposes costs hidden by both line counts and final-state assertions. A stale snapshot that is corrected 500 ms later, an empty collection that never learns a new member, and a previous page displayed as current are three different user failures; the test must identify which promise it is checking.

This refinement keeps the pre-alpha investment small: use the repaired tutorial to observe authoring, teach one complete consequence/dependency story, and make one tool-assisted diagnosis excellent. It provides concrete opportunities to simplify the existing API and examples without proposing a normalized store, a generic sync platform or an additional public query abstraction.
